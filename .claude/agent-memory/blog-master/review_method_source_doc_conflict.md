초안의 서사적 주장(무엇이 무엇을 바꿨는가)을 대조할 때, 명세서의 **산문 헤더 한 줄**과
같은 파일의 **표**가 어긋나는 경우가 있다. 이때 다수결로 정하지 말고
**세션 로그(`devlog/sessions/`) + 해당 커밋 본문**을 서사의 정본으로 삼는다.

**Why:** 2026-08-08 M15 회차에서 `Docs/M15_연대기_실행명세서.md:33`은 "**②·③**은 브레인스토밍
설계를 수정시켰다"라고 적고 있었는데, 같은 파일 §1 표(①=틀림→파일 분리, ②=이미 있음→힌트 줄
정제)와 세션 로그 520~522행, `1580dcf` 커밋 본문 569~573행은 **전부 ①·②**였다. 초안이 ①·②로
썼으므로 명세서 헤더만 보고 판단했다면 **정확한 초안을 반려할 뻔했다.** 명세서 산문 헤더는
표를 고치면서 같이 안 고쳐지는 일이 잦고, 커밋 본문은 그 시점의 판단이 박제돼 있어 더 낫다.
검수팀 리포트는 이 충돌을 아예 보고하지 않았다 — 표만 보고 헤더를 대조하지 않은 것으로 보인다.

**How to apply:**
- 명세서에서 근거를 뽑을 때 **표만 보고 끝내지 않는다.** 표 바로 위/아래의 요약 문장도 읽고,
  둘이 다르면 세션 로그와 커밋 본문으로 3중 대조한다.
- 충돌을 발견하면 판정서에 **충돌 자체를 적는다.** "초안이 옳고 소스가 오기다"까지 쓰고,
  게임 파일은 고치지 않은 채 곁가지로 보고만 한다([[feedback-track-boundary]] — 블로그
  트랙은 게임 파일을 안 건드린다).
- 이건 문자열 정본 규칙([[feedback-correction-value-sourcing]])의 짝이다. **문자열·수치의
  정본은 `Assets/`의 코드·에셋, 서사·인과의 정본은 세션 로그와 커밋 본문.** 명세서는 둘 다에서
  2순위다.
