분량 기준은 이력이 길다: 800~1200(v1) → 4,000~5,500(2026-07-09) → 15,000 상한 →
**4,000~45,000(2026-07-30 사용자 지시, 현행)**. 지시문·옛 메모리에 적힌 숫자를 믿지 말고
그 시점의 `.claude/agents/blog-reviewer.md`(및 `blog-writer.md`)를 직접 읽어 확인한다.

계측 명령은 **하나로 고정**됐다 — 작성팀·검수팀 동일 기준(2026-07-16 REJECTED_3X 사고의
원인이 계측 방식 불일치였음):

```bash
LC_ALL=C.UTF-8 wc -m < <초안 파일>
```

**Why:** `LC_ALL` 없는 맨 `wc -m`은 Windows Git Bash에서 문자가 아니라 **바이트**를 센다.
한글은 UTF-8에서 글자당 3바이트라 값이 약 2.3배로 부풀고, 밴드 안 초안이 상한 초과로
오판된다(2026-07-28 실제 사고: 9,094자 → 20,997로 계측돼 잘못된 축약 지시가 나감).
`LC_ALL=C.UTF-8`을 붙이면 PowerShell `(Get-Content -Raw).Length`와 값이 일치한다 —
PowerShell 재검증은 이제 불필요하다.

**How to apply:**
1. 위 명령 결과가 **3,800 미만 또는 46,000 초과일 때만** 분량 사유로 반려한다. 한글만
   세기·공백 제외·태그 제외 등 다른 셈법 금지. 밴드 안이면 "왜 더 길게/짧게 안 썼나"는
   반려 사유가 아니다.
2. 오케스트레이터가 계측치를 함께 넘겨주더라도 같은 명령으로 한 번 재계측해 대조한다
   (2026-08-08 M15 회차: 넘겨받은 11,670 = 재계측 11,670, 일치).
3. 분량과 별개로 "내용 없이 채운 문단"은 따로 본다 — 각 절이 커밋 대조 가능한 사실을
   운반하는지로 판단.
