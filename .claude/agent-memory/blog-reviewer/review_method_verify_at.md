모든 대조는 기획 브리프의 `verify_at`(= 소재 커밋 범위의 마지막 해시) 시점에서 한다.
`git show <verify_at>:<경로>` · `git grep -F "<문자열>" <verify_at> -- 'Assets/'`.

**Why:** 글은 과거 밀스톤을 다루는데 저장소는 계속 앞으로 간다. 2026-07-28 M10 회차에서
HEAD로 봤으면 정확한 초안 3건이 반려될 뻔했다. 2026-08-08 M15 회차(`verify_at=ece7029`)
시점엔 HEAD에 이미 M17~M21이 들어와 있었다. **HEAD와 다른 것 자체는 반려 사유가 아니다.**

**How to apply:**
1. 행 번호까지 같은 시점 기준으로 적는다(문자열은 verify_at, 행 번호는 HEAD 혼용 사고 있었음).
2. 화면 문자열 검사는 검수팀만 할 수 있다(작성팀은 Read/Write뿐). 특히 `Docs/M*_실행명세서.md`
   **코드 스케치 주석 안의 플레이스홀더**가 실제 대사로 새어 들어오는 유형이 잦다 —
   명세서에서만 발견되고 `Assets/`에 없으면 전부 이 유형이다.
   ↔ 뒤집힌 사례도 있다: M15 회차에서 초안이 "처음엔 판 번호를 붙이려다 되돌렸다"고 썼는데
   명세서 W3 스케치 주석(`"▶ 판 4 — 진행 중 …"`)이 그 되돌림의 **근거**였다. 명세서 주석은
   화면 문자열의 근거로는 못 쓰지만 "명세와 달라진 것" 서사의 근거로는 쓸 수 있다.
3. 커밋 본문(`git show <hash>` 의 메시지)이 세션 로그만큼 좋은 1차 소스다 — "명세와 달리한
   것", "🟡 관찰", ADR 번호가 대체로 커밋 본문에 들어 있다.
4. `git diff --stat <범위> -- <파일>` 이 비어 있으면 "한 글자도 안 바꿨다" 류 주장의 물증이 된다.
