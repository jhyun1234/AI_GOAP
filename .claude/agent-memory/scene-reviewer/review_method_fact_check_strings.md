사실 대조 = **화면에 놓이는 모든 문자열** 을 원문 대조한다. 숫자만이 아니다.

**Why:** ep02s 1차 검수(2026-07-30) 사례. 작성팀은 "수치 정직성" 절을 두어 여섯 개
숫자를 원문과 대조하고 "화면이 주장하는 숫자는 여섯이고 전부 원문에 있다"고 정직성을
자랑했다. 그런데 같은 회차 S1 에서 원문에 없는 대사 두 개("탐구하고 싶어.", "겁이
나요.")를 회색 예시 대사로 화면에 놓았고, `writer.md` 6절이 이를 "원문 그대로"라
표기했다. 검수팀도 처음엔 숫자만 봐서 놓칠 뻔했다.

원문에 있는 대사는 정확히 하나("왜 나만 시키지..")였는데 셋으로 늘어난 이유는
아마 도형(대비를 세우려면 3자리가 필요) — 하지만 도형 구실이 문자열 창작을 허가하지
않는다. 화면에 대사가 놓이는 순간 시청자에게는 "이 게임의 실제 대사"로 보인다.

**How to apply:** 사실 대조 절차에

1. spec 안의 모든 label · line · expects · note 등 **화면 텍스트 필드를 열거**하고
2. 각각을 원문 grep 로 확인
3. 원문에 없으면 (a) 도형 파라미터(수치·색·비율)인지 (b) 원문에 근거 있는 요약인지
   (c) 창작인지 셋 중 어디에 해당하는지 판정
4. (c) 창작이 발견되면 반려 사유로 등록 — 시청자에게 "게임의 실제 요소"로 오해될 여지가
   있으면 특히

숫자 대조와 문자열 대조는 **다른 두 절차**로 분리한다.

## 🔴 "없다"는 판정은 개수가 아니라 **매치 문맥**으로 한다 (ep11s 검수 오판, 2026-08-08)

**Why:** ep11s 화면 문자열 「쫓아가서 건네준다」를 두고 내가 *"원문에 없다(소제목의 「건네주기」뿐)"*
라고 🟡 정정을 냈는데 **틀렸다.** 발행 HTML 에 큰따옴표째로 **두 번 실재**했다. 원인은 방법이다 —
`len(re.findall(패턴, 본문))` 의 **숫자만** 보고 `1` 이 나오자 「소제목 하나뿐」이라고 결론지었다.
매치를 출력했으면 즉시 보였다. 🔑 게다가 나는 **태그를 지운 본문**에서 셌는데, 인용문이 `<p>`·`<b>`
경계에 걸리면 공백이 하나 더 끼어 패턴이 안 맞는다. 작성팀이 반박했고 작성팀이 옳았다.

**How to apply:**
- 🔴 **`count` / `len(findall)` 로 「없다」를 결론짓지 마라.** 반드시 `finditer` 로 돌며
  **앞뒤 100자를 출력해 눈으로 본다.** 0건이 나왔을 때가 가장 위험하다 — 그게 반려 사유가 된다.
- 🔴 **태그 제거본과 원본 HTML 둘 다에서 찾는다.** 태그를 공백으로 바꾸면 공백이 늘고,
  글에는 일반 공백 아닌 문자가 섞이기도 한다. 한쪽에서 0건이면 다른 쪽에서 다시 본다.
- 🔴 **어미/조사만 다른 변형을 같이 찾는다.** 「건네주기」(소제목)와 「건네준다」(본문)처럼
  같은 개념이 두 형태로 쓰이는 일이 흔하다. **핵심 어간**(`건네주`)으로 먼저 훑고 문맥을 본다.
- 🔑 **작성팀이 반박하면 반박이 먼저다.** 내 지적이 「원문에 없다」류면 재검증 비용이 1분이고,
  틀렸을 때 잃는 것은 화면에서 옳은 문자열이다.

## 🔴 「2026-08-09 16:20 기준」처럼 **기준 시각을 선언한 수치**는 그 시각의 트리에서 전수 재측정한다

**Why:** lf02 3차(2026-08-09). 원장 샷이 스스로 「16:20 기준」이라 못 박고 일곱 값을 띄웠는데
`SO ASSETS 110 · SPECS 31` 은 그 시각에 **116 · 32** 였다(에셋은 16:06 부터 116, 명세서는
15:33 커밋에서 32). 두 값 다 브리프 원장(**오전** 실측)에 실재하므로 **지어낸 수는 아니었고**,
작성팀 표는 이 두 칸만 「변동 없음」이라고 적어 뒀다 — **재보지 않은 자기보고**였다.
같은 표의 다른 칸들은 출처를 정직하게 표시했기 때문에 더 안 보였다.

🔑 **드리프트(쓸 때는 맞았는데 나중에 낡음)와 미측정(쓸 때부터 틀림)은 다른 결함이다.**
드리프트는 「렌더 직전 재실측」으로 넘겨도 되지만, 미측정은 그 자리에서 잡아야 한다.

**How to apply:**
- 화면에 **기준 시각·기준일이 붙은 수치**가 있으면, 그 시각의 커밋을 찾아
  `git ls-tree -r <커밋> <경로>` 로 **일곱이든 열이든 전부** 다시 센다. 하나도 빼지 않는다.
  (`git rev-list --count <커밋>` · `--count <커밋> -- . ':(exclude)tools' …` 로 커밋 수,
  `ls-tree | grep -c` 로 파일 수. 🔴 한글 경로는 `-c core.quotepath=false` 없으면 0건이 나온다.)
- **값이 언제 바뀌었는지 이력을 뽑아** 보고서에 붙인다 — 그래야 「기준 시각을 언제로 잡아야
  맞는가」가 보인다(`for C in $(git log --format=%h --since=…); do … done | awk '$2!=p'`).
- 화면 수치는 **자막 · `say`(한글 읽기까지) · kind 의 상수 배열 · `chapters` · `blurb`**
  다섯~여섯 자리에 흩어진다. **한 자리만 고치면 일관성이 깨지므로 반드시 동시 갱신을 요구**한다.
