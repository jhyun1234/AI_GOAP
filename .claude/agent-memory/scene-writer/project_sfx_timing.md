효과음 `at`·`delayMs` 는 **자막 내용이 아니라 그 샷 kind 의 `draw` 를 풀어서** 정한다.
`cue(i, lead, span)` 은 `a = tᵢ − lead` ~ `b = tᵢ + durᵢ × span` 의 0~1 이고
`durᵢ` 는 **발화 + pauseAfter** 다(`engine/engine.js:156, 240-245`). 창 = `lead + durᵢ × span`.

🔴 **함정 — 사건이 `cue` 가 아니라 `t` 로 도는 kind 가 있다.**
ep02s `tripwire.js` 의 걸림은 `u = frac(t / 5.2)` 로 돌고 `trapCue` 는 라벨만 붙인다.
자막 인덱스만 보고 `trapCue` 자리(at2)에 `latch` 를 놓으면 그 순간 실선은 곧고
화살표는 정방향이라 **아무 일도 안 일어나는 화면 위에서 소리가 난다.**
실제 걸림은 at1+324ms 였다. `cue` 이름과 사건 시각이 일치한다고 가정하지 말 것.

**Why:** ep02s 효과음 재작업(2026-07-31)에서 사용자 참고 배치 6개 중 3개가 draw 와
어긋나 있었다 — S8(위 사례) · S5(회전은 `flipCue`=at0 이 몰고 at1 은 밑줄만 자란다) ·
S3(wardline 은 알파·위치가 전부 연속 램프라 물 이산 사건이 아예 없다).
자막만 읽으면 셋 다 그럴듯해 보인다.

**How to apply:** 소리를 달기 전에 그 kind 에서 **가지가 갈리는 지점**을 찾는다 —
`if (k > 0.4)` 로 색이 바뀌거나(`ink`→`accent`), `absScale < 0.06` 처럼 다른 그림이 켜지거나,
`inK` 가 0→1 로 글자를 통째로 여는 자리. 알파가 `clamp(k × 1.4)` 로 램프하기만 하는 곳은
소리를 물 자리가 아니다. 그런 샷은 **조용히 두는 게 맞다.**
`riser`·`sweep` 처럼 긴 소리는 시작점이 아니라 **에너지 정점**(sweep 은 `sin(PI·k)` 라
한가운데)을 사건에 맞춘다.

## 🔴 `gain` 상한은 kind 가 **아니라** kind + 옵션이 정한다 (ep09s-1 반려, 2026-08-07)

지시서의 표(`tick 0.065` · `latch 0.071`)는 **기본 옵션의 값**이다. 그대로 옮겨 적으면 걸린다.

**Why:** ep09s-1 이 「tick 상한 0.065」를 근거로 `gain 0.060` 을 썼는데,
그 조합(`dur 0.052 · freq 1180`)의 실제 상한은 **0.0598** 이라 렌더 로그에
`⚠️ sfx tick: 피크 천장(0.46)에 걸려` 가 떴다. 천장에 걸리면 RMS 정규화가 없애 둔 불균형이
되살아나 **그 소리만 조용해진다.** 지시서에도 「상한은 kind + 옵션이 정한다」고 적혀 있는데
표의 숫자만 봤다.

**How to apply:** 자기 설정의 값이 필요하면 재라 —
`synth(kind, {…opts, gain}, 48000)` 의 피크로 `0.46 ÷ (peak/gain)`.
🔴 **그 결과값도 박제하지 마라**(0.0598 은 그 dur·freq 에서만 참이다).
🔑 기본값 0.060 을 쓰고 도드라져야 하는 소리만 올리라는 원칙이 여기서도 안전판이다 —
뾰족한 kind(tick·latch)는 기본값조차 조합에 따라 천장에 닿을 수 있으니, 그 둘만은
**올리기 전에 재고 못 재면 0.058 쪽으로 내려 잡는다.**

## 🔴 `delayMs` 는 실측이 나오면 **반드시** 다시 푼다

산정 초/자로 낸 값은 늦거나 이르다. ep09s-1: tick **1,870 → 1,541**(−329ms = 9.9프레임) ·
latch **2,130 → 2,012**. 창은 `pauseAfter` 를 포함한 **실측 `rel dur`** 로 잡는다.
🔴 그리고 **자막 글자가 바뀌면 또 풀어야 한다** — ep09s-1 은 사실 정정으로 한 줄이
19 → 20자가 되면서 그 줄의 latch 값이 다시 미확정이 됐다.
🔑 형제 편 관측: **자막을 한 글자도 안 건드린 줄도** 초/자 가정이 실측과 다르면 `l.dur` 이
바뀌어 다시 풀어야 한다. **보정치를 만들어 끼워 넣지 말고 미확정으로 신고하라** —
ep09s-1 이 1차본에서 「어림값」이라고 신고했고 그 판단이 맞았다.

🔑 **오차는 같은 회차 안에서도 3배 갈린다** (ep12s-1, 2026-08-08): 산정 → 실측이
thud **1,850 → 2,070**(+220ms = 30fps 6.6프레임) · drop **1,560 → 1,630**(+70ms = 2.1프레임).
두 줄 다 같은 산정 계수(192ms/자)를 썼는데 실측은 **215.75 / 201.7ms/자**였다.
→ 「이 회차의 초/자」 같은 단일 계수조차 `delayMs` 에는 못 쓴다. **총 길이 예측에만 쓰고
시각은 줄마다 실측 `rel` 로 푼다.**

## 🔴 돌려막기는 kind 하나가 아니라 **kind 「쌍」**으로도 난다 (ep12s, 2026-08-08)

같은 글에서 갈라진 형제 편 `ep12s-1` 과 `ep12s-3` 이 **둘 다 `thud` 로 열고 `drop` 으로 닫는**
상태로 나왔다. 파라미터는 갈렸고(thud 배음 격자 `264·528·792` vs `198·396·594` = 겹침 0 ·
drop 하강 폭 280Hz vs 570Hz = 2.04배) 사건도 달랐는데(고정 vs 헛닿음 / 값이 반이 됨 vs 밭이 부서짐),
**연달아 보면 형태가 같다.**

**Why:** 형제 편은 같은 원문·같은 축을 쓰므로 **각자 정직하게 골라도 같은 답에 도달한다.**
「전수를 세서 파라미터가 안 겹치는지」만 보면 이 유형은 통과한다 — 전수 대조는 **한 소리씩**
보기 때문이다. 그리고 형제 편은 대개 `scene.json` 이 아직 없어서 **작성 시점에는 셀 수도 없다**
(세 편 다 서로를 "대조 대상 0건"이라고 적었다).

**How to apply:**
- 🔴 **뜻이 덜 맞는 kind 로 갈아치우지 마라.** 그건 「돌려막기를 피하려고 소리를 틀리게 고르는」
  반대편 잘못이다. 값은 두고 **`why` 에 형제 대조 행을 남겨 판정을 검수팀에 넘긴다.**
- 대조 행에 넣을 것 셋: ①파라미터 거리(배음 격자·하강 폭처럼 **파형에 직결되는 양**)
  ②그 소리를 고른 **사건**이 다른가 ③**회차의 소리 문장**이 다른가
  (예: 「박힌다 → 반으로 떨어진다」 vs 「헛되이 닿는다 → 무너진다」).
- 🔑 형제 편이 뒤에 나오면 **그때 다시 세라.** 「작성 시점에 없었다」는 면책이 아니라 예약이다.

## 🔴 `why` 에 **「>0.5 임계」를 근거로 쓰지 마라** — 소리는 그보다 이른 자리에 놓인다 (lf02, 2026-08-09)

`delayMs` 는 실무상 거의 항상 **리빌이 열리는 첫 프레임**(`ease(cue) ≈ 0.05~0.16`)에 떨어진다.
그런데 `why` 를 쓸 때는 kind 코드에서 **눈에 띄는 분기**(`if (k > 0.5)` 로 색이 바뀌는 줄)를
집어 「거기다」라고 적기 쉽다. 그러면 **배치는 맞는데 서술이 틀린다.**

**Why:** lf02 는 효과음 11개가 전부 「리빌 시작」에 놓인 **일관된 배치**였는데,
`why` 가 임계를 명시한 둘만 실물 프레임과 어긋났다 — S2 `drop` **1.31초**,
S5 `latch` **0.84초** 이르다(22.00초 프레임에서 막대는 아직 기준선 위 40px, 90.50초
프레임에서 값은 `6` 한 글자·테두리 흰색). 검수가 「소리를 옮겨라」로 읽을 뻔했고
그랬으면 **재렌더 22분**이 들 뻔했다.

**How to apply:**
- `why` 에는 **자기가 `delayMs` 를 정할 때 실제로 쓴 기준**을 적는다. 「리빌이 열리는
  첫 프레임」이면 그렇게 쓴다. 코드에서 다른 줄을 인용하면 두 기준이 갈린다.
- 🔴 **어긋남을 발견해도 소리부터 옮기지 마라.** 배치가 회차 안에서 일관되면
  **고칠 것은 서술이다.** 옮기는 쪽은 렌더 비용이 크고 일관성을 깬다.
- 렌더 후 검수는 `delayMs` 를 **실물 프레임**으로 재므로, 산정 단계의 `why` 는
  「이 자리는 실측 뒤 확인 대상」이라고 표시해 두는 편이 안전하다.

## 🟢 사건을 `since(i)` 위에 세우면 `delayMs` 가 **TTS 와 무관해진다** (ep13s-3, 2026-08-10)

되풀이되는 사건(주기 루프)을 `t`(샷 시작 기준) 대신 **`since(i)`(그 자막이 시작된 뒤 흐른 초)**
위에 세우면, `delayMs` 와 **원점이 같아져** 자막 길이가 바뀌어도 값이 안 움직인다.

```js
const s1 = since(1);                       // 아직이면 음수
const q  = s1 >= 0 ? frac(s1 / P) : 0;     // 주기 P 루프
const wipe = ease(clamp((q - 0.56) / 0.09));
// → 지움 구간 = since(1) 0.952~1.105s (P=1.7) · 한가운데 1.0285s
// → sweep(정점이 한복판)이면 delayMs = 1029 − dur/2 = 810  ← 실측 없이 확정
```

**Why:** `cue(i, lead, span)` 창은 `lead + rel × span` 이라 **실측 `rel` 이 있어야** 시각이 나온다.
그래서 초안의 `delayMs` 는 늘 어림값이고 실측 뒤 다시 풀어야 한다(위 절들). 반면 `since()` 는
자막 시작을 0 으로 두므로 **그 위에 세운 사건의 절대 시각은 자막 길이와 독립**이다.

**How to apply:**
- **주기적으로 되풀이되는 사건**(같은 일이 2~3번 일어나는 루프)에 특히 쓴다. `t` 로 돌리면
  앞 줄이 한 글자만 늘어도 사건 시각이 통째로 밀린다.
- 앞 구간(다른 자막)과의 이음매는 **두 구동이 같은 값에서 만나게** 설계하면 튐이 없다
  (ep13s-3 `graze` 는 cue 구동 `hxA` 와 루프 구동 `hxB` 가 둘 다 `F0` 에서 만난다).
- 🔴 **한 회차 안에 두 종류가 섞이면 `notes` 에 신뢰도를 갈라 적어라.** ep13s-3 은
  S2 810ms = 확정 / S4 1,400ms = 어림값이다. 같은 표에 나란히 두면 검수가 둘 다 재계산한다.
- ⚠️ `since(i)` 는 자막이 시작되기 전에는 **음수**다. `clamp` 없이 `frac()` 에 넣지 마라.

### 🟢 되풀이가 아니라 **한 번뿐인 사건**에도 쓸 수 있다 (ep14s-1, 2026-08-10)

ep13s-3 은 주기 루프(되감기 두 번)에 썼지만, **한 번만 일어나는 사건**(그릇이 내려앉는다 ·
채움이 바닥까지 내려간다)도 그냥 `since(i)` 위에 절대 초로 세우면 된다:
`landK = ease(clamp((s1 - 0.95) / 0.65))` → 착지 = 1.60초 → `delayMs 1600` (실측 불필요).
그러면 **회차의 sfx 둘이 다 초안에서 확정**되고 실측 라운드에 재계산이 0 이다.

- 🔴 **지켜야 할 조건은 하나** — 그 자막이 사건 시각보다 길어야 한다.
  `since(i)` 가 도는 최댓값 = `rel` + `SHOT_TAIL 0.35`. 여유를 `notes` 에 적어 두면
  실측 뒤 **그 여유만 다시 확인**하면 되고 값은 안 푼다.
- 🟢 **부수 이득이 실물로 확인됐다**: 어미 3연속을 고치느라 `sfx` 붙은 샷의 자막 자수를
  바꿨는데 **`delayMs` 재계산이 0**이었다. [[ending-variety]] 의 「고칠 줄은 sfx 없는
  샷에서」 제약이 이 설계에서는 풀린다.
- ⚠️ 대신 **등장 램프와 페이드는 여전히 `cue`** 로 둔다(자막에 물려야 하므로).
  한 kind 안에 두 구동이 섞이니 **머리 주석에 어느 쪽인지 적어라.**

### 🟢 같은 수법이 **페이오프 지각**도 원리적으로 막는다 (ep14s-3, 2026-08-10)

`since()` 의 쓸모는 소리에만 있는 게 아니다. **③남는 한 줄의 완성 시각**을 `cue()` 창
(`lead + rel × span`)이 아니라 `since()` 위에 세우면 **자막이 짧아져도 완성이 안 밀린다.**
ep08s-3 이 반려된 형태 — *마지막 자막이 2.79초로 짧아 cue 창이 좁아지면서 판정 완성이
0.54초 늦어 아웃트로 카드에 가려짐* — 가 그 자리에서 **일어날 수 없게 된다.**
(형제 ep08s-1 은 같은 설계인데 자막이 4.78초라 통과했다. 즉 그때 갈린 것은 설계가 아니라
**자막 길이**였고, `since()` 는 그 변수를 통째로 없앤다.)

**How to apply:** 페이오프 샷의 리빌을 `since(n)` 초 단위로 적고 `notes` 에
「완성 = `since(1)` 1.15초 = 그 줄 `rel` 예측의 37~40%」처럼 **비율까지** 적어 둔다.
그러면 실측이 와도 검수가 재계산할 것이 없다 — 확인만 하면 된다.
🔴 단 `since()` 는 **절대 초**라 자막이 예상보다 **크게 짧아지면**(리빌 1.15초 > 자막 1.0초)
반대로 리빌이 자막보다 오래 간다. 자막 최소 길이(2초)와의 여유를 함께 적어라.

- ⚠️ 부작용 하나: 알파를 시간으로 갈라 겹침을 막는 설계(`A 는 s1=0.26 에 0`, `B 는 s1=0.58 부터`)도
  `since()` 라야 보장된다. `cue()` 로 짜면 두 구간의 절대 간격이 자막 길이에 따라 줄어든다.

### 🔴 `since()` 도 **「줄 안의 낱말 위치」**까지 면역은 아니다 — 소리를 옮기지 말고 **줄을 잘라라** (ep15s-5, 2026-08-10)

`since(i)` 는 **자막의 시작**을 0 으로 고정할 뿐, 그 줄 안에서 특정 낱말이 언제 발음되는지는
여전히 TTS 가 정한다. 사건이 「그 낱말이 나오는 순간」이면 `delayMs` 를 줄 길이의 60% 같은
비율로 잡아야 하는데, **그 비율은 회차·엔진 설정마다 달라 못 고정한다**(같은 편 안에서도
자당 6% 갈린다 — 위 ep12s-1 관측).

ep15s-5 초안: `게으름뱅이 둘 다 그냥 죽었어, 별 이야기가 없었다.` 한 줄에서 「죽었어」가
줄의 60% 지점이라 `drop` 을 2,700ms 쯤에 놓아야 했다.
→ **이름을 앞 줄로 옮겨** 둘째 줄이 `그냥 죽었어,` 로 **시작하게** 잘랐다.
이제 사건(`since(1)` 0.30~1.20)·소리(555ms)·말이 같은 구간이고 재계산이 0 이다.

**How to apply:** `delayMs` 를 「줄의 몇 % 지점」으로 잡고 있다는 걸 깨달으면 그건
**소리 문제가 아니라 자막 구성 문제**다. 사건을 부르는 낱말이 **줄 머리에 오도록** 줄을
다시 자르면, 소리·그림·말이 한꺼번에 맞고 실측 의존이 통째로 사라진다.
