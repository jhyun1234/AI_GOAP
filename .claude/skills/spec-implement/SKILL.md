# 실행명세서 구현 절차

## 0단계 — 착수 전 (작업대 정리)
1. `git status`로 작업 트리를 확인한다. 이번 항목과 **무관한 변경이 섞여 있으면 먼저 정리한다**
   (관련 없는 것은 별도 커밋하거나 사용자에게 보고). 되돌릴 지점이 없는 상태에서 구현을 시작하지 않는다.
   > Superpowers `executing-plans`는 여기서 git worktree 격리를 요구한다. Unity는 worktree마다
   > `Library/` 전체 재임포트(수십 GB·수십 분)라 비용이 커서 채택하지 않는다. 대신 **"직전 커밋 =
   > 언제든 돌아갈 수 있는 지점"**을 보장하는 것으로 같은 목적을 달성한다.
2. 브랜치를 확인한다. 이 리포는 main 작업이 기본이므로 금지하지 않되, **main이면 보고에 명시**한다.

## 1단계 — 코드를 열기 전에
1. 명세서의 ADR/아키텍처 결정 절을 전부 읽는다. 구현 중 판단이 갈리면 여기 답이 있다.
2. 담당 항목(예: W5)의 ⚠️ 오해 위험 절을 읽는다. 여기 적힌 실수를 하지 않는 것이 최우선이다.
3. 항목의 "대상 파일"을 열어 코드 스케치와 실제 코드의 차이(이름, 시그니처)를 확인한다.
   스케치의 프로퍼티명이 실제와 다르면 실제 코드를 따르고, 그 사실을 커밋 메시지에 남긴다.

## 2단계 — 구현 중
- 스케치는 뼈대다. 그대로 복붙하지 말고 프로젝트의 기존 스타일(한글 주석, 상수 명명, region)에 맞춘다.
- 수치가 필요한데 명세가 "실제 값을 찾아 쓸 것"이라 하면: grep으로 런타임 원본을 찾는다.
  못 찾으면 임의 값을 넣지 말고 TODO 주석 + 질문으로 남긴다.
- 명세에 없는 개선이 떠오르면: 구현하지 않는다. 커밋 메시지나 이슈에 제안으로만 남긴다.
- **서브에이전트에 위임했으면 보고를 믿지 않는다** — `git diff`로 실제 변경을 직접 확인한 뒤에만
  그 결과를 DoD 근거로 쓴다. "완료했습니다"는 증거가 아니다.

## 즉시 멈추고 질문할 때 (밀어붙이지 않는다)
- 명세의 ADR끼리 충돌하거나, 이 항목이 다른 ADR을 위반해야만 성립할 때
- 명세가 지시한 수치의 런타임 원본을 못 찾을 때
- DoD가 검증 불가능하게 쓰여 있을 때 (무엇을 돌려야 통과인지 알 수 없을 때)
- 대상이 동결 코어(GOAPPlannerJob)나 재사용 라이브러리(JPS·타일예약·FoW)일 때
- **같은 수정을 2회 시도했는데 게이트가 계속 red일 때** — 3회째를 시도하지 말고 진단을 보고한다.

## 3단계 — 완료 판정 (증거 없이는 완료 없다)
- 항목의 DoD 체크리스트(`- [ ]`)를 하나씩 직접 수행한다.
  수행 완료 항목은 `- [x]`로 표시한다. **읽고 넘기는 것은 수행이 아니다.**
- **이번 작업에서 실제로 돌린 명령의 출력만 근거가 된다.** 아까 돌린 결과·예상·"될 것 같다"는 근거가 아니다.
  보고에는 판정 근거를 한 줄로 함께 적는다 (예: `EditMode 346/346 pass`, `build exit 0`).
- CLAUDE.md의 커밋 전 체크 4종을 실행한다.
- 전부 `- [x]` → 커밋 (형식: `feat(goap): <항목번호> <요약>`, 이슈 연동 시 `Fixes #N`).
- 하나라도 미완 → 커밋하지 않고 미완 항목을 명시해 보고한다. "거의 됐다"는 없다.

### 합리화 차단표 (이 문장이 떠오르면 그 자리가 위험 지점이다)

| 떠오른 생각 | 실제 |
|---|---|
| "컴파일 통과했으니 됐다" | 컴파일은 게이트가 아니다. EditMode M0-T를 돌려라 |
| "게이트 green이니 명세대로다" | 게이트는 ADR 위반을 잡지 DoD를 잡지 않는다. DoD는 손으로 |
| "테스트를 새로 썼다" | **그 테스트가 실패할 수 있는지 확인했는가** (전과 3회: 실패 불가능한 테스트) |
| "수치가 대충 맞는다" | 산수는 손으로 검산한다 (전과: 감쇠율 계산 오류로 전원 아사) |
| "에이전트가 완료라고 했다" | `git diff`로 직접 확인하기 전엔 미확인이다 |
| "명세와 조금 다르지만 이게 더 낫다" | 더 나은 것은 **제안**으로 남기고 구현은 명세대로 |
| "이번 한 번만 건너뛰자" | 예외 없음. 건너뛴 검증은 다음 밀스톤에서 청구된다 |

## 4단계 — 커밋 이후 (여기서 끊지 않는다)
- **커밋 본문에 "왜"를 쓴다** — 훅이 그 본문을 세션 로그의 '왜' 칸에 그대로 싣는다.
- 훅이 못 채우는 칸(**막혔던 문제/해결 · 다음에 할 일**)은 대화에만 있으므로 `devlog/sessions/`에 직접 적는다.
- 다음 행선지를 명시한다: 다음 항목으로 갈지 / `spec-review`로 대조할지 / 사용자 Play 확인이 필요한지.
- 밀스톤의 마지막 항목이었다면 `devlog/` 변경분 커밋·푸시까지 마친다.

## 보고 형식
[항목번호] 상태(완료/부분/차단) / DoD 체크 결과 **+ 판정 근거 한 줄** / 명세와 달리한 것과 사유 / 발견한 문제
+ 이번 변경이 게임에서 어떻게 보이는지 비개발자용 한 문단 (CLAUDE.md 설명 의무)
