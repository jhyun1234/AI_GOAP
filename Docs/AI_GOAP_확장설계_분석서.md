## 1. 현재 시스템 진단 요약

### 1.1 잘 구축된 부분 (유지·계승)

| 영역 | 평가 | 근거 |
|---|---|---|
| A* 플래너 코어 | ★★★★★ | Burst Job, min-heap, g/f-cost 분리, admissible 휴리스틱(2.9 < 최소비용 3.0), 깊이 6·노드 2048 제한, "이미 달성" 특수값(-1) — 상용 수준 |
| FSM 래핑 구조 | ★★★★☆ | Idle→Planning→Executing→Replanning 생명주기, 틱 그룹 분산(1/6), LOD 모드 — 70명 규모 대응 설계 완료 |
| 명령 거부 시스템 | ★★★★☆ | ConflictScore + Loyalty 임계값 + RefusalBubble — 이 게임의 정체성. RimWorld 대비 차별점으로 이미 작동 |
| 팩션 AI | ★★★☆☆ | 자원 부족 기반 자율 침략 결정, 3개 팩션 개성(숲의 부족/철의 도시/상인 연합) 골격 존재 |
| 주변 시스템 | ★★★★☆ | 계절, FoW, 자원 재생, 모집, 건설 큐, VillageAdvisor 자동 건설 — 콜로니 심 인프라 완비 |

### 1.2 한계 요약 (2장에서 상세 분석)

| # | 한계 | 체감 증상 |
|---|---|---|
| L1 | 불리언 전용 월드 스테이트 (43슬롯 0/1) | 플랜이 1~3스텝으로 짧고 획일적. "수량"을 계획하지 못함 |
| L2 | 정적 액션 비용 (역할 보정만) | 같은 Goal → 항상 같은 플랜. 거리·위험·계절 무시 |
| L3 | 휴리스틱 무력화 (h ∈ {0, 2.9}) | 사실상 Dijkstra. 다중 목표 플래닝 불가능 구조 |
| L4 | Goal 선택 로직 이원화 + 하드코딩 if | Brain과 FSM에 분산, 우선순위가 이산적이라 상황 감응 없음 |
| L5 | Effect가 대입(=)만 지원 | 자원 소모/증가 모델링 불가, 동일 액션 반복 무의미 |
| L6 | 개인차 부재 (역할 비용 보정뿐) | 70명 주민이 사실상 7종의 복제인간 |
| L7 | AI의 사고 과정이 비가시 | 플레이어는 "왜 저러지?"만 느끼고 "똑똑하다"를 못 느낌 |
| L8 | 주민 간 협동 계획 없음 | 동일 자원 노드에 몰림, 분업이 창발이 아닌 우연 |

## 2. 핵심 한계 심층 분석

### L1. 불리언 월드 스테이트 — "플랜과 현실의 괴리"

**현재 구조**
```
슬롯 예시 (GOAPPlanningSlots.cs):
  WoodLow = 0        // woodAvailable < 30 → 1
  HasWoodForBuilding // woodAvailable >= 35 → 1
  ResourcesGathered  // Goal 달성 플래그
```

**문제의 메커니즘**

1. 목재가 5개인 상황 (`WoodLow=1`)에서 `GatherResources` Goal 발동.
2. 플래너 내에서 `ChopWood` 액션 1회의 Effect가 `ResourcesGathered=1` → **플랜 길이 1로 즉시 성공**.
3. 실행 후 실제 목재는 5→10. 여전히 부족(`WoodLow=1`).
4. 다시 Idle → 다시 Planning → 다시 ChopWood... **플래너가 아니라 리플래닝 루프가 일을 하고 있음**.

**결과**: GOAP의 존재 이유인 *멀티스텝 체인 계획*이 발현되지 않는다. 플레이어 눈에는 "한 번 캐고 멍때리다 또 캐러 가는" 어색한 행동으로 보인다. 사실상 비싼 FSM으로 동작 중이다.

**부수 문제**: `HasCookedFood` 같은 자원 보유 플래그가 Effect로 소모되지 않아, "요리 1개로 주민 3명이 동시에 식사 계획"을 세우는 논리적 모순이 발생 가능하다 (실행 시점 검증으로 걸러지지만, 그만큼 리플래닝 부하 증가).

### L2. 정적 비용 — "지도를 못 보는 계획자"

`GOAPActionRegistry.BuildActionDefs(role)`에서 비용이 **플래닝 시작 전에 확정**된다. 나무꾼의 ChopWood는 언제나 같은 비용이다.

- 바로 옆 나무 vs 적 진영 옆 나무: 동일 비용.
- 겨울(채집 효율 저하) vs 가을(0.333 배율): SeasonManager가 존재함에도 플래너 비용에 미반영.
- 부상 상태에서의 전투 vs 만전 상태: 동일 비용 (거부 시스템에서만 반영).

GOAP의 진짜 매력은 **상황이 바뀌면 플랜이 바뀌는 것**인데, 비용이 정적이면 상황이 바뀌어도 플랜이 안 바뀐다.

### L3. 휴리스틱 — "안내자 없는 A*"

`h(n) = 미충족 목표 슬롯 수 × 2.9`. 그런데 `BuildGoalState()`를 보면 **모든 Goal이 단일 슬롯 마스크**다 (`SurviveHunger → HungerSolved=1` 하나뿐).

→ h는 목표 미달 시 2.9, 달성 시 0. 두 값뿐. A*가 방향성을 전혀 얻지 못하고 균등 탐색한다. 지금은 액션 19개·깊이 6이라 버티지만, 액션이 40개를 넘어가면 MAX_NODES=2048이 순식간에 소진된다. **확장의 발목을 잡는 시한폭탄.**

### L4. Goal 선택 — "반쪽짜리 두뇌"

```
VillagerBrain.GetHighestPriorityGoalId():
  P0(생존), P1(전투)까지만 판정 → P2 이하는 null 반환
VillagerFSM.State_Idle():
  P2a(건설), P2b(채집), P3(탐험)을 하드코딩 if로 판정
```

- 로직이 두 파일에 분산 (코드 내 TODO 주석으로도 인정됨).
- 이산적(binary) 판정: 배고픔 79는 완전 무시, 80은 최우선. **"슬슬 배고파지니 일 마치고 먹으러 가야지"** 같은 인간적 판단 불가.
- 동순위 Goal 간 경합 불가: 자원도 부족하고 건설도 대기 중이면 항상 건설 우선 (코드 순서가 곧 우선순위).

### L5~L8 요약

- **L5**: Effect가 `state[s] = v` 대입뿐이라 `wood += 5`, `cookedFood -= 1` 표현 불가. L1과 동전의 양면.
- **L6**: Mood(70)·Loyalty(55) 필드는 존재하나 Loyalty만 비용 배율에 쓰임. Mood는 사실상 미사용. 성격 특성 없음.
- **L7**: GOAPDebugOverlay는 개발자용. 플레이어용 사고 과정 노출 UI 부재. RefusalBubble이 유일한 "속마음" 창구.
- **L8**: SensorSystem·MessageBus 인프라는 훌륭하나, 플래닝은 완전 개인 단위. "네가 나무를 하면 내가 요리할게"가 불가능.

## 3. 확장 설계 1 — 플래너 코어: 수치형 GOAP

> **목표**: 플랜이 "ChopWood ×3 → 창고 납부 → CookMeal ×2 → 식사"처럼 수량을 포함한 5~8스텝 체인이 되게 한다. 이것이 "완벽한 AI" 체감의 토대다.

### 3.1 상태 표현 확장

현재 43슬롯 `NativeArray<int>`를 유지하되, 슬롯의 의미를 3계층으로 재정의한다.

| 계층 | 예시 슬롯 | 값 범위 | 비고 |
|---|---|---|---|
| Bool 플래그 | AtBase, HasTool, TownHallBuilt | 0/1 | 기존 유지 |
| **수치 슬롯 (신규)** | WoodStock, CookedFoodStock, MyHunger | 0~255 | 실수를 정수 양자화 (예: 자원 5단위 = 1) |
| 파생 플래그 | WoodLow 등 | 0/1 | 수치 슬롯에서 자동 파생 — 하위 호환용으로 점진 제거 |

**Burst 호환성**: `NativeArray<int>`는 그대로다. 바뀌는 것은 비교/적용 연산뿐이므로 Job 구조 재설계가 필요 없다.

### 3.2 Precondition 연산자 확장

현재: `state[slot] == value` 만 지원.
확장: `GOAPActionDef`의 각 Precondition 쌍에 연산자 바이트 추가.

```csharp
public enum PrecOp : byte { Equal, NotEqual, GreaterEq, LessEq }

// 예: CookMeal
//   Prec: RawFoodStock >= 2, NearFireplace == 1
//   Eff : RawFoodStock -= 2, CookedFoodStock += 1, MealCooked = 1
```

switch-unroll 구조는 유지 가능 — case 내부에서 op에 따라 분기하는 인라인 함수 하나만 추가하면 된다.

### 3.3 Effect 연산자 확장

```csharp
public enum EffOp : byte { Set, Add, Sub }
```

이것 하나로 다음이 전부 열린다:

| 시나리오 | 현재 | 확장 후 |
|---|---|---|
| 목재 30 확보 계획 | ChopWood 1회로 "달성" (거짓) | `ChopWood(+5)` ×6 체인을 플래너가 스스로 도출 |
| 식량 소모 | 모델링 불가 | `EatCookedFood(CookedFoodStock -1, MyHunger -60)` |
| 건설 자원 예약 | 실행 시점 충돌 | 플랜 내에서 `WoodStock -35` 선반영 → 논리 모순 차단 |

### 3.4 휴리스틱 재설계

수치 슬롯 도입으로 진짜 휴리스틱이 가능해진다:

```
h(n) = Σ_goal슬롯 ( 부족량(slot) / 최대증가량(slot) ) × 최소액션비용
```

- `부족량` = max(0, GoalState[s] − state[s])
- `최대증가량` = 해당 슬롯을 가장 크게 올리는 액션의 Effect 값 (레지스트리 빌드 시 사전 계산 테이블)
- admissibility 보장: "이 슬롯을 채우려면 최소 몇 번의 액션이 필요한가"의 낙관적 하한이므로 과대평가하지 않는다.

**효과**: 탐색 노드 수가 수십 배 감소 → 액션을 40~60개로 늘려도 성능 예산(1.8ms/70명) 유지 가능. **L3 해결이 곧 콘텐츠 확장의 허가증이다.**

### 3.5 깊이·노드 예산 조정

수치형 전환 시 플랜이 길어지므로:
- `MAX_DEPTH`: 6 → **12** (ChopWood ×6 체인 등 수용)
- `MAX_PLAN_LEN`: 동기화
- `MAX_NODES`: 2048 유지 후 프로파일링으로 조정 (3.4의 휴리스틱이 탐색을 크게 줄이므로 증설 불필요 예상)

### 3.6 플랜 무효화 조건 정교화

긴 플랜은 도중에 세계가 변한다. 현재의 "실패 시 전체 리플래닝" 대신:

1. **부분 검증**: 다음 액션의 Precondition만 실행 직전 재검사 (현재도 유사 로직 존재 — 체계화).
2. **플랜 수선(Plan Repair)**: 실패 지점부터 남은 Goal까지만 재플래닝. 앞 스텝의 성과(이미 캔 나무)는 보존.
3. **기회주의적 중단**: 더 좋은 기회 발견 시(바로 옆에 드롭 아이템) 현재 플랜에 1스텝 삽입 — "주우면서 지나가는" 자연스러움.

## 4. 확장 설계 2 — 컨텍스트 비용

> **목표**: 같은 Goal이라도 주민의 위치·상태·계절·위험도에 따라 다른 플랜이 나온다. 플레이어가 "쟤는 왜 저 길로 가지? …아, 적을 피해서구나"를 경험하게 한다.

### 4.1 비용 = 기본비용 × 동적 배율의 합성

플래닝 스케줄 시점(메인 스레드)에 액션별 배율을 계산해 `GOAPActionDef.BaseCost`에 곱해 넣는다. **Job 내부는 무수정** — 입력 데이터만 풍부해진다.

```
FinalCost(action, agent) =
    BaseCost
  × RoleModifier        (기존)
  × DistanceModifier    (신규) — 대상 노드/건물까지 JPS 경로 길이 정규화
  × DangerModifier      (신규) — 경로가 적 인지 반경 통과 시 ×2~×5
  × SeasonModifier      (신규) — SeasonManager.GetCurrentGatherCostModifier() 연결
  × ConditionModifier   (신규) — 피로 70↑ 시 노동 액션 ×1.5, 부상 시 전투 ×3
  × PersonalityModifier (6장)  — 특성별 배율
  × SkillModifier       (9장)  — 숙련도 반비례
```

### 4.2 거리 배율의 구현 포인트

- 이미 존재하는 **JPSPathfinder / FlowFieldManager**를 재활용한다.
- 정확한 경로 비용은 비싸므로, **맨해튼 거리 + FoW 미탐험 페널티**의 근사치로 시작 → 필요 시 캐시된 플로우필드 비용 조회로 승급.
- 자원 노드가 여럿일 때: SensorSystem이 이미 최근접 노드를 알고 있으므로 그 거리를 사용.

### 4.3 플레이어 체감 시나리오

| 상황 | 현재 행동 | 확장 후 행동 |
|---|---|---|
| 가까운 숲에 적 출현 | 그대로 가서 채집하다 전투/도주 | **먼 숲으로 우회 채집** (Danger 배율이 거리 배율을 역전) — "위험을 아는구나" |
| 가을 진입 | 변화 없음 | 채집 액션 비용 급감 → 주민들이 **일제히 수확에 몰두** — "계절을 아는구나" |
| 피로 75의 주민에게 채집 Goal | 즉시 채집 | `RestOnGround → ChopWood` 체인이 더 저렴해져 **먼저 쉬고 일함** — "자기 관리를 하는구나" |

## 5. 확장 설계 3 — Utility 기반 Goal 중재기

> **목표**: "배고픔 80 초과 = 즉시 식사"의 기계적 스위치를, 연속 점수 경쟁으로 바꿔 **살아있는 우선순위**를 만든다. Goal 선택 로직을 한 곳(`GoalArbiter`)으로 통합해 L4를 해소한다.

### 5.1 구조

```
GoalArbiter (신규, 순수 계산 클래스 — ConflictScoreCalculator와 동급 위치)
  입력: VillagerBrain, AuthoritativeWorldState, SensorSystem 스냅샷
  출력: (goalId, urgencyScore) 정렬 리스트

각 Goal은 Response Curve로 점수화:
  SurviveHunger : score = curve(hunger)     — 60부터 완만히 상승, 85부터 급등
  SurviveFatigue: score = curve(fatigue)    — 동일 패턴
  DefendVillage : score = enemyProximity × weaponFactor × (mentalState==Rage ? 1.5 : 1)
  GatherWood    : score = (30 − woodStock)/30 × villageNeedWeight × seasonBonus
  BuildStructure: score = queueUrgency × hasResourcesFactor
  Explore       : score = baseCuriosity × unexploredRatio × personality(호기심)
  Socialize(신규): score = curve(mood 저하) × nearVillagerFactor
```

### 5.2 히스테리시스와 관성

- **관성 보너스**: 현재 수행 중인 Goal에 +15% — Goal이 매 틱 뒤바뀌는 "우왕좌왕" 방지.
- **최소 유지 시간**: P0 외 Goal은 최소 5초 유지.
- **P0 하드 오버라이드 유지**: 생존 위기는 여전히 즉시 인터럽트 (기존 AnyState 체크 계승). Utility는 P1 이하의 세계다.

### 5.3 체감 포인트

- 배고픔 70의 주민: 채집 점수 0.6 vs 식사 점수 0.55 → **하던 일을 마저 하고** 먹으러 간다.
- 배고픔 70 + 요리가 바로 옆: 식사 점수에 근접 보너스 → **지나가는 길에 먹는다**.
- 이 미묘함이 "스크립트가 아니라 판단"으로 읽힌다. **완벽한 AI 체감의 절반은 임계값이 아니라 곡선에서 온다.**

## 6. 확장 설계 4 — 성격·기분·관계

> **목표**: 70명이 70가지로 행동하게 한다. GOAP 구조를 전혀 바꾸지 않고 **비용 배율과 Utility 가중치만으로** 개성을 주입한다 — 이 프로젝트 아키텍처의 가장 큰 미개발 광맥.

### 6.1 성격 특성 (Traits)

주민 생성 시(RecruitmentSystem) 2~3개 무작위 부여. 각 특성은 **(액션 비용 배율 테이블 + Utility 가중치 테이블)** 데이터로만 정의 — 코드 분기 없음.

| 특성 | 액션 비용 효과 | Utility 효과 | 창발 시나리오 |
|---|---|---|---|
| 겁쟁이 | AttackEnemy ×3.0, Flee 임계 완화 | DefendVillage −40% | 전투를 회피하고 채집에 몰두 → **후방 경제 담당으로 창발** |
| 용맹함 | AttackEnemy ×0.6 | DefendVillage +50%, Fear 저항 | 적 출현 시 항상 선봉 → 플레이어의 "믿는 전사" |
| 부지런함 | RestOnGround ×2.0 | 노동 Goal +20% | 피로를 참고 일하다 탈진 → **관리 필요한 일꾼** 드라마 |
| 게으름 | 노동 액션 ×1.4 | SurviveFatigue 조기 발동 | 자주 쉼 → 플레이어가 명령으로 다잡는 재미 |
| 대식가 | — | SurviveHunger 임계 65로 하향 | 식량 소모 큰 리스크 요인 |
| 호기심 | Explore ×0.5 | Explore +60% | FoW를 스스로 걷어내는 탐험가 창발 |
| 외톨이 | — | Socialize −80%, 단독 작업 보너스 | 마을 외곽에서 혼자 일함 |

**핵심**: 특성이 거부 시스템(ConflictScore)에도 연결되면 완성된다 — 겁쟁이에게 전투 명령 시 `IMPACT_ATTACK_NO_WEAPON`에 특성 배율이 곱해져 거부 확률 급등. **"얘한테 이 명령은 안 통해"를 플레이어가 학습하는 것 자체가 게임플레이**가 된다.

### 6.2 기분(Mood) 시스템 활성화

현재 `MoodLevel=70`은 사실상 사장된 필드다. 다음과 같이 살린다:

**Mood 변동 이벤트** (MessageBus 재활용):
- 동료 사망 목격 −20 (Fear 전염 반경과 동일 로직), 식사 +5, 수면 +10, 명령 거부 후 강행당함 −10, 건물 완공 참여 +8, 승전 +15

**Mood → 행동 연결**:
- Mood < 30: 전 노동 액션 비용 ×1.5, 거부 임계값 하향 (반항적)
- Mood > 80: 이동속도 +10%, "콧노래" 말풍선 (7장 UI와 연동)
- Mood 0 지속 시: **가출 이벤트** — LOD 모드로 마을 이탈, 3일 내 Mood 회복 조건 미충족 시 영구 이탈. 콜로니 심 최고의 긴장 장치.

### 6.3 관계(Relationship) 매트릭스

- 주민 쌍별 호감도 int8 (−100~100). 70명 기준 2.4KB — 무시 가능한 메모리.
- **상승**: 같은 액션을 근접 수행(함께 벌목), 위기 구조(치료), 식사 동석.
- **하락**: 자원 노드 경합(8장 참조), 상대가 내 명령 거부를 목격.
- **행동 연결**: 호감 상대와 같은 작업지 선택 시 Utility 보너스 → **자연스럽게 "단짝 벌목조"가 창발**. 원한 관계는 전투 시 지원 지연.
- Fear/Rage 전염(기존 구현)에 관계 가중치를 곱하면: **친구의 죽음은 더 큰 공포, 원수의 죽음은 무덤덤** — 전투가 드라마가 된다.

## 7. 확장 설계 5 — 플랜 가시화

> **목표**: AI가 아무리 똑똑해도 **보이지 않으면 없는 것과 같다.** L7은 기술 문제가 아니라 연출 문제이며, 투자 대비 체감 효과가 전체 항목 중 최대다.

### 7.1 3단계 노출 레벨

| 레벨 | UI | 내용 |
|---|---|---|
| 1. 상시 | 머리 위 아이콘 | 현재 액션 아이콘 (도끼/침대/포크/칼) + P0 위기 시 느낌표. 원거리에서도 마을 상태가 한눈에 |
| 2. 클릭 | 주민 패널 확장 | **사고 체인 시각화**: `😰 배고픔 82 → 목표: 굶주림 해결 → 계획: 모닥불 이동 ▸ 요리(생식량 2 소모) ▸ 식사` — 현재 스텝 하이라이트, 완료 스텝 체크 |
| 3. 이벤트 | 말풍선 (RefusalBubble 확장) | 리플래닝 순간: *"나무가 다 떨어졌네… 돌이나 캐야겠다"* / Goal 전환: *"슬슬 배고픈데"* / 위험 회피: *"저긴 위험해 보여"* |

### 7.2 구현 자산 재활용

- **GOAPDebugOverlay**가 이미 플랜 데이터를 읽고 있다 → 렌더링만 플레이어용으로 교체.
- **RefusalBubble**이 이미 말풍선 인프라다 → 메시지 종류만 확장.
- 대사 생성은 `(GoalId, 전이 원인) → 대사 후보 3~5개` 정적 테이블 + 랜덤 선택. 특성 보유 시 전용 대사 (겁쟁이: *"난 절대 안 싸울 거야!"*).

### 7.3 왜 이것이 결정적인가

리플래닝은 현재 시스템의 **약점**(플랜-현실 괴리의 땜질)이지만, 대사 한 줄이 붙는 순간 **강점**(임기응변하는 지능)으로 반전된다. *"나무가 없네, 돌이나 캐자"*라는 말풍선 하나가, 내부적으로는 단순 재플래닝인 것을 플레이어에게는 **적응적 사고**로 보이게 만든다. 3장(수치형 GOAP)으로 플랜이 길어지면 이 사고 체인 UI의 정보량도 극적으로 풍부해진다 — **3장과 7장은 서로를 증폭하는 세트다.**

## 8. 확장 설계 6 — 협동 GOAP

> **목표**: "각자 똑똑함"에서 "함께 똑똑함"으로. 마을 전체가 하나의 유기체처럼 분업하는 장면이 콜로니 심의 최상급 체감이다.

### 8.1 블랙보드 예약 시스템 (1단계 — 저비용 고효율)

`AuthoritativeWorldState`에 예약 테이블 추가:

```
ReservationTable:
  자원 노드 → 예약 주민 수 / 최대 동시 작업 수 (예: 나무 1, 광맥 2)
  건설 부지 → 참여 주민 목록 (GDD v0.4의 다중 주민 건설과 연결)
  요리 슬롯 → CookedFood N개를 특정 주민이 "찜"
```

- 플래닝 스케줄 시, 예약 찬 노드는 해당 액션의 거리 배율 계산에서 제외 → **자연스럽게 흩어진다.**
- 플랜 확정 시 예약 등록, 플랜 취소/완료 시 해제 (기존 Dispose 경로에 후킹).
- **효과**: 주민 5명이 같은 나무에 몰려드는 현재의 어색함 즉시 해소. 식량 1개를 3명이 계획하는 L1 부수 문제도 함께 해결.

### 8.2 마을 수요 게시판 (2단계)

VillageAdvisor를 확장해 **수요 발행자**로 승격:

```
VillageAdvisor → 수요 게시판:
  "목재 40 필요 (Forge 건설)"  가중치 0.8
  "조리 식량 10 필요 (겨울 대비)" 가중치 1.2  ← SeasonManager WinterCrisis 연동
  "무기 3 필요 (침략 경보)"     가중치 1.5  ← FactionAI RaidDecision 연동
```

- 각 주민의 GoalArbiter(5장)가 게시판 항목을 Utility 후보에 포함. 자신의 역할·거리·특성에 유리한 항목을 집어간다.
- 집어간 항목은 게시판에서 수량 차감 → **중앙 명령 없이 분업이 창발**한다.
- 플레이어 UI로 게시판을 노출하면: "마을이 지금 무엇을 원하는가"가 보이고, 플레이어 명령은 게시판 가중치 조작으로 재해석 가능 — **명령 거부 시스템과도 자연 통합** (가중치를 올려도 안 하는 주민 = 개성).

### 8.3 요청-응답 프로토콜 (3단계 — 선택)

MessageBus에 `HelpRequest` 타입 추가: 전투 중 주민이 반경 내 동료에게 지원 요청 → 수신자의 GoalArbiter에 임시 Goal 후보 삽입 → 용맹한 주민은 달려오고 겁쟁이는 무시. **관계 시스템(6.3)과 결합하면 "친구는 온다"가 완성된다.**

## 9. 확장 설계 7 — 기억과 학습

> **목표**: 어제와 오늘의 주민이 다르다. 시간 투자가 애착으로 전환되는 장치.

### 9.1 숙련도 (Skill)

- 액션 카테고리별(벌목/채광/요리/건설/전투) 숙련치. 수행 시마다 +1, 로그 성장.
- 효과: 해당 액션 **비용 배율 최대 −40%** + 수행 시간 단축 + 산출량 소폭 증가.
- GoalArbiter와의 상호작용: 숙련 액션의 비용이 낮으니 **자연히 그 일을 더 자주 맡는다** → 명시적 직업 배정 없이 **전문화가 창발**하고, 기존 AgentRole은 "초기 성향"으로 의미가 재정립된다.
- 숙련 주민의 사망 = 복구 불가 손실 → 전투의 무게가 달라진다.

### 9.2 에피소드 기억 (경량)

주민별 링버퍼 16슬롯: `(이벤트 타입, 위치, 게임일, 강도)`.

| 기억 | 행동 효과 |
|---|---|
| "동쪽 숲에서 습격당함" | 해당 구역 Danger 배율 ×2를 **개인적으로** 유지 (강도는 시간 감쇠) — 마을 전체가 아니라 *그 주민만* 피한다 |
| "북쪽에서 철광 발견" | FoW 재탐험 없이 해당 노드로 직행 가능 |
| "지난 겨울 굶주림" | 가을 채집 Utility에 개인 보너스 — **트라우마가 근면을 만든다** |

### 9.3 팩션 AI의 학습 (대칭 확장)

GDD의 `AssessPlayerStrength`를 확장: 침략 실패 시 다음 침략 병력 +50% 또는 **다른 전술 선택**(정면 → 자원 약탈 게릴라). 플레이어가 "적도 배운다"를 느끼면 방어 배치가 매판 달라져야 하는 전략 게임이 된다. 주민 GOAP와 동일한 비용-배율 철학으로 구현 가능.

## 10. 게임플레이 시스템 추가 제안

AI 확장을 콘텐츠로 전환하는 시스템들.

### 10.1 무역·외교 (상인 연합 완성)

- FactionAI에 이미 `TradeProposal` 발행 코드가 존재 — **수락/거절 UI + 자원 교환 처리만 붙이면 된다.**
- 확장: 팩션별 관계도 게이지. 무역 누적 → 동맹 (침략 시 지원군) / 결렬 → 침략 트리거 가중. GDD의 미구현 Win2(팩션 동맹 승리)와 직결.

### 10.2 동적 이벤트 시스템

MessageBus + SeasonManager 인프라 재활용. 각 이벤트는 **월드 스테이트 슬롯 변화**로 정의되므로 GOAP가 자동 대응한다 — 이벤트 대응 스크립트를 짤 필요가 없다는 것이 이 아키텍처의 보상이다.

| 이벤트 | 트리거 | GOAP 자동 반응 |
|---|---|---|
| 방랑자 도착 | 랜덤 (식량 여유 시 확률↑) | 모집 시스템 연결, 특성 랜덤 — "누굴 받을까" 선택지 |
| 들불 | 여름 + 건조 | 진화 액션 추가 시 주민들이 자발 진화, 겁쟁이는 도망 |
| 질병 | 겨울 + Mood 저하 | SeekMedicalAid 수요 급증 → Medic 가치 급등 |
| 풍년 | 가을 확률 | 채집 산출 ×2 — 게시판 수요 조기 충족 → 탐험/건설로 전환하는 마을 |
| 늑대 무리 | 야간 | 소규모 전투 — 망루(Watchtower) 가치 재조명 |

### 10.3 마일스톤 서사

30일 생존이 단조로워지는 것을 막는 중간 목표: Day 5 첫 침략 예고 → Day 10 팩션 활성화(기존) → Day 15 대침략 → Day 20 Silver Citadel 해금 → Day 30 승리. 각 마일스톤 전 **VillageAdvisor가 게시판으로 준비 수요를 발행**하면, 마을 전체가 "다가올 위기를 준비하는" 그림이 자동으로 그려진다.

### 10.4 플레이어 역할 재정의

명령 거부 시스템이 있는 게임에서 플레이어는 "명령자"가 아니라 **"설득자·환경 설계자"**여야 한다:
- 직접 명령(기존) — 거부 리스크 있음
- 게시판 가중치 조정(8.2) — 간접 유도
- 보상 선포: "이번 주 벌목 기여 1위에게 고기 배급" → 해당 Utility 임시 부스트
- 이 3단 구조가 "AI를 조종하는 게임"이 아닌 **"AI와 협상하는 게임"**이라는 고유 장르 감각을 만든다.

## 12. 성능 예산 검토

현행 예산: **70명 동시 플래닝 ≤ 1.8ms (Burst)**. 확장별 영향:

| 확장 | 예산 영향 | 완화책 |
|---|---|---|
| 수치형 Prec/Eff | 비교 연산 소폭 증가 (+, 분기 1개) | switch-unroll 유지, op를 상수 폴딩 가능한 구조로 |
| 깊이 12 확장 | 탐색 공간 이론상 급증 | **3.4 신 휴리스틱이 상쇄** — 도입 순서상 휴리스틱이 반드시 선행 |
| 컨텍스트 비용 | 스케줄 시 배율 계산 (메인 스레드) | 배율 테이블 0.5초 캐시, 거리 근사치 사용 |
| Utility 중재기 | 틱당 Goal 후보 ~10개 점수화 | 순수 산술, 틱 그룹 분산에 이미 편승 |
| 예약/게시판 | 딕셔너리 조회 수 회 | 프레임당 접근 수백 회 수준 — 무시 가능 |
| 관계/기억 | 70² int8 + 링버퍼 16 | < 10KB, 갱신은 이벤트 주도 |

**결론**: 가장 비싼 확장(수치형 + 깊이 12)조차 신 휴리스틱과 세트로 도입하면 현행 예산 내 수렴이 현실적이다. LOD 시스템이 이미 있으므로, 원거리 주민의 플래닝 빈도 하향으로 추가 여유 확보도 가능하다.

## 맺음: "완벽한 AI"의 공식

이 문서의 확장안을 한 문장으로 압축하면:

> **긴 플랜(3장) × 상황 감응(4·5장) × 개성(6·9장) × 협동(8장), 그리고 그 전부를 보여주는 창(7장).**

기술적으로 가장 어려운 것은 수치형 GOAP지만, 플레이어 체감상 가장 결정적인 것은 **가시화**다. 지금의 엔진도 이미 훌륭하다 — 부족한 것은 지능이 아니라, 지능이 *수량을 세고*, *지도를 보고*, *성격을 갖고*, *서로 조율하고*, 그 과정을 *플레이어에게 말하는* 능력이다. Phase 1만 완료해도 "이 주민들, 생각이란 걸 하네?"라는 첫 반응을 얻을 수 있고, Phase 2가 끝나는 순간 이 게임은 참고작(RimWorld)과 구별되는 자기만의 답을 갖게 된다.
