## 0. 핵심 전략 요약

**모델 격차는 지능이 아니라 "빈칸 채우기"에서 벌어진다.**

| 시점 | 문서 형식 | 1차 반영률 |
|---|---|---|
| Phase 1 최초 | 설계 서술 위주 | ~78% |
| F1~F7 보완가이드 이후 | 파일 경로 + 코드 스케치 + DoD + ⚠️ 오해 위험 | ~95% |

전략: **이 프로젝트에서 실제로 발생한 판단 실수를 파일로 외재화한다.**
설계 단계(구조적 통찰이 필요한 영역)는 상위 모델로, **구현·리뷰·검증 단계는 어떤 모델이든 절차화로 커버한다.**

## 2. CLAUDE.md 최종안

> 아래 내용을 리포 루트 `CLAUDE.md`에 그대로 배치한다.

```markdown
# AI_GOAP — Claude 작업 규칙

Unity 탑다운 마을 생존 시뮬레이션. GOAP(Burst Job A*) 기반 주민 AI 70명이 핵심.
게임 정체성: "자기 생각이 있는 AI와 협상하는 게임" — 주민은 명령을 거부할 수 있다.

## 핵심 파일 지도
- 플래너: `Assets/Scripts/Core/GOAP/` (PlannerJob=탐색, Registry=액션데이터, PlanningSlots=상태/Goal, Scheduler=배선)
- 에이전트: `Assets/Scripts/AI/VillagerFSM.cs`(실행), `VillagerBrain.cs`(상태), `GoalArbiter.cs`(Goal 선택, N4+)
- 런타임 수치: `Core/ActionDatabase.cs`, `UI/BuildingCosts.cs`
- 명세 문서: `Docs/` — 작업 전 해당 Phase 명세서를 반드시 읽는다

## 불변 규칙 — ADR (위반 금지, 변경하려면 사유를 커밋 메시지에)

1. **수치의 단일 출처**: 기획서 수치의 원본은 런타임(ActionDatabase/BuildingCosts/FSM 상수)이다.
   플래너(GOAPActionRegistry 상수)가 런타임을 따라간다. **절대 그 반대가 아니다.**
   새 수치가 필요하면 발명하지 말고 기존 코드에서 찾아라. 없으면 멈추고 질문하라.

2. **GoalOp 3종 세트**: Goal 판정에는 GoalOp(연산자)가 있다.
   수치 Goal 추가 시 goalState/goalMask/goalOps 3종을 항상 함께 추가한다.

3. **NoSolutionFound는 버그 증상**: MAX_NODES 인상으로 해결 금지.
   원인 진단 순서: ① `grep -rn "NodesExpanded" Assets/Scripts`로 계측 로그 위치 확인
   → ② Profiler에서 Planner Job 시간 대조 → ③ 중복 상태/휴리스틱/무한 Goal 여부 판단.

4. **Sub Effect 0 클램프 필수**: 수치 슬롯은 원시 단위 int (양자화 금지).

5. **불리언 파생 플래그 유지**: WoodLow 등 Phase 3 전까지 제거 금지 (병행 마이그레이션 중).

6. **UseNumericGoals 토글 유지**: 안정화 전까지 유지 — 문제 시 즉시 false로 롤백 가능해야 한다.

7. **Goal 목표치와 FSM 발동 임계값 세트 수정**: 신규 Goal의 목표치 < FSM 발동 임계값이면
   alreadySatisfied(-1) 무한 루프 발생. 둘은 항상 함께 수정한다.

8. **액션 추가 3종 세트**: ActionDef + names[] 배열(해시 역매핑) + Debug.Assert 개수.
   하나라도 빠지면 미완성 커밋이다.

## 작업 프로토콜
- 명세서의 작업 항목(W/F/P/N 번호) 1개 = 커밋 1개. 합쳐 커밋 금지.
- 각 항목의 DoD 체크리스트(`- [ ]` 형식) 전 항목을 `- [x]`로 표시하기 전 "완료"라고 말하지 않는다.
- 명세의 ⚠️(오해 위험) 절은 코드보다 먼저 읽는다.
- 명세에 없는 판단이 필요해지면: 구현하지 말고, 선택지와 추천을 정리해 질문하거나 GitHub 이슈로 남긴다.
- 커밋 전 체크: ① 컴파일 ② Unity Test Runner EditMode 전체 green ③ 하드코딩 grep 0건 ④ Editor 종료 시 NativeArray leak 경고 0건

## 검증 명령 (커밋 전 실행)
```
# 하드코딩 수치 소탕
grep -rn "GainResource,\s*[0-9]\|ReduceHunger,\s*[0-9]\|ReduceFatigue,\s*[0-9]\|GainHealth,\s*[0-9]" Assets/Scripts
```
→ 결과 0건이어야 커밋 가능

게임 건강 기준: "10분 무개입 방치 테스트" — 자원 수렴→건설→탐험 사이클 유지,
Console에 NoSolutionFound/Deadlock 0건.

## 금지 목록
- 스코프 밖 기능 추가 금지 (좋은 아이디어는 코드가 아니라 로드맵 문서 하단에 메모)
- 명세 없는 밸런스 수치 변경 금지
- 해시 비교만으로 상태 동일 판정 금지 (Closed Set은 반드시 전수 비교 동반)
- Job 구조 변경 금지 — 동적 요소는 스케줄 시점(메인 스레드)에서 주입

## 같은 오해 2회 반복 시 처리
리뷰나 수정에서 동일 오해가 2회 발생하면 → ADR 신규 항목 추가를 사용자에게 능동적으로 제안한다.
```

### 3-1. `.claude/skills/spec-implement/SKILL.md`

```markdown
---
name: spec-implement
description: Docs/의 실행명세서(W/F/P/N 항목)를 구현할 때 사용. "명세대로 구현해줘",
  "WN 구현", "보완가이드 반영" 류의 요청에서 반드시 이 절차를 따른다.
---

# 실행명세서 구현 절차

## 1단계 — 코드를 열기 전에
1. 명세서의 ADR/아키텍처 결정 절을 전부 읽는다. 구현 중 판단이 갈리면 여기 답이 있다.
2. 담당 항목(예: W5)의 ⚠️ 오해 위험 절을 읽는다. 여기 적힌 실수를 하지 않는 것이 최우선이다.
3. 항목의 "대상 파일"을 열어 코드 스케치와 실제 코드의 차이(이름, 시그니처)를 확인한다.
   스케치의 프로퍼티명이 실제와 다르면 실제 코드를 따르고, 그 사실을 커밋 메시지에 남긴다.

## 2단계 — 구현 중
- 스케치는 뼈대다. 그대로 복붙하지 말고 프로젝트의 기존 스타일(한글 주석, 상수 명명, region)에 맞춘다.
- 수치가 필요한데 명세가 "실제 값을 찾아 쓸 것"이라 하면: grep으로 런타임 원본을 찾는다.
  못 찾으면 임의 값을 넣지 말고 TODO 주석 + 질문으로 남긴다.
- 명세에 없는 개선이 떠오르면: 구현하지 않는다. 커밋 메시지나 이슈에 제안으로만 남긴다.

## 3단계 — 완료 판정
- 항목의 DoD 체크리스트(`- [ ]` 형식)를 하나씩 직접 수행한다.
  수행 완료 항목은 `- [x]`로 표시한다. **읽고 넘기는 것은 수행이 아니다.**
- CLAUDE.md의 커밋 전 체크 4종을 실행한다.
- 전부 `- [x]` → 커밋 (형식: `feat(goap): <항목번호> <요약>`, 이슈 연동 시 `Fixes #N`).
- 하나라도 미완 → 커밋하지 않고 미완 항목을 명시해 보고한다. "거의 됐다"는 없다.

## 보고 형식
[항목번호] 상태(완료/부분/차단) / DoD 체크 결과 / 명세와 달리한 것과 사유 / 발견한 문제
```

### 3-2. `.claude/skills/spec-review/SKILL.md`

> ⚠️ 이름을 `code-review`로 하면 Claude Code 내장 `/code-review` 슬래시 커맨드와 충돌한다.
> 반드시 `spec-review`(또는 `goap-review`)로 저장한다.

```markdown
---
name: spec-review
description: 커밋을 명세서와 대조 리뷰할 때 사용. "리뷰해줘", "잘 반영됐는지 확인",
  "코드 검토" 요청 시 이 절차로 판정표와 수정 가이드를 만든다.
  (주의: Claude Code 내장 /code-review와 충돌하지 않도록 spec-review로 명명)
---

# 명세 대조 리뷰 절차

## 1단계 — 대조 기준 수립
1. 이 커밋이 구현했다고 주장하는 명세 항목(커밋 메시지의 W/F/P/N 번호)을 특정한다.
2. 해당 명세의 요구사항을 표로 뽑는다: 요구 | 대상 파일 | DoD.

## 2단계 — 기계적 대조 (모든 항목, 예외 없이)
- `git diff <이전>..<현재> -- <대상파일>` 로 항목별 실제 변경을 확인한다.
- 명세의 ⚠️ 절 항목마다 "회피했는가?"를 개별 판정한다.
- **상수/수치가 등장하면 반드시 원본과 대조**: Registry ↔ ActionDatabase/BuildingCosts/FSM.
  값이 다르면 어느 쪽이 기획서 수치("기획서 수치" 주석)인지 확인하고 방향을 명시 (ADR-1).
- 액션 추가 커밋이면 3종 세트(Def + names[] + Assert) 전부 확인 (ADR-8).
- 신규 NativeArray가 있으면 Dispose 경로(정상/실패/예외 3곳)를 전부 추적한다.

## 3단계 — 판정과 보고
- 항목별 판정표: ✅(DoD 전부) / ⚠️(부분, 남은 것 명시) / ❌(미구현 or 오구현).
- 수정 필요 항목은 번호(P1, P2...)를 붙여: 문제 → 원인 → 수정 코드 스케치 → 검증 기준.
- 심각도 기준: 🔴 게임 진행 차단(무한 루프, Deadlock, 크래시) > 🟠 정합성/성능 > 🟡 품질.
- **잘한 것도 명시한다** — 명세에 없던 좋은 추가는 다음 명세에 반영할 정보다.
- 마지막에 반드시: "게임이 잘 진행되는가"를 판정한다 (10분 방치 테스트 통과 여부 또는 예측).

## 반복 지적 처리 규칙
동일 오해/실수가 2회 이상 지적되면 → "ADR 신규 항목 추가 제안"을 리뷰 보고 마지막에 포함한다.
```

### 3-3. `.claude/skills/spec-write/SKILL.md`

```markdown
---
name: spec-write
description: 새 Phase/기능의 실행명세서나 보완가이드를 작성할 때 사용.
  "명세서 만들어줘", "가이드 작성", "개발 방향" 요청 시 이 형식을 강제한다.
---

# 실행명세서 작성 규칙 (1차 구현 100%를 위한 형식)

모든 작업 항목은 아래 5요소를 빠짐없이 갖춘다. 하나라도 빠지면 미완성 명세다:

1. **대상 파일 경로** — "어디"가 없는 지시는 지시가 아니다.
2. **코드 스케치** — 시그니처와 핵심 로직. 프로젝트 스타일(한글 주석) 준수.
3. **DoD 체크리스트** — 반드시 `- [ ]` 형식으로 작성. 테스트 가능한 문장만.
   "잘 동작" 금지. "X 상태에서 Y 플랜 산출", "Console에 Z 로그 출력" 형식 사용.
4. **⚠️ 오해 위험** — 이 지시를 잘못 해석하는 가장 그럴듯한 방식을 미리 적고 차단한다.
5. **작업량/심각도/의존 관계** — 커밋 순서를 결정할 수 있게.

문서 전체 요구사항:
- 서두에 측정 가능한 성공 기준 (숫자로).
- ADR 절 — 구현 중 갈릴 판단을 미리 결정. "바꾸려면 사유를 커밋에" 명시.
- 커밋 분할 계획 — 1항목 1커밋, 각 커밋 단독 실행 가능.
- 스코프 가드 절 — "이번에 하지 않는 것" 목록.
- 큰 데이터 마이그레이션이 있으면 중간 리뷰 시점을 명시.
- 수치는 발명하지 않는다: 기존 값의 위치를 지목하거나, 제안치임을 명시하고 "기존 값 우선" 원칙을 병기.
```

## 6. 기대 효과와 한계 (정직한 버전)

**절차화되는 것** (Haiku도 체크리스트를 따라 Fable급 결과에 근접 가능):

- 방향 실수 재발 방지 (ADR-1~8, 전부 실제 사고 기반)

**절차화 안 되는 것** (상위 모델 필요):
