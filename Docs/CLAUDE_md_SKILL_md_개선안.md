## 0. 원리 — 모델 격차는 어디서 벌어지는가

이 프로젝트의 실측 데이터가 답을 준다:

| 시점 | 문서 형식 | 1차 반영률 |
|---|---|---|
| Phase 1 최초 | 설계 서술 위주 ("월드스페이스 말풍선을 만들어라") | **~78%** |
| F1~F7 보완가이드 이후 | 파일 경로 + 코드 스케치 + DoD + ⚠️오해 위험 | **~95%** |

**격차는 지능이 아니라 "빈칸 채우기"에서 벌어진다.** 명세가 비운 자리를 모델이 그럴듯하게 메꾸는 순간 사고가 난다 — 실제 사례 3건: ①"말풍선" → 전역 토스트로 해석, ②연산자 확장에서 GoalOp 누락(명세에 없었음), ③상수 정합화의 방향 역전(런타임→플래너인데 플래너→런타임으로). 상위 모델은 빈칸을 더 잘 메꾸지만, **빈칸 자체를 없애면 모델 차이가 절차화 가능한 영역에서는 거의 사라진다.**

따라서 개선안의 전략은 하나다: **이 대화에서 Fable이 해온 판단(검증 순서, 방향 결정, 함정 예고)을 파일로 외재화한다.** 단, 정직하게 말하면 새로운 설계 판단(예: "Closed Set이 깊이 12의 선행 조건임을 간파")까지 절차화할 수는 없다 — 그 영역은 여전히 모델 역량에 의존하므로, 설계 단계는 상위 모델로 하고 **구현·리뷰·검증 단계를 절차화해 모델 무관하게 만드는 것**이 현실적 목표다.

### 배치 전략 (Claude Code 로딩 방식 기준)

| 파일 | 로딩 | 넣을 것 | 크기 원칙 |
|---|---|---|---|
| `CLAUDE.md` (리포 루트) | **매 세션** | 불변 규칙(ADR), 수치 출처, 금지 목록, 검증 명령 | **150줄 이내** — 항상 컨텍스트에 있으므로 짧을수록 준수율이 높다 (특히 Haiku) |
| `.claude/rules/*.md` | 경로 매칭 시 | 플래너 전용 규칙 (GOAP 폴더 작업 시에만) | 모듈당 50줄 |
| `.claude/skills/<이름>/SKILL.md` | **호출/관련 시에만** | 절차: 명세 구현, 코드 리뷰, 명세 작성 | 길어도 됨 — 필요할 때만 로드 |

## 1. CLAUDE.md 초안 (리포 루트에 복붙)

```markdown
# AI_GOAP — Claude 작업 규칙

Unity 탑다운 마을 생존 시뮬레이션. GOAP(Burst Job A*) 기반 주민 AI 70명이 핵심.
게임 정체성: "자기 생각이 있는 AI와 협상하는 게임" — 주민은 명령을 거부할 수 있다.

## 핵심 파일 지도
- 플래너: `Assets/Scripts/Core/GOAP/` (PlannerJob=탐색, Registry=액션데이터, PlanningSlots=상태/Goal, Scheduler=배선)
- 에이전트: `Assets/Scripts/AI/VillagerFSM.cs`(실행), `VillagerBrain.cs`(상태), `GoalArbiter.cs`(Goal 선택, N4+)
- 런타임 수치: `Core/ActionDatabase.cs`, `UI/BuildingCosts.cs`
- 명세 문서: `Docs/` — 작업 전 해당 Phase 명세서를 반드시 읽는다

## 불변 규칙 (ADR — 위반 금지, 변경하려면 사유를 커밋 메시지에)
1. **수치의 단일 출처**: 기획서 수치의 원본은 런타임(ActionDatabase/BuildingCosts/FSM 상수)이다.
   플래너(GOAPActionRegistry 상수)가 런타임을 따라간다. **절대 그 반대가 아니다.**
   새 수치가 필요하면 발명하지 말고 기존 코드에서 찾아라. 없으면 멈추고 질문하라.
2. Goal 판정에는 GoalOp(연산자)가 있다. 수치 Goal 추가 시 goalState/goalMask/goalOps 3종 세트를 항상 함께.
3. 플래닝 실패(NoSolutionFound)를 MAX_NODES 인상으로 해결하지 마라. 그것은 버그의 증상이다.
   NodesExpanded 계측 로그로 원인(중복 상태? 휴리스틱? 무해 Goal?)을 먼저 찾는다.
4. Sub Effect는 0 클램프 필수. 수치 슬롯은 원시 단위 int (양자화 금지).
5. 불리언 파생 플래그(WoodLow 등)는 Phase 3 전까지 제거 금지 (병행 마이그레이션 중).
6. `UseNumericGoals` 토글은 안정화 전까지 유지 — 문제 시 즉시 false로 롤백 가능해야 한다.
7. 새 Goal의 목표치 < FSM 발동 임계값이면 alreadySatisfied(-1) 무한 루프가 난다. 둘은 항상 세트로 수정.
8. 액션 추가 시 3종 세트: ActionDef + names[] 배열(해시 역매핑) + Debug.Assert 개수. 하나라도 빠지면 미완.

## 작업 프로토콜
- 명세서의 작업 항목(W/F/P/N 번호) 1개 = 커밋 1개. 합쳐 커밋 금지.
- 각 항목의 DoD 체크리스트 전 항목 통과 전에는 "완료"라고 말하지 않는다. 부분 완료는 완료가 아니다.
- 명세의 ⚠️(오해 위험) 절은 코드보다 먼저 읽는다.
- 명세에 없는 판단이 필요해지면: 구현하지 말고, 선택지와 추천을 정리해 질문하거나 GitHub 이슈로 남긴다.
- 커밋 전 체크: ① 컴파일 ② Unity Test Runner EditMode 전체 green ③ 아래 소탕 grep 0건 ④ Editor 종료 시 NativeArray leak 경고 0건

## 검증 명령 (커밋 전 실행)
- 하드코딩 수치 소탕: `grep -rn "GainResource,\s*[0-9]\|ReduceHunger,\s*[0-9]\|ReduceFatigue,\s*[0-9]\|GainHealth,\s*[0-9]" Assets/Scripts` → 0건
- 상태 판정: 게임의 건강 기준은 "10분 무개입 방치 테스트" — 자원 수렴→건설→탐험 사이클이 끊기지 않고, Console에 NoSolutionFound/Deadlock 0건

## 금지 목록
- 스코프 밖 기능 추가 금지 (좋은 아이디어는 코드가 아니라 로드맵 문서 하단에 메모)
- 명세 없는 밸런스 수치 변경 금지
- 해시 비교만으로 상태 동일 판정 금지 (Closed Set은 반드시 전수 비교 동반)
- Job 구조 변경 금지 — 컨텍스트 비용 등 동적 요소는 스케줄 시점(메인 스레드)에서 주입
```

**왜 이 구성인가**: 8개 ADR은 전부 **실제로 사고가 났거나 날 뻔했던 지점**이다 (1번=이슈#1 방향 역전, 7번=P1 무한 루프, 8번=이슈#2의 names[] 누락...). 가상의 모범 규칙이 아니라 이 프로젝트의 흉터 지도라서, 어떤 모델이든 같은 구덩이에 다시 빠지지 않는다.

# 실행명세서 구현 절차

## 1단계 — 코드를 열기 전에
1. 명세서의 ADR/아키텍처 결정 절을 전부 읽는다. 구현 중 판단이 갈리면 여기 답이 있다.
2. 담당 항목(예: W5)의 ⚠️ 오해 위험 절을 읽는다. 여기 적힌 실수를 하지 않는 것이 최우선이다.
3. 항목의 "대상 파일"을 열어 코드 스케치와 실제 코드의 차이(이름, 시그니처)를 확인한다.
   스케치의 프로퍼티명이 실제와 다르면 실제 코드를 따르고, 그 사실을 커밋 메시지에 남긴다.

## 2단계 — 구현 중
- 스케치는 뼈대다. 그대로 복붙하지 말고 프로젝트의 기존 스타일(한글 주석, 상수 명명, region)에 맞춘다.
- 수치가 필요한데 명세가 "실제 값을 찾아 쓸 것"이라 하면: grep으로 런타임 원본을 찾는다.
  못 찾으면 임의 값을 넣지 말고 TODO 주석 + 질문으로 남긴다.
- 명세에 없는 개선이 떠오르면: 구현하지 않는다. 커밋 메시지나 이슈에 제안으로만 남긴다.

## 3단계 — 완료 판정
- 항목의 DoD 체크리스트를 하나씩 실제로 수행한다 (읽고 넘기지 말 것).
- CLAUDE.md의 커밋 전 체크 4종을 실행한다.
- 전부 통과 → 커밋 (형식: `feat(goap): <항목번호> <요약>`, 이슈 연동 시 `Fixes #N`).
- 하나라도 실패 → 커밋하지 않고 실패 항목을 보고한다. "거의 됐다"는 보고 형식이 아니다.

## 보고 형식
항목별로: [항목번호] 상태(완료/부분/차단) / DoD 체크 결과 / 명세와 달리한 것과 사유 / 발견한 문제
```

# 명세 대조 리뷰 절차

## 1단계 — 대조 기준 수립
1. 이 커밋이 구현했다고 주장하는 명세 항목(커밋 메시지의 W/F/P/N 번호)을 특정한다.
2. 해당 명세의 요구사항을 표로 뽑는다: 요구 | 대상 파일 | DoD.

## 2단계 — 기계적 대조 (모든 항목, 예외 없이)
- `git diff <이전>..<현재> -- <대상파일>` 로 항목별 실제 변경을 확인한다.
- 명세의 ⚠️ 절 항목마다 "회피했는가?"를 개별 판정한다.
- **상수/수치가 등장하면 반드시 원본과 대조한다**: Registry ↔ ActionDatabase/BuildingCosts/FSM.
  값이 다르면 어느 쪽이 기획서 수치("기획서 수치" 주석)인지 확인하고 방향을 명시한다 (ADR-1).
- 액션 추가 커밋이면 3종 세트(Def + names[] + Assert) 전부 확인한다 (ADR-8).
- 신규 NativeArray가 있으면 Dispose 경로(정상/실패/예외 3곳)를 전부 추적한다.

## 3단계 — 판정과 보고
- 항목별 판정표: ✅(DoD 전부)/⚠️(부분, 남은 것 명시)/❌(미구현 or 오구현).
- 수정 필요 항목은 번호(P1, P2...)를 붙여: 문제 → 원인 → 수정 코드 스케치 → 검증 기준.
- 심각도 기준: 🔴 게임 진행 차단(무한 루프, Deadlock, 크래시) > 🟠 정합성/성능 > 🟡 품질.
- **잘한 것도 명시한다** — 명세에 없던 좋은 추가는 다음 명세에 반영할 정보다.
- 마지막에 반드시: "게임이 잘 진행되는가"를 판정한다 (10분 방치 테스트 통과 여부 또는 그 예측).
```

# 실행명세서 작성 규칙 (1차 구현 100%를 위한 형식)

모든 작업 항목은 아래 5요소를 빠짐없이 갖춘다. 하나라도 빠지면 그 항목은 미완성 명세다:
1. **대상 파일 경로** — "어디"가 없는 지시는 지시가 아니다.
2. **코드 스케치** — 시그니처와 핵심 로직. 프로젝트 스타일(한글 주석) 준수.
3. **DoD 체크리스트** — 테스트 가능한 문장으로. "잘 동작" 금지, "X 상태에서 Y 플랜 산출" 형식.
4. **⚠️ 오해 위험** — 이 지시를 잘못 해석하는 가장 그럴듯한 방식을 미리 적고 차단한다.
5. **작업량/심각도/의존 관계** — 순서를 정할 수 있게.

문서 전체 요구사항:
- 서두에 측정 가능한 성공 기준 (숫자로).
- 아키텍처 결정(ADR) 절 — 구현 중 갈릴 판단을 미리 결정. "바꾸려면 사유를 커밋에" 명시.
- 커밋 분할 계획 — 1항목 1커밋, 각 커밋 단독 실행 가능.
- 스코프 가드 절 — "이번에 하지 않는 것" 목록.
- 큰 데이터 마이그레이션이 있으면 중간 리뷰 시점을 명시한다.
- 수치는 발명하지 않는다: 기존 값의 위치를 지목하거나, 제안치임을 명시하고 "기존 값 우선" 원칙을 병기.

## 3. 운영 규칙 — 파일이 낡지 않게

1. **흉터가 생기면 즉시 반영**: 새 버그의 근본 원인이 "규칙 부재"였다면, 수정 커밋에 CLAUDE.md ADR 추가를 포함한다 (이번 대화의 ADR 8개가 전부 이렇게 태어났다).
2. **리뷰에서 반복 지적 2회 = 규칙 승격**: 같은 지적이 두 번 나오면 사람이 아니라 파일이 문제다.
3. **CLAUDE.md 150줄 상한 사수**: 넘치면 상세를 `.claude/rules/goap.md`(경로 스코프)나 스킬로 이관. 항상 로드되는 파일이 길어지면 준수율이 떨어진다 — 특히 경량 모델에서.
4. **분기별 유효성 점검**: 규칙의 파일 경로·명령이 실제로 실행되는지 확인 (죽은 규칙은 전체 신뢰도를 갉아먹는다).

## 4. 기대 효과와 한계 (정직한 버전)
