# M13 실행명세서 — "사건과 흔적"

*작성 2026-07-27. 근거: `devlog/sessions/2026-07-27.md` `[00:31]`(분석)·`[02:11]`(확정).*

> **정의: 일어난 일이 세계에 남는다.**
> 舊 명칭 "표현층"에서 개정 — 인과 사슬에서 표현이 고칠 수 있는 것은 알림 1건뿐이었고
> 나머지는 **기록과 결과**의 문제였다.

## §0. 이 밀스톤이 존재하는 이유 (한 문단)

M12 회상 테스트에서 사용자는 *"게으름뱅이 둘 다 그냥 죽었어, 별 이야기가 없었다"* 고 답했다.
코드 실사 결과 원인은 재료 부족이 아니라 **기록의 부재**였다: 죽으면 `Destroy(gameObject)` +
`ReleaseBy`로 관계까지 지워지고(A1), 개인의 생애는 로그에도 없으며(A2 — `BehaviorProfiler`는
성격 **집단** 통계다), 무덤은 있는데 이름이 없다(A3). **통계는 이야기가 아니다.**
동시에 목적이 재정의됐다 — M13은 *"예쁘게"* 가 아니라 **"누가 위험한지·언제까지 손쓸 수 있는지가
화면에 있는가"** 다. 치사율은 유지하고(낮추면 다시 관찰자 게임), 대신 개입할 창을 화면에 만든다.

## §1. 측정 가능한 성공 기준

숫자가 없는 기준은 기준이 아니다. **판정은 Play 관측 1회(방치 Day 40 이상)** 로 한다.

| 기준 | 항목 | 판정 방법 | 통과선 |
|---|---|---|---|
| **S1** | A | 방치 후 화면의 무덤 오브젝트에 이름표가 붙어 있다 | 무덤 이름표 수 == `DeathCount`, 각 이름표가 `"{이름} · Day {N}"` 형식 |
| **S2** | B | 상태 알림 줄이 조건 발생 시 나타나고 **해소될 때까지 유지**된다 | 3종(식량·부상·위협) 전부 등장→해소 관측. 조건 0건이면 줄이 빈다 |
| **S3** | B | **개입이 실제로 일어난다** (가장 불확실한 가정의 조기 검증) | 관측 1판에서 플레이어 명령 사용 ≥ 1회. **0회면 §9로 가서 나머지 설계를 다시 본다** |
| **S4** | C1 | 종료 회고가 통계 대신 명부를 보여준다 | 회고 화면 줄 수 == 그 판에 존재했던 주민 수(생존자 포함). 각 줄에 이름·성격·직업·기간·퇴장사유 |
| **S5** | C2 | 정보줄에 그 주민의 최근 사건이 보인다 | 선택 시 최근 사건 최대 3줄. 사건 0건인 주민은 줄 없음(중립) |
| **S6** | C2 | 사건이 **죽은 뒤에도** 남는다 | 사망 주민의 사건 기록이 회고 화면에 개인 연대기로 출력됨 |
| **S7** | D | 선택 주민의 "왜 지금 저걸 하는가"가 화면에 있다 | 계획 사슬 + 다음 문턱까지 남은 여유가 정보줄에 표기 |
| **S8** | C3 | 관계가 죽음을 넘긴다 | 회고에 `"{이름}의 단짝이었다"` 1건 이상 (스코프 가드 — C2 완료 후 판단) |
| **S9** | 전체 | **회상 테스트** — 관측 후 사용자가 이야기를 말할 수 있는가 | 사용자 서술이 "그냥 죽었다"가 아닌 개인 서사를 포함 |
| **S10** | 회귀 | 기존 동작 불변 | `NoSolutionFound` 0건, EditMode 게이트 전체 green, 기존 알림 14곳 동작 불변 |

⚠️ **S3이 이 명세에서 가장 중요한 기준이다.** B까지 하고 개입이 0이면 C~D를 만들어도
"관찰자 게임"은 그대로다. 그래서 B가 C보다 앞에 있다.

### ② 새 선반 (신설 — M13에서 새로 짓는 것은 **이것 하나뿐**)

**`ChronicleService`** — 주민별 명부·사건 로그.

- **왜 신설인가**: `BehaviorProfiler`는 성격 **집단** 통계이고 명시적으로 *"읽기 전용 · 세이브
  대상 아님 · 계측이 게임을 바꾸면 관측이 아니다"* 로 선언돼 있다. 연대기는 **개인 단위**이고
  **세이브 대상**이라 등급이 다르다. 프로파일러에 얹으면 그 불변식이 깨진다.
- **왜 `VillagerAgent`가 아닌가**: 🔴 `Destroy(gameObject)`와 함께 사라져 **목적 자체가 무너진다.**
  기록의 존재 이유가 "죽은 뒤에도 남는 것"인데 죽으면 지워지는 곳에 둘 수 없다.
- **결합 규칙**: 후반 확장 인지 규칙 ①에 따라 **`string` ID로만 결합**한다.
  `VillagerAgent` 참조를 필드로 들지 않는다 (몬스터·타 종족이 같은 서비스를 쓸 수 있어야 한다).

### ③ 통로가 있는데 출력만 콘솔인 것 (= 가장 싼 항목)

🔑 **M13 범위 확정의 근거였던 발견**: 격차 대부분이 기능 부재가 아니라 **출력 대상이 콘솔**이다.

- `RelationshipService.AddAffinity(from, to, delta, **reason**)` — **이유 문자열이 이미 인자에
  있는데** `Debug.Log`로만 나간다(`:34`). = RimWorld의 thought 항목이 이미 만들어져 버려지고 있다.
- `GoalSO.TraitBoost(traits)`는 정수를 반환하는데(`GoalSO.cs:40`) 화면에 없다.
- 죽음·부상·완공은 이미 로그 지점을 갖고 있다.

> 이 절이 이번 실사의 **핵심 산출물**이다. 사용자 제기: *"최소부터 하나씩 완벽하게 확인하며"*

### 5.1 C1 스키마 (구현 대상)

### 5.3 스키마 결정 4건과 사유

| 결정 | 이유 | 반대안이 실패하는 지점 |
|---|---|---|
| **성격·직업을 `string`으로 저장** | `BehaviorProfiler`의 선례(*"goal 선택은 이름 키로 센다 — 에셋 참조 수명과 무관하게"*) | SO 참조를 들면 세이브에 GUID 문제가 생기고, 회고가 에셋 로드 순서에 의존하게 된다 |
| **`LeftDay = -1` 센티넬** (생존 중) | 0은 **Day 0에 죽은 주민**과 구별되지 않는다 | `LeftDay == 0`을 "생존 중"으로 읽으면 시작 직후 아사한 주민이 회고에서 살아 있다 |
| **`Events`를 C1에서 생성** | C2가 C1 클래스를 **수정하지 않게** 만드는 장치 | C2에서 필드를 추가하면 "하나씩 완벽하게"가 깨진다 (사용자 우려의 실체) |
| **저장은 `Dictionary<string, VillagerRecord>`, 출력은 `BornDay` 정렬** | 사전 순회 순서는 비결정적 — 이 프로젝트는 결정성을 규약으로 둔다(`PickNearestIndex` 동률 규칙 등) | 정렬 없이 출력하면 같은 판을 다시 봐도 회고 줄 순서가 달라진다 |

### 5.4 🔴 증분 안전성 판정 — 사용자 질문에 대한 답

**결론: C1 → C2는 안전하다. C1 → C3는 조건부로만 안전하며, 그 조건은 C1에서 못 박아야 한다.**

**① C1 → C2: ✅ 안전.**
C2는 `record.Events.Add(...)`만 한다. C1 필드를 읽지도 고치지도 않는다.
표시 지점도 다르다 — C1은 **회고 화면**, C2는 **정보줄**. 문구가 경쟁하지 않는다.
append 지점 6곳 중 2곳(완공·집획득)은 기존 이벤트 구독이라 **원본 파일을 열지도 않는다**.

**② C1 → C3: ⚠️ 한 곳에서 위험하다. 그리고 그 위험은 C1의 설계로만 막을 수 있다.**

C3의 관계 스냅샷(`BuddyIdAtExit`)은 **퇴장 시점에 찍어야** 하는데, 그 시점은 C1이
`LeftDay`·`Cause`를 쓰는 바로 그 지점이다. 그런데 —

```
VillagerAgent.Die()  →  State = Dead  →  Destroy(gameObject, TransientLineSec)   // 지연 파괴
                                              ↓ (몇 초 뒤)
                                         OnDestroy() → _sim.UnregisterAgent(this)
                                                          ├ Relationship.ReleaseBy(id)   ← 관계가 여기서 사라진다
                                                          ├ Ownership.ReleaseBy(id)
                                                          └ Requests.ReleaseBy(id)
```

**만약 C1의 퇴장 기록을 `UnregisterAgent`에 두면**, C3에서 관계 스냅샷을 찍으려는 순간
`ReleaseBy`가 **같은 메서드 3줄 아래**에서 이미 지웠거나 곧 지운다. 순서 의존이 생기고,
C3는 C1의 쓰기 지점을 **옮기는 수술**을 하게 된다 — 사용자가 우려한 정확히 그 실패다.

➡️ **그래서 C1은 지금 다음을 못 박는다 (ADR-M13-3):**

> **퇴장 기록의 쓰기 지점은 `Die()` / `StarveToDeath()` 두 곳이다.**
> `UnregisterAgent`는 **보루**로만 쓴다 — 사망 경로를 안 거치고 소멸한 레코드에 한해
> `Cause == Alive`일 때만 `Unknown`으로 마감한다(멱등).

이 결정으로 C3는 **C1이 이미 여는 두 메서드에 두 줄을 더하는 일**이 되고, C1 스키마·쓰기 지점을
건드리지 않는다. **증분이 성립한다.**

**③ 잔여 위험 1건 (🟡 관찰):** `Id` 재사용. `_usedNames`(`SimulationLoop.cs:306`)가
*"사망·이탈로 빠져도 이름은 예약 유지 — 같은 이름 재등장 = 서사 혼동"* 을 이미 보장한다.
**확인 완료 — 위험 아님.** 다만 세이브 구현 시 `_usedNames`도 함께 저장돼야 이 보장이 유지된다
(현재 주석에 세이브 대상으로 선언돼 있음).

    if (threatDays >= 0 && threatName != null)

    return sb.ToString().TrimEnd('\n');

| 퇴장 사유를 덮지 않음 | `M13-T3` `CloseIfOpen` 멱등 게이트 |
| 기존 회고 문구 호환 | **M10-T6 무수정 green** |

## §8. ADR — 구현 중 갈릴 판단 (바꾸려면 사유를 커밋 메시지에)

**`ADR-M13-1` 보이지 않는 커밋 금지.**
기록 항목은 **반드시 표시 지점과 짝지어 커밋한다.** C1은 회고 반영까지, C2는 정보줄 반영까지가
**한 커밋**이다. 기록만 있고 화면에 아무 변화가 없는 커밋은 반려.
*사유: M12에서 게이트로만 검증한 구간이 길어지자 사용자가 "질질 끌려다니는 느낌"을 제기했다.
표현층은 매 항목이 화면에 보이므로 항목마다 Play가 자연스럽다 — 그 자연스러움을 규칙으로 못 박는다.*

**`ADR-M13-2` 기록 스키마는 append-only.**
`ExitCause`·`EventId`는 **뒤에만** 추가한다(값 재배열·중간 삽입 금지). `VillagerRecord`의
필드는 C1에서 확정되며 C2·C3는 **예약된 칸을 채울 뿐 추가하지 않는다.**
*근거: M12의 `{TraitId, Value}` 쌍 배열 + enum append-only 규약("7번째 축을 추가해도 기존 에셋
0개 수정")과 `SlotId`의 append 규칙(ADR-M0-9)을 사건 로그에 복제.*

**`ADR-M13-3` 퇴장 기록은 사유를 아는 곳에서 쓴다.**
`RecordExit`의 호출처는 `Die()`·`StarveToDeath()` **둘뿐**이다. `UnregisterAgent`는
`Cause == Alive`인 레코드를 `Unknown`으로 마감하는 **보루**로만 쓴다.
*사유: `UnregisterAgent`는 `Relationship.ReleaseBy`와 같은 메서드이고, C3가 그 자리에서
관계 스냅샷을 찍어야 한다. 여기 기록을 두면 C3가 C1을 수술하게 되어 증분이 무너진다(§5.4).
"소멸 경로 단일성"(ADR-M0-3 정신)은 자원 해제의 규칙이지 기록의 규칙이 아니다.*

**`ADR-M13-4` 기록은 시뮬레이션을 쓰지 않는다.**
`ChronicleService`는 월드 상태·슬롯·플래너에 아무것도 쓰지 않는다. 읽기 전용 출력 축이다.
*단 `BehaviorProfiler`와 달리 **세이브 대상**이다 — 개인의 생애는 로드 후 재계산되지 않는다.*

**`ADR-M13-5` 치사율은 유지한다.**
사망률을 낮추는 밸런스 변경은 이 밀스톤 범위 밖이다. *사유: 낮추면 다시 관찰자 게임이 된다 —
치사성이 플레이어 개입의 "필요"를 만든다(2026-07-17 baseline 0 판정의 정면 해법).*
⚠️ **경계 명시**: `ADR-M12-4 ①`("성격 때문에 굶어 죽는 것은 금지")은 이번 건에 걸리지 않는다.
그 조항이 막는 것은 **성격이 몸을 방해하는 것**(밥을 늦게 먹게 하는 것)이다. 게으름뱅이는
배고프면 정상적으로 먹고, **대비를 안 해서** 겨울에 먹을 것이 없을 뿐이다 = 선택의 결과이지
몸의 불이익이 아니다.

## §11. 재미 검증 — 플레이어가 화면에서 새로 보게 되는 것

> 프로젝트가 2026-07-07에 정하고 **7 밀스톤 동안 안 지킨 규칙**: *"모든 작업 전 '플레이어가
> 보는 것' 한 문단을 먼저 쓴다. 못 쓰면 보류."* M13은 이 원칙으로의 복귀다.

**M13이 끝나면 플레이어는 이런 판을 본다.**
겨울이 오기 전 화면 왼쪽에 붉은 줄이 뜬다 — *"굶는 주민 — 식량 1일치."* 눌러보면 A다.
게으름뱅이, 무직, 집도 없고 지금 하는 일은 "쉬는 중"이다. 계획 사슬이 비어 있고 포만은
명령 거부 문턱까지 6밖에 안 남았다. **지금 명령하면 듣고, 조금 더 늦으면 못 듣는다.**
"저거 캐와"를 시킨다. 정보줄에 사건이 하나 쌓인다 — *"Day 31 명령 수락."* 며칠 뒤 A는
살아남았고, 그 경험이 `MyWasStarved`를 켜서 **그 뒤로 스스로 집을 원하기 시작한다.**
B는 못 구했다. 회색 비석에 이름표가 붙는다 — *"B · Day 34."*
마을이 무너진 날, 회고 화면에는 숫자 대신 명부가 뜬다:
*"B — 게으름뱅이, 무직. Day 3~34, 굶어 죽음."* / *"A — 고집쟁이, 농부. Day 0~41, 부상."*
그리고 A의 줄 아래 그가 겪은 일들이 있다 — 다쳤고, 누군가 치료했고, 집을 얻었고, 한 번
명령을 거부했다.

**이것이 회상 테스트가 찾던 것이다.** *"한 번 구해줬더니 사람이 됐다"* 는 이야기를
기계는 이미 전부 갖고 있었고(`MyWasStarved`는 M12-G에서 만들어졌다), **발동할 기회와
그것을 볼 창이 없었을 뿐이다.**
