## 0. 왜 하는가 (한 문단)

`ADR-M16-4`는 *"화폐의 구매력은 반드시 물가를 경유한다 — 액면 직접 사용 금지"* 라고 못
박았는데, 집 부탁만 `RewardCostAmount = 50`을 액면 그대로 쓴다. 결과: 촌장이 돈을 풀수록
식량은 비싸지는데 집은 그대로 → **인플레 중에 집이 상대적으로 싸져 발행의 대가가 오히려
보상이 된다** (사용자 관측 2026-08-01: "발행을 3번 했는데 집값은 50동 그대로"). 근본 원인은
`SlotCondition`이 `(슬롯, 연산, 상수)`뿐이라 슬롯 대 슬롯 비교가 안 되는 것 — M17에서 같은
벽에 두 번 부딪혔고 한 번은 아사를 냈다(`44c93fe`의 상수 49).

## 2. 전제 확인 (0단계 실사 산출물 — 2026-08-04 코드 실사)

1. **경계 지도 유효 (재확인)**: `SlotCondition[]` 배열은 정확히 6개, 비교 판정은
   `GoalSelector.AllHold` 단일 구현(GoalSelector.cs:105)뿐. 호출처 = GoalSelector 2곳(트리거·
   달성 스킵) + VillagerAgent 2곳(명령 799·부탁 809 완수 판정) + RequestService 3곳(우회 139·
   의뢰인 186·대상 196). **플래너 잡은 `ActionCompiler`가 `(int)c.Op`로 변환해 먹인다**
   (ActionCompiler.cs:115) — 새 필드·새 연산자를 잡에 넣지 않는 한 잡은 아무것도 모른다.
2. **§8.7이 놓친 결함 ① — `CompareOp`에 미만(<)이 없다** (SlotId.cs:174, 3종뿐). 상수 시절엔
   `≤ 49`로 `< 50`을 표현했지만 슬롯 비교에선 불가능. 연산자 2종(`Less`·`Greater`)을 추가한다
   (사용자 승인 2026-08-04).
3. **§8.7이 놓친 결함 ② — "TradePrice 한 줄"이 아니라 돈 지점 5곳**: 선불 판정(RequestService
   237)·선불 이전(260)·빚 설정(426)·연기 정산 판정(461)·후불 이전(535). 수락과 정산 사이에
   물가가 변하면 액수가 갈린다 → 가격을 수락 시점에 확정한다 (ADR-M18-2).
4. **§8.7이 놓친 결함 ③ — 대사에 "50동" 하드코딩**: 집 부탁 에셋 2개의 `AskLines` 6줄이
   "50동"을 문장 안에 품고 있다. 가격이 동적이 되면 대사가 거짓말을 한다.
5. **금지 칸 무충돌 (의심했으나 무혐의)**: `Goal_SaveForHome`·`Goal_RepayDebt`의
   `GoalConditions`는 증분(`MyMoney +10`, `RelativeToCurrent=1`)이라 집값·빚을 참조하지 않는다.
   바꿀 상수는 전부 트리거/의뢰인 조건(허용 칸)에 있다.
6. **연대기는 개인 레코드 체계** (ChronicleService — 주민별 `VillagerRecord.Events`): "집값
   인상"이라는 전역 사건의 자리가 없다. → 개인 사건 `HomePaid`(지불액 포함)로 번역한다.
   `Traded`(Value = 지불액) 선례 그대로.
7. **물가 배선 기존 통로**: `SimulationLoop.PricePct`(하루 1회 갱신, ADR-M16-3 캐시) →
   `RequestService`에 `() => PricePct` 델리게이트 주입(SimulationLoop.cs:869). WorldModel
   파생 슬롯 주입은 `_injuredCount` 델리게이트 선례.

### 경계 지도 (게이트의 명세 — 이 표가 곧 M18-T1이다)

| 조건 배열 | `AllHold`(관리) | 플래너 잡 | `CompareToSlot`·`Less`·`Greater` |
|---|---|---|---|
| `GoalSO.TriggerConditions` | ✅ | — | ✅ 허용 |
| `RequestSO.RequesterConditions` | ✅ | — | ✅ 허용 |
| `RequestSO.TargetConditions` | ✅ | — | ✅ 허용 |
| `RequestSO.TraitBypassConditions` | ✅ | — | ✅ 허용 |
| `GoalSO.GoalConditions` | ✅ 3곳 | ✅ 계획 목표 | 🔴 **금지** |
| `ActionSO.Preconditions` | — | ✅ | 🔴 **금지** |

🔴 금지 사유: `GoalConditions`는 관리 코드 세 곳(달성 스킵·명령 완수·부탁 완수)과 잡이 **함께**
읽는다. 켜면 관리 판정은 새 필드를, 잡은 상수를 봐서 **플래너가 세운 목표와 완수 판정이
갈린다**. `Preconditions`는 잡이 `(int)Op`로 그대로 삼키므로 새 연산자 값 3·4가 잡에 유입된다
— 잡의 스위치가 모르는 값이다 (ADR-M0-5 동결이라 잡 쪽 수용도 금지).

## 4. 넓히기 분류 (§0.5)

- **② 새 선반**: 조건 문법의 우변 축(`CompareToSlot`/`RightSlot`) + 연산자 2종.
  **완성 후 약속: "슬롯 대 슬롯 비교가 필요한 트리거는 에셋 0개로 표현된다."**
- **① 선반 위 물건**: `HomePriceNow` 파생 슬롯(기존 파생 슬롯 선반) · `HomePaid` 사건(기존
  연대기 선반) · 대사 실가격 병기(AskTrade 301 선례 재사용).

## 5. ADR-M18 (구현 중 갈릴 판단 — 바꾸려면 사유를 커밋에)

- **ADR-M18-1 (트리거 전용)**: `CompareToSlot`·`Less`·`Greater`는 경계 지도의 허용 4칸에서만.
  금지 2칸은 OnValidate 2곳 + 전체 에셋 스캔 게이트(M18-T1)가 막는다. 잡·ActionCompiler는
  손대지 않는다 — 이 금지가 ADR-M0-5(잡 동결) 무관의 근거다.
- **ADR-M18-2 (가격 수락 시점 확정)**: 집 부탁 실가격은 수락 판정 직전에 1회 산출해 진행
  기록(`_inFlight`→`_pendingReports`)에 싣고, 이후 모든 판정·이전·빚·로그는 **그 값 하나만**
  읽는다. 정산 시점 재계산 금지 — 판정 액수와 이전 액수가 갈린다.
- **ADR-M18-3 (기준가 단일 출처)**: `HomePriceNow`의 기준가는 집 소유권을 주는 Request
  에셋(`GrantOwnership && OwnershipSlot == HouseCount`)의 `RewardCostAmount`다. WorldConfig에
  새 필드를 파지 않는다(이중 기입). 해당 에셋이 여럿이면 값이 전부 같아야 하며 게이트가
  강제한다(M18-T2).
- **ADR-M18-4 (액수 표기 = 실가격만)**: 대사·연대기에 노출되는 집값 액수는 확정 실가격만.
  대사 문자열 안에 액수를 하드코딩하지 않는다 (ADR-M16-4의 표현층 연장).

## 6. 작업 항목

### W1 — 조건 문법 확장 + 금지 게이트 (한 커밋 — 문법과 금지는 한 몸)

**대상**: `Assets/Scripts/M0/Data/SlotId.cs` · `Assets/Scripts/M0/Planning/GoalSelector.cs` ·
`Assets/Scripts/M0/Data/GoalSO.cs` · `Assets/Scripts/M0/Data/ActionSO.cs` ·
`Assets/Tests/EditMode/M18_ConditionGrammarGates.cs`(신규, csproj 등록)

```csharp
// SlotId.cs — CompareOp append (기존 값 불변)
public enum CompareOp
{
    Equal = 0, GreaterOrEqual = 1, LessOrEqual = 2,
    Less = 3,     // M18 — 트리거 전용 (ADR-M18-1). 잡 유입 금지 (게이트 M18-T1)
    Greater = 4,  // M18 — 〃
}

// SlotId.cs — SlotCondition append (기존 에셋은 false/0 역직렬화 = 동작 불변)
public struct SlotCondition
{
    public SlotId Slot; public CompareOp Op; public int Value;
    public bool   CompareToSlot; // M18 — 켜면 Value 대신 RightSlot 현재값과 비교 (ADR-M18-1)
    public SlotId RightSlot;
}

// GoalSelector.AllHold — 우변 선택 + 연산 2종
int rhs = c.CompareToSlot ? snap.Get(c.RightSlot) : c.Value;
switch (c.Op)
{
    case CompareOp.Equal:          hold = v == rhs; break;
    case CompareOp.GreaterOrEqual: hold = v >= rhs; break;
    case CompareOp.LessOrEqual:    hold = v <= rhs; break;
    case CompareOp.Less:           hold = v <  rhs; break;
    case CompareOp.Greater:        hold = v >  rhs; break;
    default:                       hold = false; break;
}

// GoalSO.OnValidate — GoalConditions 금지 (ActionSO.OnValidate의 Preconditions도 동형)
foreach (SlotCondition c in GoalConditions)
    if (c.CompareToSlot || c.Op >= CompareOp.Less)
        Debug.LogError($"[GoalSO] {name}: GoalConditions에 슬롯 비교/새 연산자 금지 — " +
                       "잡과 완수 판정이 갈립니다 (ADR-M18-1)", this);
```

게이트 `M18_ConditionGrammarGates`:
- T1a: 전체 `GoalSO` 에셋 스캔 — `GoalConditions`에 `CompareToSlot`/`Less`/`Greater` 0건.
- T1b: 전체 `ActionSO` 에셋 스캔 — `Preconditions` 동일 0건.
- T1c: `AllHold` 단위 — 슬롯 비교(참/거짓 각 1) · `Less` 경계(`v == rhs` → false) ·
  `Greater` 경계 · `CompareToSlot=false`면 기존 3연산 결과 불변.
- T1d: `CompareToSlot=true && RightSlot == Slot` 에셋 0건 (자기 비교 = 상수 참/거짓 — 실수).

- [x] `CompareToSlot=false` 조건만으로 기존 게이트 전체 green (동작 불변 증명) —
      2026-08-04 batchmode 338/338 (기존 331 + 신규 7)
- [x] T1c 경계 검증 — 구현은 `MyMoney vs MyDebt`(70==70)로 수행: `HomePriceNow` 슬롯은
      W2에서 생기므로 W1 시점에 참조 불가(명세 문구의 선행 오류). 값 검증은 W2 T2가 잇는다
- [x] 실패 가능성 증명 — "임시 위반 심기 후 제거" 대신 **영구 테스트로 승격**:
      T1-Detector(위반 3종 탐지 + 오탐 3종 무혐의) + T1e(OnValidate가 실제로 에러 발화,
      LogAssert). 제거식 확인은 1회성인데 이쪽은 회귀도 잡는다
- [x] OnValidate 위반 시 Console에 ADR-M18-1 문구 에러 — T1e가 GoalSO(리플렉션)·
      RestActionSO(상속 경로) 양쪽 검증

⚠️ **오해 위험**: ①"허용 4칸에도 OnValidate를 달자" — 아니다, **금지 2칸만** 막는다. 허용
칸의 검증은 게이트가 아니라 문법의 소비자다. ②"잡 쪽 스위치에 Less를 추가해 주면 완전하다"
— 반려. ADR-M0-5 동결이고, 잡이 모르는 것이 이 설계의 안전핀이다. ③`RightSlot` 기본값 0 =
`WoodStock` — `CompareToSlot=false`면 무의미하니 정상. 기본값을 바꾸지 않는다(enum 재배열 금지).

### W2 — 파생 슬롯 `HomePriceNow` (40/52)

**대상**: `Assets/Scripts/M0/Data/SlotId.cs` · `Assets/Scripts/M0/World/WorldModel.cs` ·
`Assets/Scripts/M0/SimulationLoop.cs`

```csharp
// SlotId.cs — append (Count 39 → 40, IsNumeric에 추가)
HomePriceNow = 39, // 수치형 파생 — 집 실가격(동) = TradePrice(기준가, 확정 물가).
                   // 트리거 전용 (ADR-M9-9 패턴 — 플래너 전제·효과 금지 = MyMoney ADR-M16-5 동형).
                   // 기준가 원천 = 집 소유권 Request의 RewardCostAmount (ADR-M18-3 — 새 필드 금지).
                   // 예보(Forecast)가 아니라 **확정 물가만** 쓴다. 예산 52칸 중 40.

// WorldModel — 배선 (기존 _injuredCount 델리게이트 선례)
private int _homeBasePrice;                    // 0 = 미배선 (아래 🔴 주석 필수)
private System.Func<int> _slotPricePct;
public void BindHomePrice(int basePrice, System.Func<int> pricePct)
{ _homeBasePrice = basePrice; _slotPricePct = pricePct; }

// BuildSnapshot — MyDebt(456) 아래 append
// 🔴 이 한 줄과 SimulationLoop의 BindHomePrice가 없으면 슬롯이 0 — SeekCarpenter(≥)가
// 항상 발동하고 SaveForHome(<)이 영영 안 뜬다. MyDebt(M17-W7)와 같은 함정 자리다.

    ? RequestService.TradePrice(_homeBasePrice, _slotPricePct != null ? _slotPricePct() : 100)
    : 0;

// SimulationLoop 초기화 — RequestService 생성부(869) 근처
// 기준가 = 집 소유권 Request들의 RewardCostAmount (전부 동일 — 게이트 M18-T2)
World.BindHomePrice(FindHomeBasePrice(_worldConfig.Requests), () => PricePct);
```

게이트 `M18-T2`: 집 소유권 Request 에셋(`GrantOwnership && OwnershipSlot == HouseCount`)이
1개 이상 존재하고 `RewardCostAmount`가 전부 동일 · `TradePrice(50,140) == 70` ·
`TradePrice(50,100) == 50`(중립) 순수 검증.

- [ ] `SlotIds.Count == 40`, `IsNumeric(HomePriceNow) == true`
- [ ] 물가 100%에서 스냅샷 `HomePriceNow == 50` (기존 상수와 동치 — 동작 불변의 다리)
- [ ] 물가 140%에서 `HomePriceNow == 70` (올림 산식 재사용 확인)
- [ ] 미배선 WorldModel 단독 생성 시 슬롯 0 (게이트에 명시 — 침묵 함정 문서화)

⚠️ **오해 위험**: ①예보 물가(`forecastPct`)를 쓰면 "내일 오를 테니 오늘 비싸게"가 된다 —
**확정 `PricePct`만**. ②기준가를 `WorldConfigSO`에 새 필드로 파는 것 — 반려(ADR-M18-3,

### W3 — 실가격 수락 시점 확정 (돈 지점 5곳 단일화)

**대상**: `Assets/Scripts/M0/World/RequestService.cs`

      곱하게 되므로** 화폐 보상에만 적용: `price = r.RewardCostSlot == SlotId.MyMoney

- [ ] `Traded`(직거래) 경로 diff 없음 (이미 실가격)

## 10. 재미 검증 (플레이어가 새로 보는 것)

지금까지 발행의 대가는 식탁에만 청구됐다 — 물가가 올라도 집값은 50동이라, 돈을 풀수록 집이
싸지는 **거꾸로 된 보상**이 숨어 있었다. 이제 촌장이 돈을 풀면 다음 날 물가와 함께 집값이
오른다: 집을 부탁하는 주민의 말풍선이 "— 70동"을 부르고, 50동을 모아 뿌듯하던 주민은 목표가
밀려나 더 오래 일하며, 연대기에는 판마다 다른 "집값 지불(N동)"이 남아 **그 판의 경제가 어떤
판이었는지**를 증언한다. 발행 버튼의 무게가 무거워지는 것 — 그것이 M17이 만들려던 재미
엔진의 방향 복원이다.
