## 2. ADR — 구현 중 갈릴 판단을 미리 결정

> 아래 결정을 바꾸려면 **무엇을 관측했고 이 결정이 왜 실패하는가**를 커밋 본문에 남긴다
> ([[feedback_living_adr_revision]] 규약).

### ADR-C-1 — 개간은 채집이 아니다 (별도 액션)

**결정**: `ClearActionSO` + `ClearRunner`를 새로 판다. 채집(`GatherRunner`)에 얹지 않는다.

**기각한 안과 이유** (되살리려는 유혹이 반드시 오므로 근거를 박제한다):

| 안 | 내용 | 기각 이유 |
|---|---|---|
| B | `BuildRunner`가 계획 칸의 노드를 만나면 **스스로 치우고** 짓는다 | 새 슬롯 0·새 goal 0으로 제일 싸다. 그러나 **한 행동 안에서 두 일이 일어나 표현이 뭉개진다** — 목수가 도끼질하다 담을 세운다. M13 원칙("작업은 플레이어가 화면에서 보게 되는 것으로 정의")에 정면으로 어긋난다. 게다가 벌목 부하가 목수 한 사람에게 몰린다 |
| C | 개간 = **채집을 끝까지** (잔량 0이 되면 소멸) | 새 러너 0으로 제일 매력적이었다. 🔴 **기각 이유는 시간이 아니라 플래너 계약이다.** GOAP는 **선언된 효과**로 계획한다: `Goal_Clear`의 목표는 `ClearPendingCount` 감소인데 `ChopWood`는 그 슬롯을 안 건드린다고 선언돼 있어 **플래너가 계획을 세울 수 없다.** 건드린다고 적으면 개간과 무관한 **평범한 벌목까지 "개간했다"고 거짓말**하게 된다 (대기가 0일 때도 그 효과가 붙는다) |

> 📐 **검산 기록** (내가 한 번 틀린 자리 — 박제한다): C를 기각하며 처음에 *"나무 한 그루에
> 채집 50회"* 라고 적었는데 **틀렸다.** 배포값은 `ChopWood` 수확 **10** / 노드 `maxAmount` **50**
> = **5회**(2.5초 × 5 = 12.5초)이고, `MineStone` 8 / 40 = 역시 5회다. **시간은 문제가 아니었다.**
> 근거가 무너져도 결론이 서는지 다시 물어 얻은 것이 위의 플래너 계약이다.
> 🔑 교훈은 M17이 이미 적어 둔 것과 같다 — **산수를 에셋에서 읽지 않고 머리로 하면 틀린다.**

**그래서 개간은 제 이름을 갖는다** — 목적이 자원이 아니라 **자리**이기 때문이다.
채집은 "나무를 얻으려고" 하고 개간은 "자리를 비우려고" 한다. 목적이 다르면 행동도 다르다.

⚠️ **모션은 새로 만들지 않는다** — `AnimKind`는 채집과 **같은 것**을 쓴다 (도끼질은 도끼질이다).
`ClearActionSO`의 `AnimKind` 칸에 기존 채집 값을 넣는다. 새 그림 **0장**.

### ADR-C-2 — 노드를 지우는 유일한 문 = `DiscoveryService.RemoveNode`

`ADR-M0-3`(상태 쓰기 단일 지점)의 계승. 제거는 **이력 기록 · 재생 목록 정리 · 점유 해제 ·
뷰 소멸**을 한꺼번에 끌고 다니므로, 문이 둘이면 반드시 한쪽이 빠뜨린다.
`_nodes.Remove(...)`를 다른 어디에서도 부르지 않는다 (게이트 `M22_T18`이 전수로 감시).

### ADR-C-3 — 개간 이력은 세이브 대상 (`ADR-M0-10` 선언)

`DiscoveryService`의 개간 좌표 집합은 **판을 이어받으면 함께 와야 한다.** 이걸 안 저장하면
불러오기 뒤 M26 리스폰이 개간한 자리에 나무를 도로 심고, **오늘 닫은 구멍이 다시 열린다.**

### ADR-C-4 — 슬롯 1칸을 쓴다 (예산 50 → **51**, 잔여 2 → **1**)

`ClearPendingCount = 50`. 🔴 이 칸은 **M24 2·3차 몫으로 예약돼 있던 2칸 중 하나**다
(`M11_InventoryGates:173` 주석). 예약을 깎는 결정이므로 근거를 남긴다:

- 개간 goal은 **트리거가 필요하고**, 트리거는 슬롯으로만 걸린다 (이 프로젝트의 유일한 통로).
- 기존 슬롯 재사용은 전부 거짓말이 된다 — `DefensePlannedCount`는 **지을 수 있는** 계획의 수라
  막힌 칸을 거기 더하면 "계획인데 못 짓는다"가 되어 목수 goal이 **공회전**한다
  (M5 자가 재검토 🔴가 이미 밟은 지뢰).
- M24 2·3차가 2칸을 다 쓰게 되면 그때 `SlotIds.Count`를 52 위로 올리는 판단을 한다 —
  **예산은 성역이 아니라 예산이다.**

### ADR-C-5 — 개간은 **플레이어가 그은 칸에서만** 시작된다

자동 개간 없음. 마을이 스스로 숲을 밀지 않는다. 개간 지정의 유일한 입구는
**울타리·문·함정·망루 계획이 노드에 막히는 순간**이다.
🔴 이유: 자동으로 열어 두면 나무꾼이 마을 둘레의 나무를 전부 치우고, 그건 플레이어가
고른 적 없는 지형 개조다. 무한 자원 전제를 지키는 울타리도 여기다.

### ADR-C-6 — 회수 = 남은 잔량 **전부**, 단 **소요 시간은 잔량에 비례한다**

개간 완료 시 노드의 `CurrentAmount`를 내림해 해당 스톡에 넣는다. 플레이어가 **손해 보지
않는다** — 손해가 나면 "구멍을 그냥 두는 편이 낫다"가 되어 이 축이 스스로를 무력화한다.
⚠️ 수치를 발명하지 않는다: 회수량의 원천은 **노드가 이미 갖고 있는 값**이다.

> 🔴 **착취 구멍 — 명세 검산 중 발견 (2026-08-10)**
> 회수를 전부 주면서 소요 시간을 채집 1회로 두면, 개간이 **5배 빠른 벌목**이 된다:
> 정상 벌목은 `ChopWood` 2.5초 × 5회 = **12.5초에 나무 50**인데, 개간은 **2.5초에 나무 50**이다.
> 그러면 플레이어가 담을 세우려고가 아니라 **자원을 캐려고** 마을 둘레에 줄을 긋는다.
> 발견 경로도 적어 둔다 — *"회수는 전부"* 와 *"소요는 채집과 같은 값"* 을 각각은 합리적으로
> 정했는데 **곱해 보니** 무너졌다. 🔑 **두 수치를 따로 정했으면 반드시 곱해 볼 것.**
>
> **결정**: 소요 시간 = `채집 1회 시간 × ceil(잔량 ÷ 채집 1회 수확량)`.
> 자원 효율이 **정확히 같아지고**(착취 0), 인과도 읽힌다 — **꽉 찬 나무는 오래 걸리고 다 캔
> 그루터기는 금방 치워진다.** 두 값 다 **에셋에서 읽는다** (발명 0).

### ADR-C-7 — 개간 지정 노드는 재생하지 않는다

`TickRegeneration`이 지정 노드를 건너뛴다. 안 그러면 개간을 기다리는 동안 잔량이 차올라
회수량이 **지연 시간에 비례**하게 되고, "늦게 칠수록 이득"이라는 이상한 전략이 생긴다.

## 3. W1 — 노드 제거의 문

**대상 파일**
- `Assets/Scripts/M0/World/DiscoveryService.cs`
- `Assets/Scripts/Core/ResourceNode.cs` (플래그 1개)

**코드 스케치**

```csharp
// ── ResourceNode.cs ──
/// <summary>개간되어 세상에서 지워졌는가 (M22-4차). 뷰가 이 값을 보고 스스로 사라진다 —
/// Core가 M0 서비스를 모르므로 이벤트가 아니라 플래그다 (의존 방향 유지).</summary>
public bool IsRemoved { get; set; }

// ── DiscoveryService.cs ──
/// <summary>개간된 타일 (M22-4차 · ADR-C-3 세이브 대상) — **M26 리스폰 금지 목록**이다.
/// 이걸 안 남기면 불러오기·리스폰이 개간한 자리에 노드를 도로 심어 울타리 구멍이 다시 열린다.</summary>
private readonly HashSet<Vector2Int> _cleared = new HashSet<Vector2Int>();
public IReadOnlyCollection<Vector2Int> ClearedTiles => _cleared;
public bool WasCleared(int x, int y) => _cleared.Contains(new Vector2Int(x, y));

/// <summary>노드 제거 알림 (제거된 노드, 회수량) — 울타리 계획 승격·HUD 구독 지점.</summary>
public event System.Action<ResourceNode, int> OnNodeRemoved;

/// <summary>
/// 노드를 세상에서 지우는 **유일한 문** (M22-4차 · ADR-C-2, ADR-M0-3 계승).
/// 회수량(내림한 잔량)을 돌려준다 — 스톡 적립은 호출자(러너)의 효과가 한다
/// (수치의 단일 출처는 여기, 적립의 단일 출처는 EffectApplier).
///
/// 🔴 `_nodes.Remove`를 다른 곳에서 부르지 말 것: 제거는 이력·지정 해제·점유 해제·뷰 소멸을
/// 한꺼번에 끌고 다닌다. 문이 둘이면 반드시 한쪽이 빠뜨린다 (게이트 M22_T18이 감시).
/// </summary>
public int RemoveNode(ResourceNode node)
{
    if (node == null || !_nodes.Contains(node)) return 0;
    int recovered = Mathf.FloorToInt(Mathf.Max(0f, node.CurrentAmount)); // ADR-C-6
    node.IsRemoved = true;                    // 뷰가 다음 Refresh에 스스로 사라진다
    ResourceNode.OccupiedTiles.Remove(new Vector2Int(node.TileX, node.TileY));
    _clearPending.Remove(node);               // W2 — 지정 목록에서도 빠진다
    _nodes.Remove(node);
    _cleared.Add(new Vector2Int(node.TileX, node.TileY));
    Debug.Log($"[Clear] 개간 — ({node.TileX},{node.TileY}) {node.ResourceType} 제거 · 회수 {recovered}");
    OnNodeRemoved?.Invoke(node, recovered);
    return recovered;
}
```

/// ⚠️ `DefensePlannedCount`에는 **안 센다** (ADR-C-4): 목수가 못 짓는 칸을 세면 goal이 공회전한다.</summary>

/// <summary>줄 계획 결과 (M22-4차) — added = 바로 지을 칸, blocked = 개간을 기다리는 칸.
/// 🔴 blocked 를 **돌려주는 것 자체가 이 차수의 요점**이다: 舊 코드는 조용히 건너뛰었고
/// 화면은 "8칸"이라고만 해서 플레이어가 구멍을 모른 채 넘어갔다.</summary>
public readonly struct PlanResult
{
    public readonly int Added, Blocked;
    public PlanResult(int added, int blocked) { Added = added; Blocked = blocked; }
}

private PlanResult AddLinePlan(List<Vector2Int> target, string label,
                               IReadOnlyList<Vector2Int> tiles,
                               Func<int, int, bool> buildable,
                               Func<int, int, bool> blockedByNode)   // null = 개간 없는 판 (중립)
{
    int added = 0, blocked = 0;
    foreach (Vector2Int t in tiles)
    {
        if (IsPlannedOrBuilt(t) || _blockedFences.Contains(t)) continue;
        if (buildable != null && !buildable(t.x, t.y))
        {
            // 노드에 막힌 칸만 대기로 넘긴다 — 바위·물·맵 밖은 여전히 그냥 못 짓는 칸이다.
            if (blockedByNode != null && blockedByNode(t.x, t.y) && target == _plannedFences)
            { _blockedFences.Add(t); blocked++; }
            continue;
        }
        target.Add(t); added++;
    }
    if (added > 0 || blocked > 0) { /* 로그 + OnPlanChanged */ }
    return new PlanResult(added, blocked);
}

/// <summary>개간 완료 승격 (M22-4차) — 대기 칸이 열리면 울타리 계획이 된다.
/// `DiscoveryService.OnNodeRemoved` 구독 지점. 승격된 칸이 있었으면 true.</summary>
public bool PromoteClearedTile(Vector2Int tile)
{
    if (!_blockedFences.Remove(tile)) return false;
    if (IsPlannedOrBuilt(tile)) return true;   // 그 사이 다른 계획이 들어왔다 — 중복 금지
    _plannedFences.Add(tile);
    Debug.Log($"[Defense] 개간 완료 — ({tile.x},{tile.y}) 울타리 계획으로 승격");
    OnPlanChanged?.Invoke();
    return true;
}

public override bool Prepare(VillagerAgent agent)
{
    _node = agent.Discovery.FindNearestClearPending(agent.TileX, agent.TileY);
    if (_node == null) { FailReason = "개간 대기 노드 없음"; return false; }
    // 자원별 효율을 그대로 쓴다 (M20 ADR-M20-2) — 나무꾼은 나무를, 광부는 돌을 빨리 친다.

    //    채집 1회면 개간이 5배 빠른 벌목이 된다. 두 수치는 반드시 함께 본다.
    //    ⚠️ 배수의 두 항(1회 수확량·1회 소요)은 **에셋에서 읽는다** — 코드에 상수로 두면
    //    에셋을 고치는 순간 착취가 조용히 되살아난다 (ADR-M0-2).
    DurationMult = agent.GatherDurationMultOfJob(_node.ResourceType) * ClearWorkMult(agent, _node);
    // 노드 **곁**에 선다 (겹쳐 서기 금지 — 채집과 같은 규약, 2026-08-10 사용자 Play).
    MoveTarget = MapBounds.PickWalkableAdjacent(agent.IsWalkable,
                                                _node.TileX, _node.TileY, agent.TileX, agent.TileY);
    return true;
}

public override RunnerResult Tick(VillagerAgent agent, float dt)
{
    agent.FaceTowards(new Vector2(_node.TileX, _node.TileY));
    if (!DurationElapsed(dt, DurationMult)) return RunnerResult.Running;
    // 그 사이 누가 먼저 쳤을 수 있다 — 사라진 노드를 치는 것은 실패다 (조용한 성공 금지).
    if (_node.IsRemoved) return Fail("이미 개간된 노드");
    int recovered = agent.Discovery.RemoveNode(_node);   // 유일한 문 (ADR-C-2)
    AddRecoveredToStock(agent, _node.ResourceType, recovered);  // ADR-C-6
    return RunnerResult.Succeeded;
}

이 차수가 끝나면, 줄을 긋는 그 순간 **붉은 칸 하나가 담 위에 뜨고** 화면이 말한다 —
*"1칸은 나무에 막혀 대기 — 먼저 치웁니다."* 잠시 뒤 나무꾼이 그 나무 앞에 서서 도끼질을 하고,
**나무가 사라지고**, 붉은 칸이 갈색 계획으로 바뀌고, 목수가 와서 담을 잇는다.
플레이어는 *"길을 내고 담을 세운다"* 는 한 문장을 **네 장면으로 나눠서 본다.**

그리고 그 다음 습격에서, 고블린이 지난번 그 자리로 들어오려다 **막힌다.**
오늘 W7R이 관측한 것과 짝을 이룬다 — 방어의 인과가 화면에서 이어지기 시작했다.
