# M22 — 방어 건설 실행명세서 (울타리 + 간단한 문 + 수리 루프)

*작성일 2026-08-08. 출발 재료 = 2026-08-06 인터뷰 1차 합의 (memory `project-m22-defense-prep`),
이월 원문 = `Docs/M21_격퇴축_실행명세서.md` 784행 (킬박스 위험 동봉).*

**한 줄 목표 (인터뷰 Restate 게이트 통과분)**: 플레이어가 그린 방어 구역에 목수가 울타리와
간단한 문을 세우고 수리하는 루프 — 위협은 내구도를 깎아 뚫고, 주민은 문으로만 다니며,
목수가 죽으면 방어가 무너지는 것이 화면에서 보인다.

**두 축 (합의 1 — 대등)**: ① 격퇴의 공간화(지형 전술) ② 목수 부재의 체감(헌장 ADR-M20-1 +
표현 조항). 명세의 모든 항목은 이 둘 중 하나에 닿아야 한다.

## 0. 성공 기준 (숫자로)

인터뷰 합의 5의 검증 4종이 그대로 1차 완료 판정이다 (2차 진입 게이트):

1. **침입이 울타리에 막힘**: 방어 구역이 완성된 판에서 위협 **출몰 생략 0건**
   (울타리 때문에 출몰이 통째로 사라지면 실패 — 전제 확인 ③ 참조), 울타리가 뚫리기 전
   구역 **안** 밭 소실·주민 타격 0건.
2. **공격으로 내구도 감소**: 위협 타격 N회 후 내구도 = `MaxDurability − N × StructureDamage`
   검산 일치 (탐지기 = 정보줄/로그의 내구도 값).
3. **목수 수리로 회복**: 수리 액션 1회 완료 시 해당 시설 내구도 = `MaxDurability` 복원,
   Wood 소모량 = 에셋 `RepairCost` 값과 일치.
4. **주민이 문으로만 통과**: 주민 이동 경로의 울타리 타일 통과 **0회**, 문 타일 통과 관측 ≥1회
   (JPS가 문으로 우회하는 스크린샷/좌표 시계열).
5. EditMode 게이트 전체 green (기존 357 + 신규 M22 게이트).
6. **부재 시나리오 (관측 주 — 합의 4)**: 목수 없는(사망한) 판에서 손상 울타리의 수리 도달이
   늦어져 구멍이 **누적**되는 장면이 화면에서 읽힌다 (수치 보조: 목수 유/무 판의 수리 완료
   횟수 비교).

**중간 리뷰 (리뷰⓪, W5 직후)**: 위협이 울타리 앞에 멈춰 때리는 **공성 동선**이 화면에서
보이는가. 안 보이면 W6 착수 금지 — M21 W2가 게이트 green인 채 뒤집힌 것의 재발 방지 장치.

## 1. 전제 확인 (0단계 실사 산출물 — 2026-08-08 코드 실사 3건)

memory·문서의 주장과 코드 실물이 어긋난 것, 설계를 바꾼 사실들:

1. **슬롯 예산은 41/52다** (memory의 40은 낡음 — M21-W5 `MyHasWeapon=40` 추가,
   `SlotId.cs:109 Count=41`). 잔여 11칸. memory 정정 완료.
2. **위협은 막히면 부수는 게 아니라 "출몰을 생략"한다** — 스폰 시 대표 경로가 Unreachable이면
   그 출몰 전체를 건너뛴다 (`ThreatService.cs:319-326`). **지금 코드에 울타리를 세우면
   킬박스가 아니라 완전 무적이 된다.** → W5 공성 경로가 이 명세의 핵심 신규 축.
3. **`Walkable` 복구 경로가 없다** — `Walkable[..]=false`는 완공 구독 1곳뿐
   (`SimulationLoop.cs:751-755`), `OnRemoved` 구독 3곳 어디에도 `true` 복원이 없다.
   울타리가 부서져도 JPS는 영영 막힌 걸로 본다. → W5에서 신설.
4. **시설 내구도·수리·단일형 제거는 전부 전무** — `Durability`/`Repair` 심볼 0건, 건설
   진행도는 러너 로컬 `Elapsed`뿐(부분 완성 없음), `RemoveCountableAt` 호출처는
   재해·위협의 FarmPlotCount 둘뿐.
5. **ZoneService는 그릇만 있고 완전 휴면** — `ZoneRadius > 0`인 건물이 0개라 `_zones`는
   영원히 비어 있다 (`b51c631` 이후). 모델도 "첫 완공 = 앵커" 자동 확정이라 "플레이어가
   먼저 지정"과 방향이 반대 → 등록 API 신설(W3). 표현(`ZoneBorderView`)과 저장 그릇은 재사용.
6. **플레이어 구역 지정 입력은 0에서 시작** — `PlayerInputController`의 어휘는
   선택·채집명령·F싸워라·C연대기·배속·Y/N뿐. 타일 스냅·드래그 문법 없음.
7. **`ApproachTileOf` 폴백 전제가 깨진다** — "밭은 통행 가능하므로 출몰이 생략되는 일은
   없다"(`ThreatService.cs:401-402`)는 밭을 울타리로 두르는 순간 거짓이 된다. W5가 함께 해소.
8. **목수는 에셋만 남고 스폰 풀 참조 0건** — `Job_Carpenter.asset`(BuildDurationMult 0.5 ·
   BuildCostMult 0.7) 보존, 씬 `_jobPool` 7종(Farmer·Lumberjack·Miner·Cook·Hunter·
   Explorer·Medic)에 없음. 게이트 `M19_T3b`가 "목수만 0.5, 나머지 1f"를 단언 중 — 부활은
   풀 재편입만이라 게이트와 충돌하지 않는다.
9. **개체별 통행 차등은 경로탐색 경계의 문서화된 시나리오가 아니다** —
   `ADR_경로탐색_확장경계.md`는 가중치 지형·HPA* 둘만 예비. → ADR 개정 동봉(W1, 사유 기록
   규칙 준수).
10. **이동 중 `Walkable` 재검사가 없다** — 주민 TickMoving은 타일 예약만 본다. 문이 동적으로
    열리고 닫히면 뚫린다 → 1차 문은 **정적 차등 통행**(상태 없음)으로 설계해 우회 (ADR-M22-5).

## 1.5 넓히기 분류 (직교성 — ①선반 위 물건 / ②새 선반)

| 구분 | 항목 | 근거 |
|---|---|---|

## 2. ADR (구현 중 갈릴 판단 — 바꾸려면 사유를 커밋에)

### ADR-M22-1 · 개체별 통행 = 배열 2벌, 인터페이스 무수정

통행 데이터를 `Walkable`(주민) + `ThreatWalkable`(위협) 두 벌로 나누고, `JpsPathfinder`
인스턴스를 하나 더 만들어 위협 쪽에 물린다 (`SimulationLoop.cs:766` 분기). **"누가 묻는가"는
시그니처가 아니라 인스턴스 선택이 흡수한다** — `IPathfinder.FindPath` 4-int 시그니처와 JPS
동결 라이브러리는 손대지 않는다. `Docs/ADR_경로탐색_확장경계.md`에 **트리거 C(개체별 통행
차등)** 를 개정 추가한다. 개정 사유: 문(주민만 통과)이 1차 범위로 승격되며 개체별 차등이
실수요가 됐다 — 배열 = 지형 표현이라는 경계 2의 정신은 유지된다.
⚠️ 배열을 늘릴 때마다 인스턴스가 따라온다 — 세 번째 배열이 필요해 보이면 그때 재설계 질문.

### ADR-M22-2 · 방어 시설은 안전을 팔지 않는다 (공성 강제)

목표 경로가 Unreachable인 위협은 **출몰을 생략하지 않고 가장 가까운 방어 시설을 때린다**
(공성). 시설이 파는 것은 **시간**(내구도 ÷ StructureDamage × 재타격 주기)뿐이다.
"완성되면 안전" 상태가 생기는 변경은 반려. 단 **자연 지형 막힘(방어 시설 0개)은 기존
생략 유지** — 생략 전 분기 조건이 `Defense.HasStructures`다.
(게이트: 방어 시설 존재 + Unreachable → 공성 타깃 반환 검증)

### ADR-M22-3 · 내구도의 집 = DefenseService, 쓰기 문은 둘뿐

내구도 상태는 `DefenseService`가 `(SlotId, Vector2Int) → float` 타일 키로 소유한다
(`HomeStorageService`·`FarmService` 선례). 쓰기는 `ApplyDamage`(위협)와 `Repair`(주민)
두 문뿐 (ADR-M0-3). 수치는 전부 에셋 — `BuildingSO.MaxDurability` / `ThreatSO.StructureDamage` /
`BuildingSO.RepairCost`. CombatService에 얹지 않는다 — 그 서비스는 주민→위협 **판정**의 집이고
상태가 없다(헤더 주석의 책무 경계). 위협→시설 타격은 위협→주민 타격(`ExecuteStrike`가
`TakeDamage` 직접 호출)과 동형으로 ThreatService가 `Defense.ApplyDamage`를 호출한다.

### ADR-M22-4 · 방어 구역 = 판당 1개, 지정 후 불변

1차의 방어 구역은 판당 1개, 앵커·반경은 지정 후 불변 (ADR-M9-2 "첫 완공 후 앵커 불변"과
정합). 재지정·이전·확장은 구역 이전 백로그(`project_zone_relocation` — 코드 선반영 금지
지시)와 합류하는 2차+ 주제다. 저장 그릇은 휴면 중인 `ZoneService._zones`를 재사용하고
(기존 통로 우선, M11), 플레이어 등록 API `EstablishPlayerZone`만 신설한다.

### ADR-M22-5 · 문은 상태 없는 정적 차등 통행

문에 열림/닫힘 상태를 만들지 않는다. 문 = **주민에게 항상 통행 가능, 위협에게 항상 통행
불가**인 타일 (BuildingSO `BlocksThreatMovement` 플래그). 근거: 주민 이동 중 `Walkable`
재검사가 없어(전제 확인 ⑩) 동적 개폐는 벽 뚫기 버그를 만든다. 개폐·잠금·경비는 2차+.

### ADR-M22-6 · 파괴 = 제거 + 통행 복구의 원자

방어 시설 파괴는 `ConstructionService.RemoveCountableAt` → `OnRemoved` 구독에서 두 통행
배열 복구(`true`)까지가 한 동작이다. 복구 구독은 `SimulationLoop`의 등록 구독
(`OnCompleted`, ADR-M3-3)과 같은 자리에 대칭으로 놓는다. 부분 성공 금지 — 제거됐는데
통행이 막혀 있으면 유령 벽이다. (게이트: 제거 후 두 배열 모두 true 검증)

### ADR-M22-7 · 수리는 비독점 — 격차는 5배, 수리 전용 배율로 (사용자 확정 2026-08-08)

수리 goal에 `RequiredJob` 독점을 걸지 않는다 (ADR-M19-3: 독점은 치료 1곳뿐 — 개정 사유
없음). **격차는 사용자 지시로 5배** ("주민이 1이면 목수는 5 — 이 정도는 돼야 부재가
체감된다"). 🔴 `BuildDurationMult`를 0.2로 내리면 집·밭 건설까지 5배가 되고 게이트
`M19_T3b`(목수 정확히 0.5)와 충돌하므로, **`JobSO.RepairDurationMult` 신설**(기본 1,
목수 0.2)로 수리만 가른다 — JobSO 헤더가 예비한 "새 효율 축 = 새 필드 그룹" 문법.
새 필드에는 M19_T3b 동형의 중립 게이트(목수만 0.2, 나머지 정확히 1f)를 단다.
부재 시나리오 = "누구나 고칠 수는 있지만 목수 없는 판은 수리가 5배 느려 위협 주기를
못 따라가 구멍이 누적되는 판" — 헌장 ADR-M20-1 충족, 전이 통로·반복 노동(ADR-M20-9) 충족.

## 3. 수치 관계식 (§4) — 전부 제안치, 리뷰⓪·①에서 조정

> ⚠️ 기존 값이 존재하지 않는 축이라 아래는 **전부 제안치**다 (수치 발명 금지 원칙에 따라
> 명시). 기준으로 삼은 기존 값: House Wood 20·Stone 10 / FarmPlot Wood 5 /
> Tier1 `StrikeDamage 34`·`RepeatStrikePeriodDays 0.25`·`MaxStayDays 0.75`.

| 값 | 제안치 | 근거 검산 |
|---|---|---|
| Fence: Wood | 1 | 반경 5 구역 = 둘레 40타일(울타리 39+문 1) → Wood 42 ≈ 집 2채 값. 이보다 크면 초반에 못 두른다 |
| Fence: MaxDurability | 100 | 주민 MaxHp(100)와 같은 층 |
| Gate: Wood | 3, MaxDurability 80 | 문이 약점 — 위협 최근접 선정에서 자연히 표적이 되는 날이 온다 |
| 방어 구역 반경 | 5 (체비쇼프, 11×11) | 기지 반경(EffectiveVillageRadius ≈ 39)보다 훨씬 작게 — 홈스테드 산개(M11-K)상 전체 포위는 불가능이 설계다 (합의 6) |
| ThreatSO.StructureDamage | Wolf **34** / Pack 34(마리당) / Bear **100** | 🔑 **핵심 검산**: 재타격 0.25일 × 체류 상한 0.75일 = 최대 3타. 34×3 = 102 > 100 → **늑대 한 출몰이 울타리 딱 1칸을 부수고 떠난다.** 25로 하면 3타 = 75 < 100 → 영원히 못 뚫는 완전 안전 = ADR-M22-2 위반. 곰은 일격 |
| RepairCost (BuildingSO) | Wood 1 | 수리 1회 = 시설 1개 전량 복원 (한 걸음, ADR-M0-12) |
| 수리 DurationSec | 10 (목수 실효 **2** — RepairDurationMult 0.2) | 사용자 확정 1:5 격차. 일반 주민의 수리는 "정말 느리게" — 위협 주기(6일) 안에 목수는 여러 칸, 일반은 한두 칸이 그림 |
| JobSO.RepairDurationMult | 목수 0.2 / 나머지 1.0 | 신설 필드 (ADR-M22-7) — BuildDurationMult와 분리, 중립 게이트 동반 |
| Goal_BuildDefense 우선순위 | 24 | 생산 대역(18~30) 안 — Fight(105)·생존 위에 두지 않는다 |
| Goal_RepairDefense 우선순위 | 26 | 건설보다 약간 위 — 구멍 메우기가 새 울타리보다 급하다 |

## 7. 재미 검증 절 — 플레이어가 화면에서 새로 보게 되는 것

지금까지 위협이 오면 플레이어가 할 수 있는 일은 F(싸워라) 하나였고, 공간은 아무 말도 하지
않았다. 이 명세가 끝나면: **내가 B로 그린 사각형**에 주민들이 울타리를 한 칸씩 세워 가고,
늑대가 그 벽 앞에 **멈춰 서서 때리는** 것이 보이고, 세 대를 맞은 울타리가 색이 바래다
부서져 **구멍**이 나고, 다음 출몰 전에 누군가 나무를 들고 가서 메우는 — 혹은 목수가 죽은
판이라 아무도 제때 못 가서 구멍이 두 개, 세 개로 늘어나는 — 것이 보인다. 주민들이 아침마다
문 한 곳으로 줄지어 나가는 동선은 마을에 처음으로 "안팎"이라는 형태를 준다. 위협은 여전히
뚫는다(늑대 한 출몰 = 울타리 한 칸) — 방어는 승리가 아니라 **다음 출몰까지의 시간**을 사는
것이고, 그 시간을 사는 노동이 곧 목수의 존재 증명이다.
