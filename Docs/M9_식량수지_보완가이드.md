## 0. 목적

식량 밸런스의 언어를 "개수"에서 **"남은 일수"**로 바꾼다. 조리식×포만가치와 생식×포만가치를
합산해 "지금 인원·지금 계절 기준 며칠 버티는가"를 파생 슬롯 하나(FoodDaysLeft)로 만들고,
식량 goal의 **트리거를 전부 이 슬롯**으로 옮긴다. 인원이 늘든 줄든, 계절이 바뀌든, 후일
식량 가치를 조정하든 밸런스가 자동 비례한다 — 수동 재계산 반복(10명→4명 사고)의 구조적
종결. 버퍼 문턱은 소요보다 **의도적으로 얇게** 잡아(사용자 결정) 요리사의 비축 goal이
영구 달성 상태로 잠들지 않고 주기적으로 순환하게 한다.

## 2. 재미 검증 — 플레이어가 화면에서 새로 보게 되는 것

좌상단 달력 옆에 **"식량 3일치"**가 붙는다 — 주민이 밥을 먹을 때마다, 주민이 늘 때마다
줄고, 수확이 들어오면 튀어오르는 숫자 하나로 마을의 목줄이 보인다. 요리사는 이 숫자가
2일치 밑으로 떨어질 때마다 모닥불로 돌아가 냄비를 잡는다 — 채우고, 소비로 다시 얇아지고,
또 돌아오는 **순환하는 직업 장면**. 겨울 예고가 뜨면 기준이 5일치로 올라가는데 폭염을 맞은
판은 그 숫자를 끝내 못 채운 채 겨울을 맞는다 — "3일치로 겨울을 났다"가 플레이어 입에서
나오는 회상 문장이 된다. 이탈이 나면 남은 사람들의 일수가 **늘어나는** 것도 보인다 —
상실이 수치로 남는 잔인한 위로.

## 3. ADR-M9 추가분 (구현 중 갈릴 판단, 바꾸려면 사유를 커밋에)

- **ADR-M9-9 (파생 슬롯은 트리거 전용)**: FoodDaysLeft는 TriggerConditions에서만 쓴다.
  GoalConditions에 쓰면 반려 — 액션 효과는 CookedFoodStock을 올리지 FoodDaysLeft를 올리지
  않으므로 플래너가 체인을 찾지 못한다 (DaysToCrisis가 트리거 전용인 것과 같은 이유.
  본 명세의 WinterPrep도 목표는 Cooked 슬롯이었다 — 같은 규약의 명문화).
- **ADR-M9-10 (식량 가치 단일 출처 = 소비 액션 에셋)**: 일수 계산에 포만 가치(50·15)를
  하드코딩하지 않는다. WorldConfig.FoodSources(ConsumeActionSO[])에 등록된 액션의
  전제(스톡 슬롯)·효과(MySatiety Add)에서 **파생**한다 — 가치를 에셋에서 바꾸면 수지가
  자동 추종 (ADR-M0-2 이중 기입 금지의 적용).
- **ADR-M9-11 (버퍼는 소요 미만 — "조금 부족하게", 2026-07-18 사용자 결정)**: 식량 goal
  트리거 문턱은 환산 소요의 100% 미만으로 잡는다 (평시 2일치, 겨울 대비 5일치 = 겨울
  실소요 7일치 환산의 71%). 문턱을 소요 이상으로 올려 "항상 넉넉"하게 만드는 밸런스 수정은
  "방치가 안락하면 실패" 기준 위반으로 반려. 부족의 위치는 **버퍼(트리거 문턱)**이지 생산
  능력이 아니다 — 생산이 물리적으로 못 따라가는 좌절 루프와 혼동 금지. 얇은 버퍼의 안전망 =
  P0(100)·굶주림 계단(포만 10 미만 0.5일, 약자부터).
- **ADR-M9-12 (RelativeToCurrent 씬 goal 확장)**: 상대 목표를 씬 goal에도 허용한다 —
  해석 시점 = **goal 선택 시점** (명령·부탁의 "수신 시점"과 동일 사상, ResolveRelativeGoal
  재사용). GoalSelector는 RelativeToCurrent goal의 "이미 달성 스킵" 검사를 면제한다
  (원본 증분값을 절대값으로 오독하는 버그 차단 — §5 M9-H ⚠️①). 남용 주의: 절대 목표로
  표현 가능한 goal은 절대값 유지 — 상대 goal은 "펌프"(소량 증분 반복)가 필요한 비축류만.

## 4. 데이터·수치

### 4.1 SlotId 확장 (append 규약)

`FoodDaysLeft = 19` (수치형 — 남은 식량 일수(내림). SlotIds.Count **20**, IsNumeric에 추가.
슬롯 예산 52칸 중 20 사용). 본 명세의 IrrigationBuilt = 18과 명시값 enum이라 순서 무관 —
본 가이드가 먼저 구현되면 18은 빈 칸으로 남고 M9-D가 나중에 채운다 (Count는 여기서 이미 20).

### 4.2 산식 (전 수치의 출처 명시 — 발명 0)

```
FoodDaysLeft = floor( Σ(스톡 × 1개당 포만) ÷ (생존 인원 × SatietyDecayPerGameDay × 현재 계절 SatietyDecayMult) )
```

- 스톡·1개당 포만: WorldConfig.FoodSources 등록 액션에서 파생 (현행 EatCookedFood
  조리식→+50, EatRawFood 생식→+15 — 액션 에셋 실측값, ADR-M9-10)
- 생존 인원: SimulationLoop._agents.Count (Dead 제외 — UnregisterAgent가 이미 정리)
- 감쇠: AgentConfig.SatietyDecayPerGameDay 25 (개체 편차 ±10%는 추정에서 무시 — 평균치)
- 계절 배율: SeasonService.SatietyDecayMult (겨울 1.75 — 겨울 중엔 같은 스톡이 짧아 보인다.
  의도: 위기 중 체감 가속)
- 중립 관례값: 인원 0·미배선 = **99** (SeasonService.NO_CRISIS 관례 재사용 — "≤N" 트리거 전부 불발)

검산 (4명·평시): 조리식 6 + 생식 15 = (300+225)÷100 = **5일치**. 겨울(1.75×): ÷175 = **3일치**.

### 4.3 겨울 소요의 일수 환산 (본 명세 §4.5의 번역)

겨울 실소요 = 4일 × 1.75배 = **평시 환산 7일치**. "조금 부족하게" = 겨울 대비 문턱 5일치
(71% — 본 명세의 WinterPrep 10개 제안과 같은 비율, 이제 인원 무관). 나머지 2일치가
생식 직식·겨울 중 잔여 수확으로 메꾸는 긴장 구간이며, 폭염을 맞은 판일수록 여기가 위험해진다.

### 4.4 에셋 수정·신설 (전부 제안치 — 기존 값 우선, 관측 후 튜닝)

- **WorldConfig 추가**: `FoodSources[]` (ConsumeActionSO 배열 — EatCookedFood·EatRawFood
  등록. 비면 FoodDaysLeft 항상 99 = 중립, 기존 동작과 완전 동일)
- **Goal_CookAhead 개편**: 트리거 = FoodDaysLeft **≤ 2** + RawFoodStock ≥ 3 (CookMeal
  1회분 정합 — 현행 6에서 하향, 재료 없으면 GatherFood가 먼저) / 목표 = **RelativeToCurrent,
  Cooked +2** (CookMeal 1회분 — 소량 증분 펌프: 달성 → 여전히 ≤2면 재발동 → 실물이 늘면
  자연 종결) / Priority 18·MaxWorkers 1 유지 (요리사 boost +30 → 실효 48 유지)
- **Goal_WinterPrep 개편** (본 명세 §4.4의 "20→10" 항목 **대체**): 트리거 = DaysToCrisis
  ≤ 3 + FoodDaysLeft **≤ 5** + CampfireBuilt / 목표 = **RelativeToCurrent, Cooked +2** /
  DisplayName "비축"·Priority 30·MaxWorkers 3 유지. 절대값 10은 폐기 — 인원이 몇이든 5일치
- **Goal_GatherFood**: 무수정 (생식 ≥ 15는 조리 재료 겸 기본 노동 — 4명 기준 2.25일치로
  얼추 정합. 🟡관찰: 인원 8+ 시 재검토, §8)
- **Goal_CookExtra(부탁 요리)**: 무수정 (이미 상대 +2 — 개인 주입 경로라 본 가이드와 무관)
- **Reward_MealRation(포만 40)**: 무수정 — 보상 축은 별도 (🟡 EatCooked 50과의 간극만 §8 등재)
