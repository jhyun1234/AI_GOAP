# 긴급 복구 실행 순서 — 플래닝 실패(NoSolutionFound) 해결 로드맵

> **목적**: 현재 발생 중인 "주민 전원 플래닝 실패 → Deadlock → 정지" 버그를 해결하고, 수치형 GOAP를 안전하게 재점화하기까지의 **정확한 작업 순서**.
> 각 단계는 독립 커밋이며, 단계 사이마다 반드시 Play Mode 확인을 거친다 — "하나씩 완벽하게 구현하고 하나씩 추가"의 실행 형태다.
>
> **대상 커밋**: `ed47f9a` 기준
> **작성일**: 2026-07-06

---

## 진단 요약 (왜 이 순서인가)

| 원인 | 내용 | 해결 단계 |
|---|---|---|
| **주원인: 노드 예산 고갈** | Job에 방문 상태 중복 검사(Closed Set)가 없다. `MoveToBase→MoveToBase→…`처럼 상태가 동일한 체인이 매번 새 노드로 등록되어, 깊이 6 이내 싼 액션 조합(수만 개, 전부 g<60)이 목표 경로(g≥60~500)보다 먼저 확장된다 → 8192 노드 소진 → NoSolutionFound. 레거시는 1스텝 플랜(g≈10~25)이라 홍수보다 먼저 발견됐지만, 수치형 5~6스텝 플랜은 묻힌다 | S1 (+S2) |
| **부원인: 도구 없는 주민의 무해(無解) Goal** | ChopWood/Mine 계열은 `HasTool=1` 필요, 도구를 주는 액션은 없음. `startWithTool=false` 주민에게 GatherWood는 수학적으로 해가 없다 → 즉시 실패 → Deadlock | S3 |
| 임시 완화의 한계 | MAX_NODES 8192 인상(시간·메모리 4배)과 목표치 하향(B23~B25)은 깊이 문제만 풀었고 조합 폭발은 못 막는다 | S2 후 원복 |

**작업 순서 요약**: `S0 롤백(오늘) → S1 Closed Set → S2 휴리스틱 → S3 도구 예외 → S4 재점화+검증`
명세서(W4→W5)와 순서가 뒤집힌 이유: 이번 버그의 직접 사인이 중복 상태이므로 **W5(=S1)가 지혈**이고, W4(=S2)는 그 위의 가속이다.

## S1. Closed Set — 중복 상태 차단 (핵심 수술)

**파일**: `GOAPPlannerJob.cs`, `GOAPPlannerScheduler.cs`
**명세**: Phase 2 실행명세서 W5와 동일. 현재 코드 상태(MAX_NODES=8192)에 맞춘 조정만 반영한다.

### 1-1. Scheduler — 버퍼 3개 추가

```csharp
// PlanningContext 필드 + 할당 + Dispose 3경로 모두에 추가 (GoalOps 때와 동일 패턴)
NativeArray<int>   visitedHashes;   // 크기 16384 (MAX_NODES 8192 × 2, 2의 거듭제곱 유지)
NativeArray<int>   visitedNodeIdx;
NativeArray<float> visitedGCosts;
// visitedHashes는 기본 0 초기화 = 빈 슬롯. 별도 클리어 불필요 (매 플래닝 새로 할당)
```

### 1-2. Job — 해시·등록 함수

```csharp
/// <summary>[S1] 노드 상태의 FNV-1a 해시. 0은 빈 슬롯 표식이므로 1로 치환한다.</summary>
private int HashState(int nodeIdx, int totalSlots)
{
    int o = nodeIdx * totalSlots;
    uint h = 2166136261u;
    for (int s = 0; s < totalSlots; s++)
    {
        h ^= (uint)NodeStates[o + s];
        h *= 16777619u;
    }
    int r = (int)h;
    return r == 0 ? 1 : r;
}

/// <summary>[S1] 상태가 처음이거나 더 싼 경로면 등록하고 true. 이미 같거나 싼 g로 방문했으면 false.</summary>
private bool TryRegisterState(int newNode, float g, int totalSlots)
{
    int hash = HashState(newNode, totalSlots);
    int cap  = VisitedHashes.Length;               // 16384 (2^14)
    int idx  = hash & (cap - 1);                   // 2의 거듭제곱 전제

    for (int probe = 0; probe < cap; probe++)
    {
        int slotHash = VisitedHashes[idx];

        if (slotHash == 0)                          // 빈 슬롯 → 신규 등록
        {
            VisitedHashes[idx]  = hash;
            VisitedNodeIdx[idx] = newNode;
            VisitedGCosts[idx]  = g;
            return true;
        }

        if (slotHash == hash && StatesEqual(VisitedNodeIdx[idx], newNode, totalSlots))
        {
            if (VisitedGCosts[idx] <= g) return false;   // 같은 상태를 더 싸게 이미 방문 → 확장 포기
            VisitedGCosts[idx]  = g;                      // 더 싼 경로 발견 → 재개방
            VisitedNodeIdx[idx] = newNode;
            return true;
        }

        idx = (idx + 1) & (cap - 1);                // 선형 프로빙 (해시 충돌 = 다른 상태)
    }
    return true;   // 테이블 포화 (이론상 도달 불가: cap = 노드 상한 × 2) — 안전 측으로 허용
}

/// <summary>[S1] 두 노드의 상태 전수 비교. 해시 일치 시에만 호출된다.</summary>
private bool StatesEqual(int nodeA, int nodeB, int totalSlots)
{
    int a = nodeA * totalSlots, b = nodeB * totalSlots;
    for (int s = 0; s < totalSlots; s++)
        if (NodeStates[a + s] != NodeStates[b + s]) return false;
    return true;
}
```

### 1-3. 메인 루프 연결 — 위치가 전부다

`Execute()`의 액션 확장부에서, **Effect 적용과 g-cost 계산 이후, HeapPush 이전**:

```csharp
ApplyEffectsToNode(newNode, totalSlots, action);
float gCost = NodeGCosts[current] + action.BaseCost;

// [S1] 동일 상태를 같거나 싼 비용으로 이미 방문했다면 이 노드를 버린다.
// nodeCount를 증가시키지 않았으므로 버퍼 슬롯은 다음 후보가 재사용한다.
if (!TryRegisterState(newNode, gCost, totalSlots)) continue;

// (기존) h 계산 → NodeGCosts/NodeCosts 기록 → Depth/Parent/Action 기록 → HeapPush → nodeCount++
```

### ⚠️ 오해 위험 (지난 리뷰 패턴 기준, 특히 주의)

1. **해시만 믿고 전수 비교(StatesEqual)를 생략하지 말 것.** 해시 충돌 시 도달 가능한 플랜을 잘못 폐기해 "가끔, 재현 불가하게" 플래닝이 실패하는 최악의 버그가 된다. 52개 int 비교는 해시 일치 시에만 발생하므로 성능 문제가 아니다.
2. **루트 노드(0)도 등록할 것.** `Execute()` 초기화부에서 `TryRegisterState(0, 0f, totalSlots)` 1회 호출 — 빠뜨리면 "시작 상태로 되돌아오는 순환"(예: MoveToBase 후 복귀)을 못 거른다.
3. 재개방(더 싼 g 발견) 분기는 드물지만 반드시 필요 — 없으면 admissible 휴리스틱 하에서도 최적성이 깨질 수 있다.
4. `visitedHashes.Length`가 2의 거듭제곱이 아니면 `& (cap-1)` 인덱싱이 깨진다. Scheduler 할당 크기를 상수로 고정할 것 (`MAX_NODES * 2`).

## S2. 새 휴리스틱 — 부족량/최대증가량 (탐색에 방향 부여)

**파일**: `GOAPPlannerJob.cs`, `GOAPActionRegistry.cs`, `GOAPPlannerScheduler.cs`
**명세**: 실행명세서 W4 그대로. 요점만 재확인:

1. Registry가 `BuildActionDefs()` 직후 액션 배열을 1회 스캔해 슬롯별 `MaxGain[s]` / `MaxDrop[s]`(해당 슬롯을 가장 크게 올리는/내리는 Effect 절대값, 없으면 1) 산출 → Scheduler가 NativeArray 2개로 Job에 주입.
2. Job의 `CalculateHeuristic` 교체:
   - GreaterEq 슬롯: `ceil((목표−현재)/MaxGain[s])`
   - LessEq 슬롯: `ceil((현재−목표)/MaxDrop[s])`
   - Equal 슬롯: 1 (기존 불리언과 동일)
   - 합산 × `minActionCost × 0.99f`
3. **minActionCost는 `Execute()` 서두에서 Actions 배열 min(BaseCost) 실측** (ADR-5). `HEURISTIC_WEIGHT = 2.9f` 상수 삭제 — Phase 1 컨텍스트 배율(`RestOnGround ×0.4` 등)이 실효 비용을 2.9 밑으로 내릴 수 있어, 하드코딩은 기존 코드에서도 이미 admissibility 잠재 버그다.

### 검증
- [ ] 레거시 모드에서 산출 플랜 불변 + 확장 노드 수 추가 감소 (S1 계측 로그와 비교)
- [ ] admissibility 주석(명세서 W4의 증명 메모)을 코드에 남김

## S4. 수치형 재점화 + 최종 검증

**파일**: `GOAPPlannerScheduler.cs`, `GOAPPlannerJob.cs`

1. `UseNumericGoals = true`
2. **10분 무개입 방치 테스트** (중간점검 가이드의 최종 기준):
   - [ ] NoSolutionFound / Deadlock 경고 0건 (도구 없는 주민 포함)
   - [ ] 자원 4종이 임계값 이상으로 수렴 → 건설 진행 → Explore 전환 사이클 유지
   - [ ] 사고 체인 UI에서 `Explore → ChopWood ×5` 형태의 멀티스텝 플랜 관측 — **Phase 2의 존재 이유가 화면에 보이는 순간**
3. **MAX_NODES 원복 실험**: 8192 → 2048로 내리고 위 테스트 재실행.
   - 통과 → 2048로 확정 커밋 (메모리 1.7MB→0.43MB/플래닝, 워커 시간 최악치 ¼)
   - 실패 → S1/S2 어딘가의 버그 신호다 (명세서 W6 게이트 논리). 8192로 두지 말고 원인을 찾을 것 — NodesExpanded 로그가 어느 시나리오에서 폭발하는지 알려준다
4. Profiler 캡처: 70명 스트레스 상황 Job 합산 시간 기록 → 1.8ms 예산 확인. 이 수치가 이후 W6(깊이 12)·W8(GoalArbiter)의 기준선이 된다.

## 커밋 계획

```
commit 1 (S0): fix(goap): disable numeric goals until closed set lands
commit 2 (S1): feat(goap): closed set — duplicate state pruning in planner job
commit 3 (S2): feat(goap): deficit/max-gain heuristic + dynamic min-cost scale
commit 4 (S3): fix(ai): skip tool-gated gather goals for toolless villagers
commit 5 (S4): feat(goap): re-enable numeric goals; restore MAX_NODES 2048 (+profiler baseline)
```

commit 1은 오늘 바로. 2~5는 각각 검증 통과 후에만 진행한다. **어느 단계에서든 검증이 실패하면 다음 단계로 넘어가지 않는다** — 이것이 "많은 기능이 한꺼번에 들어가서 생기는 문제"의 구조적 재발 방지책이다.

## 이후 순서 (참고)

S4 완료 = 실행명세서의 W4·W5 완료와 동일하다. 남은 Phase 2는 **W6(깊이 12) → W7(런타임 정합화) → W9(EditMode 테스트 12케이스 + 플랜 수선) → W8(GoalArbiter)** 순서를 권장한다. W9를 W8보다 앞당기는 이유: 이번 버그 같은 회귀를 EditMode 테스트(T4/T5가 정확히 GatherWood 시나리오다)가 씬 실행 없이 잡아준다 — 테스트가 먼저 있었다면 이번 버그는 커밋 전에 발견됐을 것이다.
