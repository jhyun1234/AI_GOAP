2. Scheduler의 Complete 처리부에 조건부 로그:

## N2 (= W7). 런타임 정합화 — 하드코딩 숫자 소탕

플래너와 런타임이 **같은 상수를 참조**하게 만든다. 현재는 값만 우연히 일치하는 상태(P2에서 수동 동기화)라, 어느 한쪽만 수정되는 순간 플랜-현실 괴리가 재발한다.

### 작업

**대상 위치** (사전 조사 완료 — ActionDatabase.cs):
- L814: `MakeEffect(ReduceHunger, 50f)` → `GOAPActionRegistry.EAT_HUNGER_RELIEF`
- L828: `MakeEffect(ReduceHunger, 15f)` → `EAT_RAW_RELIEF`
- L882: `MakeEffect(ReduceFatigue, 20f)` → `REST_FATIGUE_RELIEF`
- L895: `MakeEffect(GainHealth, 40f)` → `MEDICAL_HEALTH_GAIN`
- VillagerFSM의 `SLEEP_FATIGUE_RECOVERY = 90f` → Registry 상수 참조로 교체 (또는 FSM 상수를 삭제하고 Registry 것 사용)
- 채집 산출량(ChopWood +5 등)이 반영되는 지점 → `YIELD_*` 상수 참조
- 건설 자원 차감 지점 → `BUILD_*` 상수 (이미 BuildingCosts.cs와 동기화돼 있으므로, BuildingCosts가 Registry를 참조하거나 그 역방향 중 한쪽으로 통일)

**소탕 검증 명령** (커밋 전 실행):
```
grep -rn "ReduceHunger,\s*[0-9]\|ReduceFatigue,\s*[0-9]\|GainHealth,\s*[0-9]" Assets/Scripts
→ 결과 0건이어야 함 (전부 상수 참조로 교체됨)
```

### ⚠️ 오해 위험
- float/int 혼용: Registry 상수는 int, ActionDatabase는 float를 받는다 — 캐스팅만 하면 되지만, **반올림이 끼는 구조로 바꾸지 말 것** (값이 1이라도 어긋나면 T12가 잡는다).
- 자원 증감 반영 지점이 예약 시스템 Commit과 이중이 되지 않는지 재확인 (중간점검 가이드 P2와 동일 주의).

### DoD
- [ ] 소탕 grep 0건
- [ ] 게임 동작 변화 없음 (값이 같으므로 리팩토링일 뿐 — 변화가 있다면 어딘가 값이 달랐다는 뜻이고, 그게 바로 찾아야 할 버그)

## N3 (= W9). EditMode 테스트 12케이스 + 플랜 수선

**이 단계가 이번 로드맵의 무게중심이다.** 코드보다 안전망이 먼저 커지는 시점.

### 3-1. 테스트 인프라

- `Assets/Tests/EditMode/` 폴더 + asmdef (references: 게임 어셈블리, nunit)
- 헬퍼: `Plan(Dictionary<int,int> state, string goalId, AgentRole role)` — CurrentState 구성 → BuildGoalState → BuildActionDefs → **`job.Run()`(동기 실행)** → 결과 반환. 씬·MonoBehaviour 불필요.
- 컨텍스트 배율은 `ContextMultipliers.Identity`로 고정 — 테스트는 순수 플래너 로직만 검증한다.

### 3-2. 케이스 12개 (실행명세서 W9 표 그대로 — 요약)

| 그룹 | 케이스 | 핵심 검증 |
|---|---|---|
| 회귀 | T1 레거시 플래그 Goal / T8 이미달성(-1) / T9 미지 goalId | 연산자 기본값·특수값 경로 |
| 수치 | T2 식사 1스텝 / T3 **수확→요리→식사 멀티스텝** / T4 ChopWood ×5 / T5 ×6(깊이12) / T6 GreaterEq Prec / T7 Sub 클램프 | Phase 2 본체 |
| 품질 | T10 휴리스틱 켬/끔 동일 플랜 / T11 Closed Set 켬/끔 동일 플랜 | 최적성 (속도 장치가 답을 바꾸지 않음) |
| 정합 | T12 20개 액션 플래너 Effect == 런타임 상수 delta | ADR-7 자동 강제 |

T10/T11의 "켬/끔"은 조건부 컴파일이 아니라 **테스트에서 MaxGain을 전부 1로 채우거나(휴리스틱 무력화) Visited 버퍼를 크기 1로 주는(사실상 무력화) 방식**으로 구현하면 프로덕션 코드 분기가 필요 없다.

### 3-3. 플랜 수선 (FSM, 축소판 2개만)

1. **실행 전 사전검증**: `State_Executing`에서 다음 액션 착수 직전, 최신 스냅샷으로 해당 액션의 Prec만 재검사(구조체 헬퍼 `CheckPreconditions` 재사용 — W2에서 이미 연산자 대응됨). 불충족 시 **CurrentGoalId 유지한 채** Replanning 진입 (Idle 미경유 — 완료 진척 보존).
2. **수선 카운터**: 같은 Goal에서 수선 리플래닝 2연속 실패 시에만 Idle 복귀(Goal 재선택). 기존 FallbackCounter와 **별도 필드** — 의미가 다르다(수선 = 세계 변화 대응 / Fallback = 플래닝 실패).

수선 발동 시 F3 대사 풀에 1종 추가: *"어라, 상황이 바뀌었네. 다시 생각해보자."*

## N4 (= W8). GoalArbiter — Utility Goal 중재기

Phase 2의 마지막 큰 조각. 상세 명세는 **실행명세서 W8 절을 그대로 따른다.** 여기서는 순서상 주의점만:

1. **N3의 테스트가 있는 상태에서 착수한다** — Arbiter는 Goal 선택만 바꾸고 플래너는 건드리지 않으므로, 12케이스가 깨지면 안 된다 (깨지면 스코프 위반 신호).
2. `SelectGatherGoalId()`(P1)와 S3 도구 가드의 로직을 **Arbiter 안으로 흡수**한다 — Consider의 ratio 계산이 그대로 Utility 점수의 원형이고, `hasTool` 가드는 해당 Goal 점수 0 처리로 옮긴다. FSM에는 Arbiter 호출 + 발화만 남긴다.
3. P0 하드 오버라이드는 절대 흡수하지 않는다 (명세서 ⚠️ 1번).
4. 히스테리시스(관성 ×1.15 + 최소 유지 5초) 없이 커밋하지 말 것 — 없으면 우왕좌왕이 즉시 보인다.
5. 점수 로그(`GOAL_ARBITER_LOG`) 포함 — 밸런싱은 숫자가 보여야 가능하다.
