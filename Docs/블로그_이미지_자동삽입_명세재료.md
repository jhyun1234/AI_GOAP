# 블로그 이미지 자동 삽입 — 명세 재료

작성 2026-08-01. **이 문서는 명세서가 아니라 명세 전 실사 기록이다.** 실행명세서는 M17이
끝난 뒤 `spec-write` 절차로 따로 쓴다. 여기 적힌 것은 (a) 실제로 재본 값과 (b) 그 값이
강제하는 설계 귀결, (c) 아직 안 재본 것의 목록이다.

계기: 사용자 질문 — *"쇼츠 파이프라인처럼, 블로그 글에도 상황에 맞는 이미지를 자동으로
만들어 붙일 수 있을까?"*

---

## 0. 한 줄 결론

**된다.** 그림은 AI 이미지 생성이 아니라 **에이전트가 쓰는 SVG 텍스트**로 만들고,
**data URI(`data:image/svg+xml`)** 로 본문에 넣고, **작성 단계에서는 자리표만 남기고 승인
뒤에 치환**한다. 블로거 저장 경로는 새니타이징이 없어 아무것도 막지 않는다.

## 1. 실측 (2026-08-01, 드래프트 id `3651540856696193014`)

블로거에 비공개 초안 1건을 올려 A/B/C 세 방식을 한 글에 담고, API로 되받아 대조했다.
초안은 지우지 않고 남겨둔다(재현용).

### 1-1. 저장 경로 = 무손실

| 항목 | 값 |
|---|---|
| 보낸 바이트 | 5,461 |
| 저장 후 되받은 바이트 | 5,461 |
| `diff` | 완전 일치 |

인라인 `<svg>`, `data:` URI, `style` 속성, `<figure>/<figcaption>` — **한 글자도 안 건드린다.**
"블로거가 태그를 걸러낼 것"이라는 가정은 틀렸다. 이 실측 전까지 이게 제일 큰 미지수였다.

### 1-2. 네 방식 모두 브라우저에서 렌더됨

| 변형 | 렌더 | 비고 |
|---|---|---|
| A. 본문 인라인 `<svg>` | ✅ | 한글 텍스트·화살표 정상 |
| B1. `data:image/svg+xml;base64` | ✅ | 도해 1장 = base64 1,508자 |
| B2. `data:image/png;base64` | ✅ | 320×120 체커보드 = 908자 |
| C. `raw.githubusercontent` SVG 핫링크 | ✅ | 실제 로드됨. CSP `sandbox` 헤더는 `<img>` 임베드를 막지 않음 |

### 1-3. 부수 실측 — 설계를 직접 바꾼 것들

**(a) `*.png`는 raw 핫링크가 깨진다.** [.gitattributes:131](../.gitattributes) 이 png를 LFS로
잡는다. `raw.githubusercontent`가 이미지 대신 **130바이트 포인터 텍스트**를 내려준다
(`Content-Type: text/plain`). 반면 `*.svg`는 LFS 대상이 아니라 `image/svg+xml`로 정상 서빙된다.
→ **원격 호스팅을 쓴다면 SVG여야 한다. PNG를 쓰려면 LFS 예외를 파야 한다.**

**(b) GitHub Pages가 필요 없다.** raw가 svg를 올바른 content-type으로 준다(twemoji svg로
교차 확인). 리포 설정 변경 0건.

**(c) 테마 CSS에 그림을 막는 규칙은 없다.** 라이브 블로그에서 뽑은 42개 규칙 중 관련된 것:

```css
.post-body img { max-width: 100% }      /* img만 잡는다 */
svg:not(:root) { overflow: hidden }
figure { margin: 1em 40px }             /* 인라인 style로 덮어써야 함 */
```

**(d) 🔴 테마 규칙만 믿으면 그림이 찌그러진다.** 360px 폭 컨테이너에서 실측:

| 변형 | 렌더 크기 | 판정 |
|---|---|---|
| ① 인라인 svg, style 없음 | 640×120 | **컨테이너를 넘침** (모바일 가로 스크롤) |
| ② 인라인 svg + `max-width:100%;height:auto` | 360×68 | 정상 (종횡비 유지) |
| ③ `<img>`, width/height 속성만 | 360×**120** | **종횡비 깨짐** (68이어야 함) |
| ④ `<img>` + `max-width:100%;height:auto` | 360×68 | 정상 |

테마의 `max-width:100%`는 폭만 줄이고 `height` 속성은 그대로 둔다 → 세로가 늘어난다.
**A든 B든 `style="max-width:100%;height:auto"`가 필수다.** 이건 선택이 아니다.

**(e) 🔑 `textLength`로 글자 잘림을 구조적으로 없앨 수 있다.** 클라우드 실행이라 픽셀
검수를 못 하는 게 이 트랙의 근본 제약인데, 그 구멍을 메우는 수단이 SVG 자체에 있었다.

```
<text textLength="280" lengthAdjust="spacingAndGlyphs">…</text>
```

같은 문장을 서로 다른 폰트(sans/serif)로 렌더해 실측: 자유 폭은 267px, `textLength="280"`을
건 쪽은 **정확히 280px**. 즉 **뷰어 기기의 폰트가 무엇이든 텍스트 폭이 선언값으로 고정된다.**
→ 담는 상자보다 작은 `textLength`를 선언하게 강제하면, **렌더 없이도 잘림이 원리적으로
불가능**해진다. 텍스트 기반 검증기만으로 충분해지는 근거가 이것이다.

## 2. 🔴 쇼츠 파이프라인 오염 — 인라인 SVG만 샌다

[scene-planner.md:29-38](../.claude/agents/scene-planner.md) 의 본문 추출 명령을 실측 글에
그대로 돌린 결과:

```
PROBE-A 아래에 도해가 보이면 인라인 SVG가 살아남은 것입니다.

  이전: 굶주림 30
  ↓
  이후: 포만 70
  ↑
  PROBE-A          ← SVG 안 <text> 내용이 본문 문장으로 샌다
```

`.replace(/<[^>]+>/g,'')` 가 `<svg>`·`<rect>`는 지우지만 **`<text>`의 내용은 남긴다.**
그림 속 라벨이 출처 표시 없이 기사 본문으로 둔갑해 작성팀 브리프에 들어간다.

**data URI(B)와 원격 `<img>`(C)는 흔적 없이 사라진다** — base64 알파벳에 `>`가 없어 태그가
통째로 지워진다. 남는 건 `<figcaption>` 한 줄뿐이고, 이건 오히려 정확히 원하는 양의 신호다
(캡션은 진짜 문장이므로 대본 재료로 유효하다).

**→ 이 한 가지 사실이 방식 선택을 뒤집었다. 인라인 SVG(A)가 아니라 data URI(B1)가 기본이다.**

### 방어선 (방식과 무관하게 넣을 것)

추출기는 리포에 **한 군데뿐**이다(grep 확인: `scene-planner.md`만). 두 줄 추가:

```js
.replace(/<svg[\s\S]*?<\/svg>/g, '')     // 인라인 SVG 통째 제거
.replace(/data:[^"')\s]+/g, '')          // 혹시 남는 data URI 잔해
```

이유: `local` 사본이 없는 회차는 기획팀이 **WebFetch**로 원문을 받는데(2·3편이 그랬다),
그 경로에서 data URI가 base64 덩어리째 브리프에 실릴 수 있다. **공개 글에 아직 이미지가
없어 이 경로는 실측하지 못했다** — 방어선을 미리 깔아 두는 편이 싸다.

| | 쇼츠 오염 | 호스팅 | 발행 순서 제약 | og:image |

## 4. 파이프라인 어디에 넣는가 — 자리표 방식

### 왜 "쓰면서 넣기"가 안 되는가 (측정된 이유)

[blog-reviewer.md:56-70](../.claude/agents/blog-reviewer.md) 의 분량 게이트는 **초안 파일에
`LC_ALL=C.UTF-8 wc -m`을 돌리고, "태그 제외 등 다른 셈법을 금지"** 한다. data URI 도해 한 장이
약 2,000자다. 다섯 장이면 **1만 자의 base64가 산문으로 계수된다.** 하한 3,800자짜리 게이트가
무의미해진다. 셈법을 바꾸는 건 답이 아니다 — 그 규칙 자체가 2026-07-16 REJECTED_3X 사고의
재발 방지책이다.

### 왜 "다 쓴 뒤 붙이기"만으로도 부족한가

글쓴이가 그 순간 무슨 주장을 하고 있었는지가 사라진 뒤라, 그림이 문맥에서 겉돈다.

### 권장 = 두 이점만 취하는 자리표

1. **작성팀(Step 2)** 은 그림을 그리지 않는다. 자리표 한 줄만 남긴다:
   `[[FIG: 방아쇠 재배선 전후]]` (약 20자 → 분량 오염 사실상 0).
   "지금 무슨 주장 중인지 아는 사람이 자리를 고른다"는 이점은 그대로 살린다.
2. **검수팀(Step 3)·마스터 1차(Step 4)** 는 지금 그대로. 자리표가 그냥 텍스트라
   *"이 그림이 주장을 왜곡하지 않나"* 가 **기존 사실 검증 통로에 얹힌다.** 새 게이트를
   만들지 않는다 (방법론 M11 = 기존 통로 우선).
3. **신설 `blog-illustrator`** — 승인된 원고를 읽고 자리표를 SVG로 치환한다.
   반려 루프가 도는 동안에는 돌지 않는다 → 그림을 다시 그리는 낭비가 없다.
   (Step 5 편집팀 앞뒤 어느 쪽인지는 명세 때 결정 — §7 참조)
4. **마스터 2차(Step 6)** 가 최종 HTML에서 그림까지 판정한다. 검증기(§5) 결과를 증거로 쓴다.
5. 🔴 **실패 개방(fail-open).** 그림 생성·검증이 실패하면 **자리표만 지우고 글은 나간다.**
   그림 때문에 발행이 멈추면 안 된다.

## 5. 검증기 (블로그판 `check`) — 텍스트만으로 재는 항목

클라우드엔 크로미움이 없다. 픽셀을 못 보는 대신, **못 보고도 판정 가능한 형태로 SVG를
제약**한다. §1-3(e)의 `textLength`가 이 설계를 성립시킨다.

- [ ] `viewBox` 필수. 모든 좌표가 viewBox 안
- [ ] `width`/`height` 속성 + **`style="max-width:100%;height:auto"`** (§1-3(d) — 없으면 찌그러짐)
- [ ] 모든 `<text>`에 `textLength` + `lengthAdjust="spacingAndGlyphs"`,
      그리고 `textLength` ≤ 담는 도형 폭 − 여백
- [ ] **배경 `<rect>` 필수** (투명 배경 금지 — 다크 배경에서 글자가 사라진다)
- [ ] 외부 참조 전면 금지: `<script>`, `<image href>`, `<foreignObject>`, 외부 폰트
- [ ] `font-family` 화이트리스트 (`sans-serif`만)
- [ ] 색 팔레트 화이트리스트
- [ ] `alt`(또는 `aria-label`) 필수 + `<figcaption>` 필수 — 접근성 겸 쇼츠 쪽 유일한 신호
- [ ] 글당 base64 총합 상한 (기준값은 명세 때 — 도해 1장 ≈ 1.5KB)
- [ ] 🔴 **최종 HTML에 `[[FIG:` 잔해가 남아 있지 않을 것** (치환 누락 검출)

## 6. 그 밖에 짚인 것

- **🎨 회차가 그림을 소유한다.** 공용 도형 라이브러리를 만들면 글마다 같은 그림이 나온다.
  영상 트랙에서 이미 겪고 공용 kinds를 폐지했다 — 같은 실수를 반복하지 않는다.
  붓(검증기·제약)은 공유하고 그림은 매번 새로 그린다.
- **저작권 검수 규칙과 충돌 가능.** [blog-reviewer.md:55](../.claude/agents/blog-reviewer.md) 가
  *"저작권 미표기 이미지"* 를 반려 사유로 본다. 자체 생성 SVG는 해당 없음을 명시하지 않으면
  검수팀이 반려할 수 있다 → 규칙에 예외 한 줄이 필요하다.
- **애드센스 자동 광고와의 인접.** 본문 자동 광고가 켜지면 그림 바로 아래에 광고가 붙을 수
  있다. 캡션이 광고 라벨처럼 보이면 오인 클릭 유도로 읽힐 여지가 있다 → 캡션과 그림을
  시각적으로 묶고, 그림 직후 문단을 비우지 않는다.
- **리포 사본 비대.** 게시팀이 최종 HTML을 `published/<날짜>-<슬러그>.html`로 저장한다
  (blog-publisher.md:59). base64가 그대로 들어가지만 도해 1장 ≈ 1.5KB라 무시 가능하다.
  다만 diff 노이즈는 생긴다.
- **폰트는 뷰어 기기 것을 쓴다.** SVG 안 한글은 뷰어 폰트로 렌더된다 → 폭이 기기마다
  다르다. 이게 `textLength`를 필수로 만드는 이유다.

## 7. 아직 안 재본 것 / 결정할 것

측정 안 된 것을 측정된 것처럼 쓰지 않기 위해 분리해 둔다.

1. **테마 안에서의 최종 모습.** 초안은 공개 URL이 없어 로그인 없이 못 본다. 저장본이
   바이트 동일하고 방해 CSS도 없어 위험은 낮지만 **확인은 안 됐다.**
   확인 경로: [초안 편집기](https://www.blogger.com/blog/post/edit/6014451945015572125/3651540856696193014) 미리보기.
2. **`og:image`(썸네일/소셜 카드).** 현재 글엔 이미지가 없어 og:image가 아예 안 붙는다.
   블로거가 어느 방식에서 썸네일을 뽑는지는 실제 발행 전엔 알 수 없다. data URI는 거의
   확실히 안 잡히고 원격 `<img>`는 잡힐 가능성이 크다 — **썸네일이 필요하면 C**.
3. **WebFetch 경로의 base64 오염** (§2) — 실측 불가, 방어선으로 대응.
4. **`blog-illustrator`의 위치**: 편집팀(Step 5) 앞이냐 뒤냐.
   앞 = 마크다운 자리표를 그림으로 바꾼 뒤 편집팀이 HTML 변환 / 뒤 = 편집팀 HTML에 삽입.
   뒤가 깔끔해 보이나, 편집팀이 자리표를 어떻게 다룰지 정해야 한다.
5. **그림 개수·자리 기준.** h2 절당 최대 1장? 글당 2~5장? 미정.
6. **기존 14편 소급 적용 여부.** 백필하면 쇼츠 원본이 바뀐다 — 이미 만든 회차와의 정합성 검토 필요.
7. **자리표 문법** `[[FIG: …]]` 확정 여부 (마크다운·HTML 변환 어디서도 충돌은 없어 보임).
