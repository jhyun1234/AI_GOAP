## 1. 게시 플랫폼 결정 — Blogger 확정 (2026-07-09)

### 조사 경위 (정정 사항 포함)

처음에는 "티스토리 Open API가 2022년 2월 이후 신규 발급만 막혔고, 기존 API 키가 있으면
계속 쓸 수 있다"고 판단했으나 — **이는 오류였다.** 실제로 App ID 1508021로 인증 URL을
방문했을 때 `/oauth/authorize` 엔드포인트 자체가 "없는 페이지"를 반환했고, 웹 검색으로
확인한 결과 **티스토리 Open API는 2024년 2월에 전면 종료**되었다(파일첨부 → 글 관련
기능 → 댓글 관련 기능 → 그 외 기능 순으로 단계적 종료, 출처: [티스토리 Open API
서비스 종료 안내](https://tistory.github.io/document-tistory-apis/)). 기존 키 보유
여부와 무관하게 현재는 누구도 티스토리 공식 API로 글을 올릴 수 없다.

완전 무인 운영(0장)이 확정된 상태에서 "사람이 대신 붙여넣는" 폴백도 쓸 수 없으므로,
남은 선택지는 (a) Playwright로 티스토리 로그인+글쓰기 전체를 자동화 — 로그인 세션/2단계
인증/UI 변경에 취약하고 사람이 없어 조용히 깨질 수 있음, (b) 다른 플랫폼으로 전환뿐이었다.
**사용자가 (b) Blogger 전환을 확정했다.**

## 2. 파이프라인 개요

```
[스케줄러 트리거]
      ↓
Step 1. 소재 수집          [기획팀] git log + memory diff, 마지막 게시 이후 변경분만
      ↓
Step 2. 초안 작성          [작성팀] 개발 로그를 블로그 글로 변환
      ↓
Step 3. AI 리뷰            [검수팀] 품질/정책/사실관계/애드센스 저품질 정책 위반 여부 점검
      ↓
Step 4. 마스터 에이전트 1차 검수 [마스터 에이전트] 증거 기반 자체 판정, 방향/내용 승인
      ↓ (미승인 시 → Step 2로 재작성 루프)
Step 5. 최종 포맷팅        [편집팀] SEO 제목/메타, 이미지, 광고 위치, Blogger HTML 포맷 변환
      ↓
Step 6. 마스터 에이전트 2차 검수 [마스터 에이전트] 증거 기반 자체 판정, 최종본 발행 승인
      ↓ (미승인 시 → Step 2로 재작성 루프)
Step 7. 게시               [게시팀] 1장 권장안에 따름, 완전 무인
      ↓
Step 8. 게시 이력 기록      [게시팀] memory에 "이 커밋까지 다뤘음" 저장 → 중복 소재 방지
```

**부서(서브에이전트) 구조를 쓰는 이유**: 하나의 거대한 프롬프트가 소재선정→집필→검수→포맷팅을
전부 하면 역할이 섞여 자기 글을 자기가 검수하는 꼴이 된다. Step별로 별도 서브에이전트를 두면
검수팀이 작성팀의 결과물을 "남의 글"로 독립적으로 평가할 수 있고, 각 부서 프롬프트도 짧고
명확하게 유지된다.

**마스터는 사람이 아니라 에이전트다 (2026-07-09 확정)**: 사용자는 운영에 전혀 관여하지
않는다. 마스터 에이전트가 검수팀 리포트와 실제 산출물을 직접 대조해 "증거 제시" 원칙에
따라 자체적으로 승인/반려를 판정하고, 승인되면 게시팀에 게시 실행까지 위임한다. 사람이
"확인"이라는 텍스트를 입력하는 절차는 없다 — 대신 마스터 에이전트의 판정 자체가 구조화된
출력(승인 근거 필드 필수 기입)이어야 하며, 근거를 채우지 못하면 자동으로 반려 처리한다.

**반려 처리 규칙**: 마스터 에이전트가 승인 근거를 명확히 제시하지 못하면 반려로 처리한다.
반려되면 반려 사유를 Step 2 작성팀에 전달해 재작성 → 재검토 루프를 돈다. 매 반복마다 이전
반려 사유를 누적해서 다음 초안에 반영한다 (같은 지적을 두 번 받지 않도록). **연속 3회
반려되면 이번 스케줄 사이클의 게시를 자동 중단**하고 `memory/blog_pipeline_alerts.md`에
실패 로그를 남긴다 (6장 안전장치 참조) — 사람이 승인해야 재개되는 게 아니라, 다음 스케줄
사이클에 새 소재로 자동 재시도한다.

## 3. 소재 수집 (Step 1) 상세

- **범위**: 마지막으로 게시에 사용한 커밋 해시 이후 ~ 현재 HEAD까지의 `git log`
  (`git log <last_hash>..HEAD --stat`), 그리고 그 기간에 갱신된 `memory/project_*.md` diff.
- **마지막 커밋 해시 저장 위치**: `memory/blog_last_published_commit.md` (reference 타입) —
  다음 소재 수집 시 이 파일을 읽어 시작점을 정한다.
- **소재가 너무 적을 때(스케줄 도래했지만 커밋 1~2개뿐)**: 자동 스킵하고 다음 스케줄로
  넘긴다. 억지로 짧은 글을 양산하면 애드센스 "저품질/실질 콘텐츠 부족" 정책 위반 리스크가
  커진다.
- **민감정보 필터**: 상업적으로 민감한 수치(예: 아직 미공개 수익화 전략, 개인 식별 정보)는
  초안 작성 전에 제외 대상으로 마킹한다. Step 3 리뷰 에이전트가 이 필터링도 겸한다.

## 4. 구현 방식

### 4.1 왜 별도 커스텀 서버가 아니라 Claude Code 자체 스케줄링을 쓰는가

이 저장소에는 이미 `schedule` 스킬과 `scheduled-tasks` MCP(cron 기반 클라우드 에이전트)가
연결되어 있다. 별도 서버/워커를 새로 구축하지 않고, **정해진 주기(예: 매주 일요일)에 Claude
Code 세션을 자동 기동해 이 파이프라인 프롬프트를 실행**하는 방식이 엔지니어링 비용이 가장
낮다. 게임 개발과 무관한 인프라를 새로 만들 필요가 없다.

### 4.2 디렉토리 구조 (게임 코드와 분리)

부서(서브에이전트)는 Claude Code의 표준 서브에이전트 정의 방식(`.claude/agents/*.md`
frontmatter)을 그대로 쓴다 — 이 프로젝트의 다른 서브에이전트(unity-senior-programmer 등)와
동일한 방식이라 별도 프레임워크가 필요 없다.

```
.claude/agents/
  ├── blog-planner.md     # 기획팀 — Step 1 소재 선정 + SEO 키워드 방향
  ├── blog-writer.md      # 작성팀 — Step 2 초안 작성
  ├── blog-reviewer.md    # 검수팀 — Step 3 품질/정책/사실 검증
  ├── blog-editor.md      # 편집팀 — Step 5 SEO 포맷팅·이미지·광고 배치
  ├── blog-publisher.md   # 게시팀 — Step 7~8 게시 실행 + 이력 기록
  └── blog-master.md      # 마스터 에이전트 — Step 4·6 증거 기반 승인/반려 판정

tools/blog-automation/
  ├── README.md              # 오케스트레이션 순서 (Phase 3 스케줄 프롬프트가 따를 절차)
  ├── credentials/           # OAuth 클라이언트/토큰/블로그 설정 — .gitignore 처리, 커밋 금지
  ├── scripts/
  │   ├── blogger-auth.js    # 최초 1회 OAuth 인증 스크립트
  │   └── blogger-client.js  # Blogger API 클라이언트 (token/get-blog/post)
  └── published/             # 게시 완료된 글의 로컬 사본 (이력 확인용)
```

게임 Unity 프로젝트(Assets/, ProjectSettings/)와는 완전히 독립된 디렉토리이며, 게임 커밋
전 체크리스트(CLAUDE.md의 7종 체크)와는 무관하다.

### 4.3 부서(서브에이전트) 구조

| 부서 | 담당 Step | 역할 | 비고 |
|---|---|---|---|
| **기획팀** (`blog-planner`) | Step 1 | git log + memory diff에서 이번 글의 소재를 선정하고 SEO 키워드 방향을 정한다 | 소재가 너무 적으면(3장 기준) 이번 회차를 스킵하도록 판단하는 것도 이 부서 역할 |
| **작성팀** (`blog-writer`) | Step 2 | 선정된 소재로 "개발일지" 톤의 초안 작성 | 독자는 비개발자 포함 — 게임 CLAUDE.md "설명 의무" 원칙 재활용 |
| **검수팀** (`blog-reviewer`) | Step 3 | (a) 사실관계가 실제 커밋/memory와 일치하는지, (b) 애드센스 정책 위반 표현 여부, (c) 최소 분량/실질 콘텐츠 기준 | 영상에서 배운 "증거 제시" 원칙 적용 — 어떤 문장을 어떤 커밋/파일과 대조했는지 근거를 리포트에 남긴다. 통과 못하면 마스터에게 올리지 않고 작성팀에 자체 반려 |
| **편집팀** (`blog-editor`) | Step 5 | SEO 제목/메타 작성, 이미지 삽입, 광고 위치 배치, Blogger HTML 포맷 변환 | 기존에는 별도 단계로만 있었고 담당 주체가 불명확했음 — 이번에 부서로 명시 |
| **게시팀** (`blog-publisher`) | Step 7~8 | 1장 권장안에 따라 게시 실행(완전 무인), 성공 시 게시 이력(`blog_last_published_commit.md`) 갱신 | |
| **마스터 에이전트** (`blog-master`) | Step 4, 6 | 1차(방향/내용)·2차(최종본) 검수. 검수팀 리포트와 실제 산출물을 대조해 증거 기반으로 자체 승인/반려 판정, 승인 시 게시팀에 실행 위임 | 사람 개입 없음 — 전 부서를 통제·조율하는 유일한 게이트지만 그 자체도 에이전트 |

**"증거 제시" 원칙(영상 7번째 세팅에서 채택)**: 검수팀·마스터 에이전트는 "검증 완료"라고만
보고하지 않고, 실제로 대조한 커밋 해시/memory 파일 경로를 판정 근거에 인용한다. 확인하지
못한 항목은 "확인 못함"이라고 그대로 반려 사유에 남긴다 — 사람이 없는 만큼, 이 원칙이
무너지면 형식적 자기승인(러버스탬핑)으로 전락해 품질 게이트가 통째로 무력화된다. 그래서
마스터 에이전트의 승인 출력은 반드시 구조화된 근거 필드를 요구하도록 강제한다(자유
서술로 "확인했음"이라고만 쓰고 넘어가는 것을 금지).

### 4.4 Step 8: 게시 이력 및 중복 방지

게시 성공 시 `memory/blog_last_published_commit.md`를 최신 커밋 해시로 갱신하고,

## 5. 애드센스 수익화 체크리스트

1. **정책 위반 최소화가 최우선**: 애드센스는 "자동/대량 생성 저품질 콘텐츠"를 명시적으로
   금지한다. 이 파이프라인은 완전 무인(사람 검수 없음)으로 운영되므로 "사람이 확인했다"는
   근거를 댈 수 없다 — 대신 **검수팀·마스터 에이전트의 증거 기반 자체 판정(4.3장) + 연속
   반려 시 자동 발행 중단(6장)**이 유일한 안전장치다. 이 장치들이 형식화(러버스탬핑)되지
   않도록 유지하는 것이 이 파이프라인 전체에서 가장 중요한 관리 포인트다. 애드센스 계정이
   정지되면 전체 수익 구조가 무너지므로, 초기에는 스케줄 주기를 낮게(예: 주 1회) 잡아
   실제 게시물 품질을 정기적으로 무작위 점검하는 것을 권장한다(승인 절차는 아니고,
   문제 조기 발견용 로그 확인).
2. **가입 조건**: 애드센스 신규 가입 시 일정 수의 실질적인 글(보통 20~30편 이상 권장, 공식
   기준은 없으나 실무 기준)과 최소 몇 주의 운영 이력이 있어야 승인 확률이 높다. 초기에는
   수익화 없이 콘텐츠 축적 단계로 본다.
3. **SEO 키워드 전략**: "인디게임 개발일지", "Unity GOAP AI", "게임 AI 알고리즘 구현" 등
   틈새 키워드는 경쟁이 적어 신규 블로그도 상위 노출 가능성이 있다. 초안 작성 에이전트
   프롬프트에 이 방향을 명시한다.
4. **광고 배치**: 본문 상단 1개 + 본문 중간 1개 정도로 과도한 광고 밀도를 피한다 (정책
   위반 및 이탈률 상승 방지).
5. **노출 모니터링 (Phase 5 이후)**: 구글 서치콘솔을 사이트에 연동해 게시글이 색인·노출되고
   있는지 주기적으로 확인한다. "검색에 노출은 되는데 클릭이 안 되는지" vs "아예 색인이
   안 됐는지"를 구분해 SEO 제목/메타 수정에 반영한다. 다만 초기(글 5~10편 미만)에는 데이터가
   너무 적어 무의미하므로, 콘텐츠가 어느 정도 쌓인 뒤(Phase 5)에 붙인다.

> **참고 (검토 후 제외)**: 벤치마킹한 영상(AI 직원 8단계 세팅)에는 마케팅팀이 SNS 카드뉴스를
> 자동 생성해 홍보하는 단계가 있었으나, 이 기획서에서는 **채택하지 않는다**. 이유: 이 블로그는
> Unity/GOAP 개발일지 같은 니치 기술 콘텐츠로, 유입이 거의 구글 검색(SEO)에서 발생하고 SNS
> 바이럴 효과는 낮다. 디자인·마케팅 에이전트를 추가 운영하는 비용 대비 효과가 낮다고 판단
> (2026-07-09 사용자 확정). 추후 "개인 브랜딩"으로 목적이 바뀌면 재검토.

**수정**: `tools/blog-automation/.staging/`에 각 단계 결과물을 파일로 저장하는 규칙을
신설(README.md 및 스케줄 태스크 프롬프트에 반영). 재시도 시 "처음부터 다시 써라"가

마라"고 명시하도록 변경. 이 수정으로 Phase 3 자동 실행에서 동일 사고가 반복되지
않도록 했다. 이번 회차는 결국 오케스트레이터(사용자 세션)가 원본 텍스트를 직접
