## 이슈 #1. YIELD 상수 불일치 — 방향이 거꾸로다 🔴

### 검증 결과: 불일치는 사실, 그러나 제안된 수정을 그대로 적용하면 안 된다

이슈는 "FSM의 하드코딩(+10f 등)을 Registry 상수로 교체"를 제안한다. 그런데 실측 대조:

| 항목 | 런타임 실측 (전부 "기획서 수치" 주석) | Registry 현재 | 이슈대로 적용 시 |
|---|---|---|---|
| ChopWood | **+10** (FSM L2145, ActionDatabase L927) | YIELD_CHOP_WOOD = 5 | 채취량 절반으로 **너프** |
| MineStone | **+8** | 5 | 동일 |
| MineIron | **+5** | 3 | 동일 |

Registry의 5/5/3은 Phase 2 실행명세서의 **기본 제안치**가 그대로 들어온 값이고, 런타임의 10/8/5가 기획서 원본 수치다. W3 명세의 원칙은 명확했다: *"플래너 수치를 새로 정하는 게 아니라, 런타임에 이미 존재하는 수치를 플래너에 알려주는 작업."* 중간점검 P2에서 식사/수면을 이 원칙으로 고쳤는데, 채취량은 누락됐던 것이다 (N2 커밋도 ReduceHunger 계열만 처리하고 GainResource 계열은 놓쳤다 — 이슈가 그 빈틈을 정확히 찾았다).

**따라서 올바른 순서는 2단계다:**
1. **Registry 상수를 기획서 수치로 수정** (플래너가 현실을 배운다)
2. 그 다음에 이슈의 제안대로 런타임 리터럴을 상수 참조로 교체 (재발 방지)

## 이슈 #2. BuildHouse / BuildWatchtower 누락 — 사실이며, 단 명세는 보강 필요 🔴

### 검증 결과

사실이다: 레지스트리는 정확히 20개 액션이고 두 건물이 없다. VillageAdvisor가 Day 3+에 House를 자동 큐잉하므로 **매 게임 확정 재현되는 진행 차단**이라는 판단도 맞다. "즉시 수정" 우선순위 동의.

### 그러나 이슈의 제안 명세 2가지를 고쳐야 한다

**① 불리언 게이트 사용 금지 — P4의 교훈 역행.** 이슈는 `HasWoodForBuilding=1, HasStoneForBuilding=1`을 Precondition으로 제안하는데, 이 플래그의 임계값은 35다. House는 목재 **20**, Watchtower는 목재 **10**이면 지을 수 있다 — 불리언 게이트를 쓰면 목재 10~34 구간에서 부당하게 차단된다. P4에서 Campfire/Storehouse를 고칠 때 확립한 패턴(수치 Prec + Sub Effect)을 그대로 따라야 하며, 실제로 현재 BuildCampfire 정의가 정확한 참고 템플릿이다 (이슈가 참고하라고 한 "기존 BuildCampfire 패턴"은 커밋 3534c99 이전의 옛 명세다).

**② Watchtower는 철이 든다.** BuildingCosts.cs 실측: House 20/10(목재/석재), **Watchtower 10/30/5(목재/석재/철)** — 이슈 명세에 철 Precondition이 빠져 있다.

### 확정 명세

```csharp
// ── BuildHouse ── BuildingCosts: HOUSE_WOOD=20, HOUSE_STONE=10
public const int BUILD_HOUSE_WOOD  = 20;   // BuildingCosts.HOUSE_WOOD와 동기 (ADR-7)
public const int BUILD_HOUSE_STONE = 10;

float buildHouseCost = 30f;
if (role == AgentRole.Builder) buildHouseCost *= BUILDER_BUILD_MODIFIER;
defs[i++] = new GOAPActionDef
{
    ActionStringHash = Animator.StringToHash("BuildHouse"),
    BaseCost  = buildHouseCost,
    PrecCount = 3,
    Prec0S = S.BuildingQueued, Prec0V = 1,
    Prec1S = S.WoodStock,  Prec1V = BUILD_HOUSE_WOOD,  Prec1Op = 1, // GreaterEq
    Prec2S = S.StoneStock, Prec2V = BUILD_HOUSE_STONE, Prec2Op = 1,
    EffectCount = 4,
    Eff0S = S.StructureBuilt, Eff0V = 1,
    Eff1S = S.BuildingQueued, Eff1V = 0,
    Eff2S = S.WoodStock,  Eff2Op = 2, Eff2V = BUILD_HOUSE_WOOD,   // Sub
    Eff3S = S.StoneStock, Eff3Op = 2, Eff3V = BUILD_HOUSE_STONE
};

// ── BuildWatchtower ── WATCHTOWER 10/30/5 — 철 Prec 필수!
public const int BUILD_WATCHTOWER_WOOD  = 10;
public const int BUILD_WATCHTOWER_STONE = 30;
public const int BUILD_WATCHTOWER_IRON  = 5;
// PrecCount 4 (BuildingQueued + 자원 3종), EffectCount 5 (Built/Queued + Sub 3종) — 8쌍 한도 내
// BaseCost 35f, Builder ×0.6 — 이슈 제안 값 채택
```

### 이슈가 놓친 연쇄 수정 2곳 (여기서 가장 사고 나기 쉬움)

1. **`names[]` 배열 (해시 역매핑, L~400)**: `"BuildHouse", "BuildWatchtower"` 추가. 빠뜨리면 액션은 실행되는데 사고 체인 UI·로그에서 이름 역조회가 실패한다 — 해시 충돌 감지 로직이 이 배열 기반이므로 반드시 함께.
2. **FSM 실행 매핑 확인**: `State_Executing`의 액션 분기(또는 ActionDatabase)에 BuildHouse/BuildWatchtower 실행 케이스가 실제로 존재하는지 확인. VillageAdvisor가 큐잉해왔다는 건 **건설 실행 경로 자체는 있다**는 뜻이지만, GOAP actionId → 실행 함수 매핑이 제네릭(Build 계열 공통 처리)인지 개별 case인지에 따라 추가 작업이 갈린다. 개별 case 방식이면 두 케이스 추가.

배열 크기 `20 → 22`와 `Debug.Assert(i == 22)`는 이슈 제안 그대로.

### DoD
- [ ] House 큐잉 → 목재 20/석재 10에서 플랜 성공 (목재 34 이하에서도!)
- [ ] Watchtower 큐잉 + 철 0 → 플랜에 MineIron 선행 체인 등장 (철 Prec의 존재 증명이자 수치형 GOAP 쇼케이스)
- [ ] 사고 체인 UI에 "집 건설/망루 건설" 한글 라벨 정상 표시 (names[] 검증)
- [ ] Day 5까지 방치 시 BuildStructure Deadlock 0건

## 이슈 #3. N3 테스트 12케이스 + 플랜 수선 — 승인, 조정 3가지 🟠

### 검증 결과

선행 조건(#1, #2 먼저)이 명시된 것, T05(음수 클램프)·T12(Closed Set 노드 상한) 같은 실전 회귀를 반영한 커스텀 케이스 — 원안(실행명세서 W9)보다 나아진 부분이 있다. 다만 3가지 조정이 필요하다:

**조정 1 — 레벨 혼재 분리.** T04(도구 없으면 GatherFood 선택)와 T10(Idle 폴백)은 **플래너가 아니라 FSM의 Goal 선택 로직**이다. `SelectGatherGoalId()`는 MonoBehaviour 컨텍스트(Brain, _registry)에 묶여 있어 EditMode에서 그대로 못 돌린다. 두 가지 중 택1:
- (권장) `SelectGatherGoalId`의 판단부를 순수 정적 함수로 추출 (`GatherGoalSelector.Select(stocks[], hasTool)`) → EditMode 테스트 가능 + N4에서 GoalArbiter로 흡수하기도 쉬워진다
- (차선) T04/T10을 "Play Mode 수동 체크리스트"로 강등하고 플래너 케이스 2개를 대체 투입

**조정 2 — 빠진 정합성 테스트 복원.** 이슈의 T12가 원안의 T12(플래너 Effect == 런타임 delta 정합)를 Closed Set 검증으로 교체하면서, **ADR-7 자동 강제 테스트가 사라졌다**. 이슈 #1이 바로 그 정합성 버그였는데 그걸 잡는 테스트를 빼는 건 모순이다. **T13으로 추가**하라 (12케이스 고집할 이유 없음):
```
T13: 20(→22)개 액션 각각 — Registry Prec/Eff 수치로 시뮬레이션한 상태 변화가
     런타임 상수(YIELD_*, *_RELIEF, BUILD_*) 기반 기대 delta와 일치
```
이 테스트가 있으면 이슈 #1류의 버그는 **커밋 전에 자동으로 잡힌다.**

**조정 3 — T11(13스텝 실패) 구현 방법.** `BuildGoalState`의 문자열 API로는 "목재 61" 같은 임의 목표를 못 만든다. 테스트 헬퍼가 goalState/goalMask/goalOps **NativeArray를 직접 구성**하는 오버로드를 갖추면 해결된다 (예: 목표 WoodStock ≥ 61, 초기 0, YIELD 10 기준 7스텝… 13스텝 실패를 만들려면 목표 121). #1 수정으로 YIELD가 바뀌므로 **테스트 수치는 상수 참조로 계산**할 것 — `target = YIELD_CHOP_WOOD * 13 + 1` 식으로 쓰면 밸런스 변경에도 테스트가 안 깨진다.

플랜 수선 파트(PlanRepairCount, TryRepairPlan, 실패 시 전체 Replanning 폴백, 패널 표시)는 이슈 명세 그대로 진행 — 로드맵 N3의 수선 카운터 설계와 일치한다.

### DoD (이슈 완료 조건에 추가)
- [ ] T13 정합성 테스트 포함 (13케이스)
- [ ] 테스트 내 모든 기대 수치가 리터럴이 아닌 Registry 상수 참조로 계산됨
- [ ] T04/T10의 레벨 분리 방식 결정이 커밋 메시지에 기록됨
