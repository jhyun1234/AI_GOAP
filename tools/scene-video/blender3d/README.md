> ## 🔄 2026-08-16 — 사람은 이제 Mixamo 것이다
>
> 코드로 지은 리그·모델(`rig.py`·`model.py`)과 손으로 짠 동작 22종(`motions.py`),
> 그리고 그 둘을 잇던 리타기팅(`mocap2pose.py`·`mocap.py`)을 **전부 지웠다**(약 9,800줄).

>
> **왜** — 캐릭터와 동작이 같은 뼈대(`mixamorig:*`)를 쓰면 옮길 것이 없다. 옛 판이 밟은
> 지뢰 여덟(오일러 짐벌 · roll 임의값 · 레스트 차이 43° · 자동 웨이트 폭발 · 척추 3→1 ·
> 축 켤레)은 전부 「남의 뼈대를 우리 뼈대로 옮긴다」에서 나왔고, 그 전제를 지우면 같이 사라진다.
>
> **딸려온 것** — 주민 키가 0.95 → **1.70m** 이고, 마을은 `village.SCALE`(1.789)로 통째로
> 커진다. 🔴 마을 좌표를 바깥에서 쓸 때는 `village.at()` 을 거쳐라. 날것 `SPOTS` 는
> 지어지기 전의 단위다. `build()` 뒤에 소품을 더 놓을 때는 `village.add()` 다.

블렌더가 **1080 × 846 알파 PNG** 를 굽고, 엔진 캔버스가 그것을 `drawImage` 로 그린 뒤
자막·HUD·계기층을 위에 얹는다. 그 크기는 쇼츠 1920 중 자막·HUD 를 뺀 안전 띠(y 420~1266)다.

## 왜 캔버스 안에 넣는가

🔴 **`check.mjs` 는 캔버스 픽셀을 읽는다.** 그림이 캔버스 밖으로 나가면 팔레트·정적·잘림·
결정성 게이트가 전부 장님이 된다. 그래서 `serve.js` 에 `/3d/` 라우트를 두고 **같은 오리진**
으로 준다 — 다른 오리진에서 받은 이미지를 캔버스에 그리면 캔버스가 오염되어
`getImageData` 가 예외를 던진다.

## 실행

```bash
BL="C:/Program Files/Blender Foundation/Blender 5.2/blender.exe"
"$BL" --background --factory-startup --python mixamo.py -- build   # 사람+동작 → ybot.blend
"$BL" --background --factory-startup --python mixamo.py -- demo    # 자체 점검
"$BL" --background --factory-startup --python village.py           # 마을 → village.blend

"$BL" --background --factory-startup --python render_mixamo_check.py  # 동작이 읽히나
"$BL" --background --factory-startup --python render_village_look.py  # 축척이 맞나

python bake.py                    # 샷 여섯을 동시에 굽는다(기본 -j 3)
python bake.py hook body1 -j 2    # 고른 것만
python bake.py --range 0:23       # 샷마다 앞 24프레임만 — 재거나 눈으로 볼 때
```

🔴 `bake.py` 가 부르던 회차 샷 스크립트(`render_body*`·`render_hook`·`render_outro`)는
철거됐다. **새 회차를 만들기 전까지 `bake.py` 는 굽을 것이 없다** — 이건 고장이 아니라
아직 안 지은 것이다.

GUI 블렌더에서 굽지 않고 보려면 [`live.py`](./live.py) 다. BlenderMCP 로 붙은 창에서:
```python
import live; ns = live.show('render_body1.py'); live.frame(ns, 3.4)
```
그다음 그냥 재생(Space)하면 돈다 — **렌더와 같은 코드**가 프레임마다 돈다.

경로는 `stage.py` 가 혼자 정한다. 산출물 루트는 환경변수 `SCENE_3D_ROOT`(기본
`D:\AI_GOAP-videos\3d`)이고, **`serve.js` 가 같은 변수를 본다** — 한쪽만 바꾸면 어긋난다.

| | 어디 |
|---|---|
| 스크립트 · 모델 원본(`../blender/Shorts.blend`) | 리포 |
| 리그·마을 `.blend` · 렌더 프레임 · mp4 | `SCENE_3D_ROOT` |

## 조정 손잡이 둘 (`stage.py`)

- `EXPOSURE` — 인물의 밝은 면이 sRGB 0.85 근처에 앉는 값. 1.85 에서 실측 218/255, 클리핑 0px.
- `LANE_LEVEL` — 바닥 알베도. `EXPOSURE` 로 나눠 써서 **노출을 바꿔도 바닥 밝기는 안 변한다.**

🔴 눈으로 고치지 마라. 이 값들은 픽셀을 재서 맞춘 것이고, 눈대중으로 만지다 세 판을 헛돌았다.

## 함정 여섯 — 전부 한 번씩 밟았다

1. **GLB 임포트 객체는 `rotation_mode` 가 `'QUATERNION'`** 이라 `rotation_euler` 가 무시된다.
   안 바꾸면 인물이 전부 옆을 본 채 렌더된다.
2. **Blender 5.2 는 `Material.use_nodes` 를 아직 본다**(6.0 제거 예정 경고만 뜬다).
   안 켜면 노드 트리를 무시하고 **기본 회색 0.8** 로 렌더된다 — 바닥이 사람보다 밝아진다.
3. 바닥을 눕혀서 보면 **스치는 각도의 프레넬 정반사**가 알베도를 압도한다.
   알베도를 0.035 까지 떨어뜨려도 밝다. `Specular IOR Level = 0` 으로 끈다.
4. `view_transform` 이 `'Standard'`(롤오프 없음)라 **광량을 올리면 바로 흰색 클리핑.**
   그 상태에서 어두운 바닥이 중간 회색으로 올라와 「바닥이 밝다」로 오진하게 된다.
5. ~~뼈 roll~~ → **Mixamo 뼈대를 쓰면서 사라졌다.** 우리가 뼈를 안 놓으니 roll 도 없다.
6. 유채색 물체를 **스케일 0 이나 발광 0 으로 끄면 밑색이 남는다.** 흰색만 있어야 할
   프레임에 유채색이 남아 규약을 깬다. `stage.gate()` 가 `hide_render` 로 렌더에서 뺀다.

## Mixamo 판에서 새로 밟은 지뢰 다섯 (2026-08-16)

1. **키가 1/100 이 된다.** Mixamo 메시는 자기 스케일 0.01 을 부모 역행렬 100 으로 상쇄하는데,
   `mesh.parent = arm` **대입 자체가 그 역행렬을 리셋한다.** 복사해 두고 다시 넣어야 한다.
2. **사람이 반만 선다.** Y Bot 은 메시가 **둘**이다(몸통·관절). 하나만 복제하면 반이 없다.
3. **걸음마다 3m 씩 튄다.** 스케일을 `transform_apply` 로 구워 넣으면 뼈만 100배가 되고
   액션의 골반 이동 키는 안 따라온다. **회전만 굽고 스케일은 객체에 남긴다.**
4. **블렌더 4.4+ 는 `action.fcurves` 가 없다**(5.2 에서 제거). 슬롯 액션이라
   레이어→스트립→채널백을 타야 한다(`mixamo.fcurves`).
5. **쿼터니언 노름이 1 을 벗어난다**(실측 0.9954). 성분을 fcurve 별로 따로 보간하기
   때문이다. `play` 가 마지막에 정규화한다.

그리고 인물 알베도는 **`stage.INK_LIN`(0.62)과 다르다**. 같은 값을 주면 인물의 37.9%가
순백으로 클리핑한다 — 도형은 평평해서 정면광을 한 면으로만 받고 사람은 굽은 면이다.
`palette.FIGURE_LIN`(0.30)이 단일 출처다.

## ~~발은 땅에 붙는다 — 다리는 IK 로 역산한다~~ (2026-08-13, 철거됨)

🔴 아래는 **`motions.py` 시절의 기록**이다. 그 파일과 함께 지워졌다. 남겨 두는 이유는
결론이 아니라 **재는 법** 때문이다 — 모캡으로 바꿔도 「디딘 발이 미끄러지는가」는
여전히 물어야 하고, 그때 재는 자리와 문턱(2cm · 골반 가속도 0.016)이 여기 적혀 있다.

걷기·뛰기의 다리는 **`motions.py` 가 각을 적지 않는다.** 발이 있어야 할 자리를 먼저 정하고
허벅지·정강이를 두 뼈 IK 로 역산한다(`_gait_plan` → `_foot` → `_legs` → `_leg_ik`).

- **왜** — 순수 FK 에는 디딘 발이 고정되는 순간이 아예 없었다(실측 최대 **23.8cm** = 보폭의
  76%). 사람 눈이 가장 먼저 잡는 결함이고 **눈높이로 다가갈수록 더 드러난다.**
- **결과** — 디딘 자리의 세계 이동 **0.000 m**(검사가 2cm 에 문턱). 스킨된 발바닥 정점으로
  블렌더에서 다시 재도 발바닥이 붙어 있는 동안 프레임당 0.4mm 다.
- 🔴 **골반 상하는 이제 계산 결과다.** 발을 묶으면 다리 길이가 천장이라, 보폭 31.3cm 를
  다리 24.5cm 로 감당하려면 이중지지에서 골반이 **3.5cm** 내려앉아야 한다(앞 판은 손으로 적은
  1.4cm 였고, 그래서 발이 미끄러질 수밖에 없었다). 사람 걷기의 상하가 키의 3% 근처다 — 계산이
  거기로 떨어졌다.
- 🔴 **발 크기는 뼈가 아니라 메시를 재서 넣는다.** 뼈 꼬리(발목 앞 0.075)를 발끝으로 알고
  한 판 버렸다. 실측한 발바닥은 발목 **뒤 2.5cm ~ 앞 14.1cm**(길이 16.6cm)다. 발이 길다는 것이
  값을 한다 — 발끝을 축으로 미는 지렛대가 그만큼 길어서 골반이 덜 내려앉아도 된다.
- 🔑 **`WALK_THIGH` 는 이제 각이 아니라 보폭 손잡이다.** 키우면 골반이 더 내려앉는다.
  ❌ `WALK_SLIP`(속도를 깎아 미끄러짐을 감추던 손잡이)은 걷어냈다 — 1 이 아니면 그 자체가
  미끄러짐이다.
- 검사 셋이 지킨다: 디딘 발 이동 < 2cm · 다리가 모자라 잘리지 않음(무릎 역꺾임 포함) ·
  골반 곡선의 가속도(30fps 2차 차분) < 0.016. 셋 다 `bpy` 없이 돈다.

## 굽는 구조 — 한 번에 굽고, 프레임은 핸들러가 그린다 (2026-08-13)

샷 스크립트는 `def draw(fi)` 를 정의하고 끝에서 `stage.bake(OUT, NF, FPS, draw, 태그)` 를
부른다. `bake` 가 `draw` 를 **프레임 변경 핸들러**로 걸고 `render(animation=True)` 를
한 번 부른다. 프레임마다 `render(write_still=True)` 를 부르던 앞 판을 대체한 것이다.

- 속도는 곁다리다: 0.288 → **0.267 s/frame**(7%).
- 진짜 이유는 **길이 하나가 된 것**이다. 굽는 길과 GUI 에서 보는 길이 같은 `draw` 를
  돈다 — `live.py` 가 `stage.LIVE` 를 켜면 `bake` 는 굽지 않고 핸들러만 건다.
  타임라인 재생·스크럽이 렌더와 같은 계산이라 「본 것과 구운 것이 다르다」가 안 생긴다.
- 🔴 **키프레임을 굽는 것이 아니다.** 키를 만들면 스크립트가 정본이 아니게 되고
  결정성 게이트가 검증하는 대상 밖으로 나간다.
- 파이썬 계산은 병목이 아니다: 214프레임 **0.64초** — 렌더 61.6초의 1%다. 여기 손대지 마라.
- 전환 검증: 샷 여섯 × 프레임 셋을 앞 판과 픽셀 비교해 **maxdiff 0.0**(PNG 바이트는
  1바이트 다른데 렌더 시각 메타데이터다). 검사 8종·게이트 33종 통과.

## 병렬은 어디까지 먹히나 (실측 · 샷 여섯 × 40프레임)

| `-j` | 벽시계 | 프로세스 시간 합 | 배속 |
|---|---|---|---|
| 1 | 116.9초 | 116.9초 | 1.00× |
| 3 | 76.1초 | 156.2초 | **1.54×** |
| 6 | 64.8초 | 229.6초 | 1.80× |

🔴 **샷 수만큼 안 빨라진다.** 프로세스들이 같은 GPU 를 나눠 쓴다 — `-j` 를 6 으로 올리면
프로세스 시간 합이 2배로 늘어난다(대기). 그리고 **천장은 가장 느린 샷 하나**다:
`body3` 이 혼자 47.2초인데 `-j 6` 벽시계 64.8초가 곧 그 샷 시간이다.
그래서 기본값은 **3**이다. 더 줄이고 싶으면 `-j` 가 아니라 body3 을 봐라.

## 로우폴리는 답이 아니다 (실측)

| | 64 샘플 | 16 샘플 |
|---|---|---|
| 원본 (인물 면 40,716) | 0.268 s/frame | **0.151 s/frame** |
| 데시메이트 25% (10,176) | 0.280 s/frame | 0.181 s/frame |

면을 75% 날려도 **더 느리다** — 데시메이트 모디파이어가 매 프레임 평가된다.
손잡이는 **샘플 수**다. 그리고 이 캐릭터는 이미 로우폴리다(6,786 삼각형 · 플랫 셰이딩).
🔴 그래서 **새 소품도 로우폴리 플랫 셰이딩으로 만든다.** 매끈한 소품을 넣으면 그때 깨진다.
