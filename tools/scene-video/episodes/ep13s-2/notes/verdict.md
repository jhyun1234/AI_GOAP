## 2. 수치 — 전수 + 「그 수가 그 슬롯의 값인가」

### 2-2. 🔴 1차 반려의 핵심 — 슬롯 결합을 다시 물었다

**결론: 수리가 옳다.** 다만 **`minTo: "5"` 는 인용이 아니라 추론**이므로 사슬을 박아 둔다.

- 원문이 직접 말하는 것 두 개뿐 — ①고치기 전 카탈로그 최저 = **5** ②간호를 **1 → 8**.
- 원문은 *"고친 뒤 최소 비용이 5로 돌아왔다"* 고 **적지 않는다.**
- 성립 근거: 8 > 5 이고, 1 을 걷어내면 남는 최저가 다시 5 다. 원문의 게이트 문장
  *"카탈로그의 최소 비용이 기준선 밑으로 내려가면"* 이 **고친 뒤 최저가 기준선 위**임을
  전제하므로 방향도 맞는다. 승인·발행된 롱폼 `lf02`(`kinds/costfloor.js`)가 같은 사슬로
  기준선 5 · `TendInjured 8` 을 그렸다 — 리포 안에서 해석이 일관된다.
- 🔑 **그리고 화면은 기준선의 수를 안 적는다**(`gateLabel` = 「기준선」, 숫자 없음).
  원문에 없는 값을 세우지 않았다. 이 자리에 어떤 수를 적었으면 그게 지어낸 수치다.

**형제 편과도 어긋나지 않는다** — `ep13s-1` 의 `excluded` 가 이 편 재료를
「**간호 비용 1 → 8** · **최저 비용 5 → 1**」로 적어 두고 있다. 세 편이 같은 독법이다.

## 3. 픽셀 확정 재현 — **내가 렌더한 프레임으로** 다시 쟀다

🔑 마스터 교훈(ep12s-3): *kind 를 고쳤으면 스틸을 다시 뽑은 뒤에 「확인했다」고 말해라.*
`kinds/overrun.js` 가 10:56 에 바뀌었으므로 **검수 스틸을 근거로 쓰지 않고 직접 다시 떴다.**

### 3-1. 재는 방법 (판정서에 함께 적는다 — 척도가 갈린 전례가 있다)

1. `node tools/scene-video/render.mjs ep13s-2 --still 26.6,24.85,23.6,25.9,20.9`
   → **렌더 전 md5 와 렌더 후 md5 가 같다**(`26.6s.png` = `68816c8a…`).
   즉 검수 스틸은 현행 코드의 진짜 렌더이고, 아래 측정은 **내가 만든 프레임**의 것이다.
2. `ffmpeg -i <png> -pix_fmt rgb24 -f rawvideo` 로 1080×1920 원시 바이트.
3. 흰 = `r,g,b > 150` 이고 채널 편차 < 30 · 강조색 = `g>60 && g−r>25 && g−b>18`(검수와 같은
   **느슨한** 문턱 — 통과시키기 쉬운 쪽이 아니라 접촉을 **잡기 쉬운** 쪽이다).
4. **좌표계는 가정하지 않고 화면에서 역산했다.** 세로는 「간호 8」 칩(캔버스 y 52~84,
   획 3)이 화면 558~655 로 나오는 것에서 `Y0 = 418.9`, 가로는 1번 칸 왼쪽 획(캔버스 22)과
   마지막 칸 오른쪽 획(캔버스 230)의 화면 중심 115.5·688.5 에서
   **`s = 2.7548` / `X0 = 54.9`** (`x_css = (x_screen − 54.9) / 2.7548`).
   기기 DPR 1080/392 = 2.7551 과 일치한다. 검수의 2.753 과도 같다.

### 3-2. 걸음 칸 — 검수 값이 그대로 나온다

`26.6s.png` 캔버스 y 190(화면 942) 의 흰 런:

```
내 측정  [112,119] [189,201] [271,284] [354,367] [437,449] [519,532] [602,615] [685,692] [776,788]
검수     [111,119] [189,202] [271,284] [354,367] [437,449] [519,532] [602,615] [684,692] [775,788]
```

±1px(문턱 차) 안에서 같다. 여기서 나오는 값:

- **런 9개 = 칸 8런 + 한도선 1** → 칸 개수 `N+1 = 8` → **N = 7칸.**
  코드 산술과도 같다(`endX = CAP−8 = 256`, `x < 228` → 22·52·82·112·142·172·202).
- 이웃 런 중심 간격 82.5 · 83 · 82.5 · 82.5 · 83 화면 px → **pitch = 30.02 CSS px.**
- 마지막 칸 오른쪽 획 끝 CSS **231.3** · 한도선 CSS **261.4~266.1**(중심 263.7 ≈ `CAP` 264)
  → **`w = CAP + 88 = 352`.**

### 3-3. 🔑 **「폭 30 = 비용 5」를 회차 안에서 실측으로 세웠다** (검수가 안 한 것)

검수는 「S2 의 척도로 보면」이라고 **주장**했다. 나는 그 척도를 **S2 프레임에서 직접 쟀다** —
새로 뜬 스틸 둘로:

| 스틸 | 화면의 「최소 비용」 | 눈금 간격(내 측정, CSS) |
|---|---|---|
| `15.4s.png` (S2 앞) | **5** | 29.76 · 30.13 · 30.13 · 29.76 · 30.13 · 29.76 · 30.13 → **≈ 30.0** |
| `18.6s.png` (S2 뒤) | **1** | 6.17 · 5.81 이 50번 되풀이 → **≈ 6.0** |

→ 척도는 **6 CSS px = 비용 1** 이고, S3 의 최종 pitch 30.02 는 **정확히 비용 5** 다.
화면 글자 `5` 와 폭이 같은 말을 한다. **1차의 26(= 비용 4.34)이 어긋났던 것도 이 척도로 확정된다.**
🔴 이 확정은 **노트·주석을 근거로 삼지 않았다** — 두 샷의 렌더된 픽셀만 썼다.

## 4. 새 요소(칩)가 결함을 만들었는가 — 두 축 다 쟀다

### 4-1. 강조색 ↔ 흰 : **접촉 0 픽셀** (검수 6장 → 내가 **14장**으로 넓혔다)

| 스틸 | 7.6 | 13.4 | 19.4 | 20.9 | 21.6 | 23.31 | 23.6 | **23.9** | 24.2 | **24.4** | 24.85 | 25.6 | **25.9** | 26.6 | 31.42 |

**SH·S1·S2·S3·SO 다섯 샷 전부 0.** 칩은 결함을 만들지 않았다.

### 4-2. 흰 ↔ 흰 : 접촉은 없다 — 🔴 **다만 검수 수치 두 개를 교정한다**

캔버스 y 190 을 CSS 로 풀어 색까지 분류해 재면:

| 프레임 | 마지막 칸 오른쪽 획 | 한도선 왼쪽 획 | 실측 간격 |
|---|---|---|---|
| `26.6s` (안정) | …231.2 | 261.4… | **30.2 CSS px** (검수 31.5) |
| `23.6s` (전이 최악, fix≈0.84) | …257.4 | 260.6… | **3.2 CSS px** (검수 5.25) |

**왜 갈렸나 — 검수가 한도선 획 두께를 고정으로 봤다.**
`overrun.js:122` 가 `lineWidth = 5 + 2 * clamp(grow * (1 − gate))` 다. 칩이 들어오는 동안은
`grow = 1 · gate = 0` 이라 획이 **7**이고, 왼쪽 모서리가 261.5 가 아니라 **260.5** 다.
검수가 5 로 놓아 **1px 낙관**했고, 거기에 획 반폭을 안 뺀 차가 더해져 5.25 ↔ 3.2 가 됐다.
칸 쪽 끝(기하 256.25)은 검수 값이 정확히 재현된다.

🟢 **결론은 안 바뀐다** — 최악 프레임에서도 **3.2 CSS px(= 8.8 화면 px) 떠 있고 접촉 0** 이다.
오차 방향이 검수에게 유리한 쪽이었다는 사실만 남긴다.

🟡 **cue 0 구간에서 칸이 한도선을 통과하는 것은 설계된 사건**이다(`20.9s`·`21.6s` 에서 런이
258.5~269 로 병합된다). 넘어간 칸은 `over/40` 알파로 사그라들고 둘 다 흰색이라 색 충돌이
아니다 — `reads` 가 *"넘어가 사그라들고"* 라고 미리 선언한 그림이다.

### 4-3. 🔴 「66px」 판정 — 검수가 옳다. **그리고 검수가 한 곳을 빠뜨렸다**

검수는 작성팀 자기보고 「칩과 흰 라벨이 66px 뜬다」가 **틀린 쌍을 잰 수치**라고 했다.
캔버스 y 70 을 색 분류로 재서 확인했다:

```
W[23.3..67.5]  ← 흰 라벨 「최소 비용」
A[87.5..101.7] ← 강조색 값 숫자 「5」
A[148.5..235.2]← 강조색 칩 「간호 8」 (왼쪽 획 148.5~151.4 = x 150, 획 3)
```

- 그 줄의 **실제 최근접 쌍은 칩이 아니라 값 숫자**이고 간격은 **67.5 → 87.5 = 20.0 CSS px.**
  검수의 「약 20 CSS px」이 그대로 재현된다. ✅ **검수 판정이 옳다.**
- 게다가 노트가 이름을 댄 쌍(라벨↔칩)조차 **66 이 아니라 81.0 CSS px** 다. 노트가
  라벨을 22~84 로 봤는데 실제는 22~67.5 라, **쌍도 틀리고 그 쌍의 수도 틀렸다.**
- 🔴 **검수가 빠뜨린 것**: 같은 틀린 수가 `notes.색과 겹침` 말고 **`kinds/overrun.js` 41~42행
  주석**에도 그대로 있다 (*"흰 라벨 「최소 비용」은 x 22~84 라 칩과 66px 뜨고"*).
  검수는 노트 한 곳만 지적했다. **「고칠 곳을 전수로 세었다」가 또 전수가 아니었다** —
  내 판정 이력에서 다섯 번째다.

**접촉 0 이므로 그림의 결함이 아니고 1차부터 있던 배치라 이번 수리의 회귀도 아니다.**
→ **반려 사유로 세우지 않고 §7 의 인계 조건으로 넘긴다.**

## 5. 소리 — `delayMs` 산수를 엔진에서 다시 풀었다

`check.mjs` 에 sfx 검사가 0건이라 기계 게이트가 없는 유일한 계층이다. 직접 풀었다.

`:396` `cue(i,lead,span)` = `a = t−lead`, `b = t + dur×span`.

| 소리 | `rel.dur` | 창 `W` | 리빌 문턱 | **내 계산** | 대본 | 차 |
|---|---|---|---|---|---|---|
| S2 `drop` (`at 0`) | 4,100+180 = **4.280s** | 0.15 + 4.280×0.85 = **3.788s** | `shr` c0 = 0.52 | **1,820ms** | 1,820 | **0** |
| S3 `latch` (`at 1`) | 3,702+200 = **3.902s** | 0.15 + 3.902×0.80 = **3.272s** | `gate` c1 = 0.52 | **1,551ms** | 1,550 | **1ms** |

**검수 실측이 그대로 재현된다.** 두 값 다 리빌이 열리는 첫 프레임에 놓였다(임계가 아니라

🔑 **`delayMs` 는 이 대본에서 안전하다** — 검수 2차 이후 `timed.json` 이 안 바뀌었고(10:22,

## 7. 내가 판단하라고 넘어온 것 — 결정

### 7-1. 본문 18.1초(하한 +0.1초) → **승인한다. 반려하지 않는다.**

- 길이 정본은 W3 하나이고 `본문 18~22초` 는 **통과**다. 총 34.5초도 권장대역 안,
  경고 0건이다. **「여유가 없다」는 규격에 없는 잣대**이고, 그걸로 반려하면
  ADR-V-7(미측정 주장으로 규칙 만들지 않기)을 내가 어기는 것이 된다.
- 🔴 대신 **인계 조건으로 못 박는다**: 이 회차의 본문 자막(`SH`·`S1`·`S2`·`S3`)을
  **한 글자라도 줄이는 수정은 `check.mjs` 를 다시 돌리기 전에는 확정하지 않는다.**
  6.67자/초에서 한 글자 ≈ 150ms 이므로 **한 글자만 줄여도 17.95초로 warn** 이다.

### 7-2. 어미 `-었어요` 3연속 → **그대로 둔다.** 단, 사유를 갈아 끼운다.

- **작성팀이 든 사유는 틀렸다. 내가 코드로 확인했다.**
  `engine.js:205` 가 `rel = ls.map(l => ({ t: (l.t − ls[0].t)/1000, … }))` 로 **샷 상대 좌표**이고,
  `tts.mjs:64` `keyOf` 가 `voiceName|speed|steps|say` 를 FNV 해시해 파일명을 만든다.
  → **S1 을 고쳐도 S2·S3 의 `rel` 도 wav 도 안 움직인다.** 「`delayMs` 근거가 흔들린다」는
  근거가 성립하지 않는다. **검수의 반박이 옳다.**
- 그런데도 두는 이유는 **§7-1** 이다 — 가장 자연스러운 개작(「…못 캐더라고요」)이 한 글자
  짧아져 그 자리에서 warn 을 만든다. 굽는다면 **같은 길이 이상의 변형만.**
- 🔴 **이것으로 반려하지 않는 이유는 「이번엔 봐준다」가 아니다.** `voice.json` `rules.1` 은
  9편 중 5편에서 위반됐고 게이트가 0건이다 — **파이프라인 문제로 이미 승격된 항목**이라
  단독 반려 사유로 못 쓴다(ep12s-3 판정). 이 편에 벌을 주면 규칙이 아니라 복권이 된다.

### 7-3. 한국어 라벨(개정 `ADR-V-10`) → **통과.** 영어 전수를 내가 다시 셌다.

화면 문자열을 기계로 뽑아(§2) 영어를 전수로 셌다. **캔버스 라벨의 영어는 딱 둘이다.**

| 영어 | 자리 | 원문 출현 | 예외 항 |
|---|---|---|---|
| `NoSolutionFound` | S1 콘솔 줄 | **1회** | ⓐ 코드·로그 그대로 인용 |
| `MAX_NODES` | S3 한도선 | **1회** | ⓐ 〃 |

둘은 원문의 **같은 한 문장** 안에 있다 — *"「NoSolutionFound는 버그 증상 — MAX_NODES
인상으로 해결 금지」"*. 규칙 조항을 **증거로 보여 주는** 자리라 옮기면 「증거」가 「번역」이

「기준선」·「경우의 수」·「플래너」가 전부 한국어다.
🔴 **`ep06s`~`ep12s-3` 은 반대 규칙으로 나갔으므로 선례로 인용하지 않았다.**
`NoSolutionFound`·`MAX_NODES` 만 mono, 한국어는 전부 disp 로 갈라 둔 것도 맞다(SceneMono 에
한글이 없어 폴백이 머신마다 갈리는 사고를 막는다).
